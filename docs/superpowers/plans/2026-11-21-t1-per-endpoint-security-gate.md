# T1 per-endpoint HTTP security gate Implementation Plan

> **For agentic workers:** Run `/sharpit:status --feature t1-per-endpoint-security-gate` for the next unchecked step. Execute one task at a time; run `/sharpit:check` before every commit.

**Goal:** Add an opt-in pytest advisor that evaluates explicitly configured response expectations against HTTP requests host tests already make, and reports unobserved expectations as unknown.

**Architecture:** Keep observation and framework adapters in `sharpit.pytest_plugin/`; keep normalized facts and findings in the existing engine test-session/advisor path without importing pytest or web frameworks into the engine. Observe only requests made through an explicit pytest wrapper for the exact registered app; previous requests outside that wrapper do not count. FastAPI/Starlette and Flask adapters wrap the exact app supplied to the fixture; automatic app discovery does not imply observation. Omit sensitive values before facts are stored, and reuse existing findings, xdist aggregation, severity, report-only, baseline, terminal, JSON, SARIF and JUnit paths.

**Tech Stack:** Python 3.12+, pytest, pytest-xdist, Starlette/FastAPI and Flask test extras; existing sharpit findings and test-session reporting.

## Global Constraints

- Python `>=3.12`; runtime dependencies exactly `starlette` and `packaging`. `fastapi` and `pydantic-settings` are optional: import them only inside `try/except ImportError` or in `sharpit/fastapi/`.
- **Reads have no side effects:** no GET route and no read MCP or CLI tool of the console installed in a host application may open a socket, write a file, change a logger level or change `os.environ`.
- **Fails closed.** Inactive means every path under the mount answers 404 and reveals nothing.
- **Guard chain on every request**, in order: security headers → trusted source → Host allow-list → cross-site → token → panel access. Forwarded headers never grant trust.
- **Secrets masked** before filtering and before any output (JSON, errors, MCP, CLI). `FULL` exposure warns.
- **No side effects on reads; actions only behind BootUI's gates.**
- **Introspection is defensive**: FastAPI/Starlette internals change between versions; degrade, never crash the host.
- Dependencies point inward; `engine/` never imports pytest, FastAPI or Starlette. No module under `src/` may exceed 1000 lines.
- Port BootUI where it has a counterpart. T1 has none: a search of the BootUI v2.5.0 tag for `per.?endpoint|security gate` in `*.java` returns 11 lines in 7 files, all of them a per-endpoint Spring Security authorization report, per-endpoint actuator exposure checks, comments or test names, and none is a response header or status expectation gate; do not invent `# ported:` citations or BootUI goldens. Record its explicit sharpit-only deviation in the lane matrix.
- Every defect found becomes a regression test seen red first; tests use one condition per assert. Tests follow the repository's parallel-test workflow. Never weaken tests or raise an overhead budget.

## Risk register

| Severity | Risk | Mitigation |
|---|---|---|
| Critical | Raw authorization, cookie, query or response-header values enter stored facts or an output sink | Capture names/status only; omit values and bodies before facts are created; test all report formats and exception paths with secret canaries. |
| Critical | Enabling the HTTP advisor changes app behavior, sends probe requests or activates runtime capture implicitly | Separate explicit `--sharpit-http-security` / `sharpit_http_security` opt-in; observe only requests already generated by tests; preserve exact response and middleware order. |
| High | Route metadata is mistaken for an authorization contract or incomplete evidence is called a pass | Evaluate only explicit expectations; any configured expectation without complete matching evidence is UNKNOWN, which fails by default. PARTIAL may describe unrelated coverage only. |
| High | FastAPI and Flask paths produce inconsistent attribution or alter test-client behavior | Normalize method, canonical route, status and header names in pytest-facing adapters; freeze the fixture factory contract and prove both adapters and an opaque-wrapper fallback. |
| High | A response violates an expectation on one of several exchanges but aggregate route facts hide it | Evaluate each finished exchange against its method-and-route policy; one violating exchange emits one stable finding per rule and policy key. |
| High | Findings gate the run incorrectly or baselines hide unknown coverage | Use a separate advisor/rule path from `test-runtime`; reuse current xdist and report semantics; baseline only stable route/rule fingerprints and refuse partial/unknown writes. |
| High | Per-request overhead grows with payload size or report output | Never read/copy bodies or header values; bound metadata and measure observer-on/off overhead with the production pytest wrapper. |

## Task 1: Freeze opt-in and expectation contract

**Files:** `src/sharpit/pytest_plugin/options.py`, `tests/pytest_plugin/test_http_security.py`, `docs/reference/matrix-updates/0.8.0-t1.tsv`, `docs/superpowers/specs/2026-10-30-sharpit-mvp-design.md` §14.

**Interfaces:** Adds `--sharpit-http-security` and `sharpit_http_security` (default false). Adds the function-scoped fixture `sharpit_http_observed`. A pytest fixture cannot take a call-time argument, so the fixture value is a callable `observe(app) -> app_or_wrapper`, used as `client = TestClient(sharpit_http_observed(app))`. It is defined in the `sharpit.pytest_plugin` module, which the `pytest11` entry point registers, so tests need no import and it is listed by `pytest --fixtures`. With observation disabled, `observe(app)` returns the same object by identity, wraps nothing and records nothing. Configured expectations without the option enabled are a pytest configuration error raised at configure time. With the option enabled and expectations configured, a test run in which `observe` is never called leaves each expectation UNKNOWN. Calling `observe` again with the same app within one test returns the existing wrapper or patched app and never nests a second layer. For FastAPI/Starlette, observation returns a separate ASGI callable and leaves the supplied app untouched. For Flask, a wrapper object cannot replace the app (`FlaskClient` needs the real `Flask` instance), so observation patches `app.wsgi_app` in place, returns the same Flask app, and restores the exact original callable at teardown; the two adapters therefore have different mutation contracts, and the documentation says so. Adds repeatable `--sharpit-required-response-header "METHOD ROUTE=HEADER"` / `sharpit_required_response_headers` and `--sharpit-expected-status "METHOD ROUTE=STATUS[,STATUS...]"` / `sharpit_expected_statuses` (pytest linelists); any listed status satisfies that route's status expectation. CLI expectation options replace their ini values as a whole. Methods normalize to uppercase, header names compare case-insensitively, duplicate method/route declarations deduplicate, status sets union per route, and route templates use one normalized syntax (`{name}`) across adapters. Parsing splits `METHOD ROUTE=HEADER` on the first space and the last `=`, strips surrounding whitespace from each part, and accepts a route containing `=` or `,`. A header expectation and a status expectation for one route are independent policies. A configured expectation is evaluated per finished matching exchange, not per route aggregate: an expectation holds only if every finished exchange of that method and route satisfies it. Every violating exchange can establish a finding, deduplicated to one per rule and `(method, route, header)` or `(method, route)` status policy key, whatever the number of violating exchanges. Expected statuses do not scope header checks, so a header expectation also applies to error and not-modified responses of the same route; a test that deliberately exercises a response that legitimately omits the header must target a route without that expectation. A header expectation scoped to statuses is out of scope for this lane. No response start means no exchange and cannot satisfy an expectation. HEAD/OPTIONS responses follow the observed status and headers; websocket and lifespan scopes are passed through and excluded. No implicit policy. An unobserved or incompletely observed configured expectation is UNKNOWN, never PARTIAL, and prevents baseline writes.

## Task 2: Add bounded facts and explicit expectation evaluation

**Files:** `src/sharpit/engine/advisors/http_security.py` (new), advisor registration under `src/sharpit/engine/advisors/`, `src/sharpit/engine/testsession/facts.py`, `src/sharpit/engine/testsession/sink.py`, and `tests/engine/advisors/test_http_security.py` (new).

**Interfaces:** A fact contains only an optional opaque per-attempt key used for attribution, method, route state (`matched(template)`, `not_found`, or `unobservable`), status, and presence bits for configured response-header names only. The key is a counter or random UUID, never a node ID or a digest of one, and is not part of finding identity. Facts are serialized through `PhaseFacts`/`TestFacts` in `engine/testsession/facts.py` and the existing sink path so xdist worker-to-controller transfer preserves them. Workers collect facts only; a controller-only hook evaluates expectations once after merging all worker facts, before report serialization. Expectations are available to that hook through `GateOptions`. Evaluation is per finished exchange: any violation produces one deduplicated `HTTP-SEC-001` HIGH per configured method/route/header or `HTTP-SEC-002` HIGH per configured method/route status policy. A 500 without a status expectation is evidence only, not a finding. Findings set `test_node_id=None` and set `Finding.identity` explicitly, because the fingerprint hashes `rule_id`, `identity or target` and `test_node_id` (`engine/advisors/findings.py:34`): the `HTTP-SEC-001` identity is `METHOD template` plus the lower-cased header name; the `HTTP-SEC-002` identity is `METHOD template` only, the configured status set and observed statuses appear in the message and never in the identity. Missing expected exchanges, unassociated evidence, missing workers, unknown routes, or any cap/truncation/unsupported metadata that could affect an expectation produce UNKNOWN; UNKNOWN is not downgraded to PARTIAL. PARTIAL describes informational coverage unrelated to configured expectations only. A definite FAILED result outranks UNKNOWN while retaining the unknown reason; the evaluator marks the run not fully usable so `AdvisorRun.derive` keeps the reason on a FAILED run (`engine/advisors/findings.py:96-97`), and the merge keeps an UNKNOWN worker reason beside a FAILED one (`engine/testsession/outcome.py:154-155`). Outcome per configured expectation: (1) observed with no violating exchange, PASSED, on a complete run or on a selection run that observed the expected route; (2) any violating exchange, FAILED, on a complete or a selection run; (3) no matching complete exchange on a complete run, UNKNOWN with reason `no matching exchange`; (4) no matching complete exchange on a selection run (`-k`, `-m`, single file, node IDs, `--lf`, `--deselect`, as classified by `engine/testsession/partial.py`), UNKNOWN with reason `selection run`, which fails unless the existing allow-unknown option is set; (5) evidence dropped by a cap or by unsupported metadata, UNKNOWN with reason `evidence incomplete`; (6) a missing worker, UNKNOWN. PARTIAL is never produced for a configured expectation because a clean PARTIAL run passes (`engine/advisors/findings.py:81-101`, `engine/testsession/outcome.py:359-369`). The evaluator receives the controller's selection classification (`partial_run`) beside the expectations. An unmapped response is `not_found`; unavailable route metadata is `unobservable`, never conflated. Neither state matches a route expectation. Raw paths, header values, unconfigured header names, query strings, bodies, exception text, and node IDs never enter HTTP facts.

## Open questions

1. **Selection runs.** An unobserved expectation in a `-k`, single-file or `--lf` run is UNKNOWN and fails unless allow-unknown is set. The alternative is SKIPPED with a reason, which does not fail but could be mistaken for coverage. The plan keeps UNKNOWN (fail closed); the choice is revisited if the failure rate of partial local runs proves too high.
2. **Header expectations on error responses.** Evaluation is per exchange, so a route with a header expectation fails on a legitimate 304 or an error response that omits the header. A status-scoped header expectation would avoid this and is out of scope for this lane.
3. **Flask second match.** The route comes from a second `url_map` match; if the lowest supported Flask or Werkzeug version cannot do this without side effects, Task 4 ships the explicit UNKNOWN behavior instead of parity.
