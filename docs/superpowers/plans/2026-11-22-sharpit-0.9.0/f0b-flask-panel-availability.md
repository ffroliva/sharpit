# F0b: Flask Panel & Action Availability Matrix

This document classifies every panel in `PANELS` (`src/sharpit/engine/panels.py:39-80`) and every console feature or action on a Flask (`WSGI`) host in 0.9.0 as **`works`**, **`adapted`**, or **`unavailable`**, with its code-verified reason and `file:line` citations.

---

## 1. ASGI-Only Subsystems Verified in Code

Before the per-panel table, seven subsystems are verified in the current codebase as coupled to ASGI middleware, Starlette exception tables, or `asyncio` event-loop tasks:

1. **HTTP exchange capture (`HttpExchangeBuffer`):**
   `CaptureMiddleware` in `src/sharpit/fastapi/capture.py:409-630` intercepts ASGI `http` scopes, wraps `receive` and `send` (`capture.py:488-615`), measures header/body timings, and appends `HttpExchange` rows to `ctx.capture.exchanges` (`src/sharpit/engine/capture/exchanges.py:85-269`). On Flask in 0.9.0, F4 wraps `app.wsgi_app` only to open a request correlation scope for SQL and unhandled exceptions (`PLAN.md` Decision 7, lines 88–90); `ctx.capture.exchanges` stays empty unless populated via synthetic fixtures.
2. **Framework exception-handler wrapping (`wrap_exception_handlers`):**
   `wrap_exception_handlers` in `src/sharpit/fastapi/capture_exceptions.py:66-143` walks Starlette `Mount` trees and wraps `app.router.exception_handlers` and `ExceptionMiddleware` tables (`capture_exceptions.py:92-138`) to record handled exceptions (`handled=True`). Flask dispatches exception handlers through `Flask.handle_user_exception` and `app.error_handler_spec`; in 0.9.0 F4 captures unhandled exceptions escaping `wsgi_app` (and logged tracebacks via `LogTailHandler._capture_exception` in `src/sharpit/engine/capture/logtail.py:216-247`), while `sys.monitoring` caught-exception events (`GET /sharpit/api/exceptions/caught`, `src/sharpit/engine/sensors/floor.py:216-254`) work identically on Flask and FastAPI.
3. **Request ID response header (`X-Sharpit-Request-Id`):**
   Emitted only by `CaptureMiddleware.send_wrapper` (`src/sharpit/fastapi/capture.py:506-509, 606-611`) when `should_append_request_id_header` (`src/sharpit/fastapi/request_id_header.py:18-51`) finds a recorded `HttpExchange` ID and `http_exchanges_expose_request_id_header` is `True`. Because Flask does not record `HttpExchangeBuffer` entries in 0.9.0, `X-Sharpit-Request-Id` is not appended to Flask host responses.
4. **Idle tracker (`IdleTracker`):**
   `IdleTracker` (`src/sharpit/engine/capture/activity.py:72-120`) is driven by `CaptureMiddleware` calling `activity.request_started()` and `activity.request_finished()` on ASGI HTTP scopes (`src/sharpit/fastapi/capture.py:475,627`) and by `SqlCapture.after_cursor_execute` calling `activity.on_sql()` (`src/sharpit/engine/sqla/listeners.py:211`). On Flask, SQL activity still feeds `activity.on_sql()` and F4's WSGI correlation wrapper can bracket active WSGI requests, while CPU/RSS/GC resource sampling (`ActivityMonitor.resources()`, `src/sharpit/engine/capture/activity.py:239-301`) works without ASGI.
5. **Distributed traces (`TraceBuffer` & `install_otel_bridge`):**
   `TraceBuffer` (`src/sharpit/engine/capture/traces.py:172-457`) builds traces either from `CaptureMiddleware.record_trace` (`src/sharpit/fastapi/capture.py:279-396`, which synthesizes HTTP server spans from ASGI requests, correlated SQL queries, and `HttpClientCapture` outbound calls) or from the OpenTelemetry `SpanProcessor` bridge (`install_otel_bridge` in `src/sharpit/engine/otel.py:45-114`). On Flask, OpenTelemetry spans exported through `install_otel_bridge` populate `TraceBuffer` normally, whereas synthetic ASGI request spans from `CaptureMiddleware.record_trace` are ASGI-only.
6. **Threads panel `asyncioTasks` (`collect_threads`):**
   `collect_threads` in `src/sharpit/engine/collectors/threads.py:143-199` inspects live OS threads via `threading.enumerate()` and `sys._current_frames()` (`threads.py:148-159`), and then calls `asyncio.get_running_loop()` and `asyncio.all_tasks(loop)` inside a `try / except RuntimeError` block (`threads.py:168-172`). On Flask, handlers run on a synchronous WSGI worker thread with no running asyncio loop, so `collect_threads` catches `RuntimeError` and returns `asyncioTasks: []` alongside the full OS thread dump and deadlock analysis.
7. **In-process HTTP probe and Pentesting probe (`run_probe` / `run_pentest_scan`):**
   `run_probe` (`src/sharpit/engine/probe.py:224-301`) and `run_pentest_scan` (`src/sharpit/fastapi/pentesting_probe.py:29-139`) currently construct an ASGI HTTP `scope` dict (`probe.py:252-270`) and `await app(scope, receive, send)` (`probe.py:277`). Under F0, `HostProbe` abstracts in-process probing: until F5 wires `WsgiHostProbe` over `app.wsgi_app`, `HostProbe` is ASGI-only (and once F5 lands, both `http-probe` and `pentesting` work on Flask through `WsgiHostProbe`).
