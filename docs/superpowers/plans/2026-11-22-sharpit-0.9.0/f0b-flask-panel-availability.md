# F0b: Flask Panel & Action Availability Matrix

This document classifies every one of the 49 panels registered in `PANELS` (`src/sharpit/engine/panels.py:27-83`) and every console action or gateway on a Flask (`WSGI`) host in 0.9.0 as **`works`**, **`adapted`**, or **`unavailable`**, with its code-verified availability reason and `file:line` citations.

---

## 1. ASGI-Only Subsystems Verified in Code

Seven subsystems in the current codebase are coupled to ASGI middleware, Starlette exception-handler tables, or a running `asyncio` request event loop (`PLAN.md:221-224`):

1. **HTTP exchange capture (`HttpExchangeBuffer`):**
   `CaptureMiddleware` in `src/sharpit/fastapi/capture.py:500-701` intercepts ASGI `http` scopes, wraps `receive` and `send` (`capture.py:589-620`), and appends `exchange_row(...)` records to `ctx.capture.exchanges` (`src/sharpit/engine/capture/exchanges.py:80-134, 181-269`) and `http_event(...)` records to `ctx.capture.journal` (`exchanges.py:137-165`, `capture.py:694-696`). On Flask in 0.9.0, F4 wraps `app.wsgi_app` for request correlation of SQL statements and unhandled exceptions (`PLAN.md:248-251`); HTTP exchange capture is not installed on Flask in 0.9.0, so `http_exchanges_report` (`src/sharpit/engine/tools.py:321-334`) returns `unavailable_report(NOT_INSTALLED)` (`src/sharpit/engine/capture/exchanges.py:168-178`).
2. **Framework exception-handler wrapping (`WrappingHandlers`):**
   `CaptureWiring._wrap_handlers` in `src/sharpit/fastapi/capture.py:291-303` replaces Starlette's `app.exception_handlers` dict with `WrappingHandlers` (`src/sharpit/fastapi/capture_exceptions.py:155-217`), recording handled exceptions with `source="handler"`. On Flask, unhandled exceptions escaping `app.wsgi_app` are captured in F4 (`PLAN.md:248-251`), and logged exceptions with `exc_info` are captured on FastAPI only before F4: `on_exc_info` is wired in `src/sharpit/fastapi/capture.py:260`; the shared log handler calls that optional callback (`src/sharpit/engine/capture/logtail.py:217-218`).
3. **Request ID response header (`x-sharpit-request-id`):**
   Appended only by `CaptureMiddleware.capture_send` (`src/sharpit/fastapi/capture.py:505-509, 606-611`) via `with_request_id_header` (`src/sharpit/fastapi/request_id_header.py:15-51`) when `ctx.capture.exchanges is not None` and `is_trusted_source` is `True`. Because Flask does not populate `HttpExchangeBuffer` in 0.9.0, `x-sharpit-request-id` is not emitted on Flask host responses.
4. **Idle tracker (`IdleTracker`):**
   `IdleTracker` (`src/sharpit/fastapi/install.py:52-86`) is started and stopped inside the ASGI `_lifespan` context manager (`install.py:220-261, 340-356`) and woken by `_activity_middleware` (`install.py:372-388`). WSGI has no ASGI lifespan protocol, so the background `sharpit-free-on-idle` timer thread (`install.py:248-249`) is ASGI-only; manual low-footprint toggling via `GET` / `POST /sharpit/api/live-memory/footprint` (`LowFootprintService` in `src/sharpit/engine/lowfootprint.py:11-50` and `src/sharpit/fastapi/routes/lowfootprint.py:59-81`) works on both frameworks.
5. **Distributed traces (`SpanBuffer` & `SharpitSpanProcessor`):**
   `SpanBuffer` (`src/sharpit/engine/capture/traces.py:251-447`) and `SharpitSpanProcessor` (`src/sharpit/engine/otel.py:71-128`) record OpenTelemetry SDK spans on any Python host where `opentelemetry-sdk` is installed and configured (`otel.unavailable_reason` at `src/sharpit/engine/otel.py:63-68`). When `opentelemetry-sdk` is not installed or no tracer provider is active, the `traces` panel reports `unavailable_reason` on both frameworks; request-path normalization against ASGI `RequestInfo.scope` (`_request_root_path` in `src/sharpit/engine/capture/traces.py:233-234`) is ASGI-only.
6. **Threads panel `tasks` (`threads_report`):**
   `threads_report` (`src/sharpit/engine/collectors/threads.py:216-254`) collects OS thread stacks via `threading.enumerate()` and `sys._current_frames()` (`_thread_rows`, `threads.py:191-213`), and then calls `_tasks` (`threads.py:161-182`), which checks `loop = ctx.capture.loop` (`threads.py:164-166`). On a synchronous WSGI Flask host, `ctx.capture.loop` is `None`, so `_tasks` returns `tasks: []`, `taskCount: 0`, and warning `NO_LOOP` (`"No running event loop is known yet: tasks show after the app's startup or its first request"`, `threads.py:46, 166`) alongside the full OS thread dump.
7. **In-process HTTP probe (`run_probe`) and Pentesting active probe (`pentesting_probe.run_probe`):**
   `run_probe` (`src/sharpit/engine/probe.py:221-370`, called by `_http_probe` in `src/sharpit/fastapi/routes/__init__.py:304-360`) and `pentesting_probe.run_probe` (`src/sharpit/fastapi/pentesting_probe.py:46-57`, called by `pentesting.py:31-45` and `src/sharpit/engine/tools04/pentesting.py:21-37`) construct an ASGI `http` scope and `await host_app(scope, receive, send)`. On a WSGI Flask host in 0.9.0 (`PLAN.md:223-224`, `h3-multi-loop.md:5`), there is no ASGI `host_app` or running host event loop (`running_host_loop` in `src/sharpit/engine/tools04/hostloop.py:14-16` returns `None`), so active probing is unavailable on Flask in 0.9.0.
