# F0 Console Contract — Predict & Scenario Analysis

## 1. Predict (`/sharpit:predict`)

### Architect

Today `src/sharpit/fastapi/adapter.py` (`SharpitMount` lines 84–138, `GuardMiddleware` lines 140–217) and `src/sharpit/fastapi/routes/` (38 modules plus `routes/__init__.py`) mix Starlette routing, guard enforcement, static asset serving, and SSE framing with framework-free collector logic that already lives in `src/sharpit/engine/`. Moving the console contract (`ConsoleRequest`, `ConsoleResponse`, `ConsoleStream`, `RouteSpec`, `ConsoleCall`, and `Console.handle`) into `src/sharpit/engine/console/` honors Architecture Rules 1 and 2 in `AGENTS.md`: `engine/` remains free of `fastapi`, `starlette`, and `flask`, while both `sharpit/fastapi/` and `sharpit/flask/` become thin protocol translators over ASGI and WSGI. The five host-specific edges—in-process HTTP probing (`HostProbe`), host event-loop discovery (`HostLoopProvider` from H3 in `src/sharpit/engine/spi.py:10-14`), live capture installation (`CaptureHooks` in `src/sharpit/engine/capture/__init__.py:21-25`), framework introspection (`AppIntrospector` in `src/sharpit/engine/spi.py:99-105`), and dev-server reload detection—cleanly separate through protocols on `EngineContext`. Eliminating the 12 ASGI `scope` dictionary reads scattered across `engine/` (`overview.py:21-23`, `probe.py:241-259`, `tools.py:103,409`, `mcp.py:391-547`) removes a subtle leak of Starlette scope conventions into the core engine.

**Vote:** GO WITH CONDITIONS — all `scope` dict reads in `engine/collectors/overview.py`, `engine/probe.py`, `engine/tools.py`, and `engine/mcp.py` must be replaced by typed fields on `ConsoleCall` / `HostProbe` so no WSGI adapter ever synthesizes a fake ASGI `scope`.

### Security Engineer

The safety model (`AGENTS.md` Safety Rules 1–6) depends on executing the exact guard order on every request under the mount: security headers, trusted source, Host allow-list, cross-site check, token check, and panel access (`src/sharpit/engine/guard.py:239-310`). Centralizing that sequence inside `Console.handle` guarantees that the Flask WSGI middleware cannot drift from the FastAPI ASGI mount, including on the bare mount path (`/sharpit`), where `SharpitMount.__call__` (`src/sharpit/fastapi/adapter.py:100-125`) currently runs `evaluate_guard` before issuing the `307` redirect to `/sharpit/`. Two WSGI-specific attack vectors require explicit contract rules: first, PEP 3333 stores headers in `environ["HTTP_*"]` as comma-joined strings rather than raw duplicate pairs, so `Console.handle` must treat any comma in `Host`, `Origin`, or `Sec-Fetch-Site` as a duplicate security-critical header (`400 Bad Request`, `src/sharpit/engine/guard.py:218-226`); second, `REMOTE_ADDR` in WSGI is a string that can carry an IPv6 zone identifier (`fe80::1%lo0`) or bracketed literal, which `is_trusted_source` (`src/sharpit/engine/guard.py:114-126`) already handles as long as the adapter passes `(environ.get("REMOTE_ADDR"), None)` without trusting `X-Forwarded-For` or `Forwarded`. Capping request body reads inside `ConsoleRequest.read_body(max_bytes)` ensures that oversized POST payloads to `/sharpit/api/mcp` (`MAX_BODY_BYTES = 1_048_576` in `src/sharpit/fastapi/routes/mcp.py:20`) or `/sharpit/api/http-probe` fail closed before allocation on both ASGI and WSGI.

**Vote:** GO WITH CONDITIONS — the duplicate-header check in `Console.handle` must reject comma-joined values in `Host`, `Origin`, and `Sec-Fetch-Site` alongside multi-tuple duplicates, and bare `/sharpit` requests must pass activation and the guard before returning `307`.

### FastAPI Host Developer

FastAPI applications rely on `sharpit.install(app)` never starving the host's AnyIO worker threadpool (`anyio.to_thread.current_default_thread_limiter()`, default 40 tokens) and never blocking the main asyncio event loop during slow filesystem or subprocess scans. Today, `async def` route handlers in `src/sharpit/fastapi/routes/__init__.py` run directly on the event loop (taking zero AnyIO threadpool tokens and allowing `GET /sharpit/api/threads` to pass `threading.active_count() <= before + 1` in `tests/fastapi/test_threads_api.py:89`), whereas sync `def` handlers (`GET /sharpit/api/config`, `GET /sharpit/api/profile-diff`, `GET /sharpit/api/alembic/migrations`, `GET /sharpit/api/rest-api/error-contract`, and sync POST scans) are dispatched by Starlette via `run_in_threadpool` so a slow first `/config` scan cannot stall concurrent `/overview` reads (`tests/fastapi/test_concurrency.py:19-46`). When `Console.handle` becomes synchronous in the engine, running all console reads through Starlette's threadpool would consume host AnyIO tokens and break `test_threads_api.py`, while running disk-heavy reads on the event loop would break `test_concurrency.py`. Furthermore, on Flask, `flask run` defaults to a multi-threaded Werkzeug dev server without reload unless `--debug` or `--reload` is passed, so activation on Flask must require an explicit reload flag rather than activating on bare `flask run`.

**Vote:** GO WITH CONDITIONS — FastAPI in-memory console reads must run directly on the ASGI event loop without taking a host threadpool slot, disk/blocking handlers (`off_loop=True`) must use a sharpit-owned on-demand daemon executor rather than the host's AnyIO limiter, and Flask activation must require `--reload` or `--debug`.

### Parity Auditor

The BootUI 2.5.0 contract requires identical JSON DTO keys (camelCase, nulls included, no envelope, epoch ms), identical HTTP status codes, verbatim error bodies and reason strings (`src/sharpit/engine/guard.py:25-39`), identical `Set-Cookie` attributes on `/sharpit/` and `/sharpit/index.html`, and identical SSE wire framing (`retry: 1000\n\n` on stream window completion, `event: change` / `event: log` / `event: heartbeat`, and `503 {"error": "Too many concurrent sharpit streams"}` on slot exhaustion). On Flask, `/sharpit/api/panels` (`src/sharpit/engine/panels.py:124-133`) and `/sharpit/api/overview` (`src/sharpit/engine/collectors/overview.py:19-46`) currently hardcode `"platform": "fastapi"` and `"webApplicationType": "ASGI"`. Both must derive from `ctx.introspector.platform` (`"fastapi"` vs `"flask"`) and `ctx.introspector.web_application_type` (`"ASGI"` vs `"WSGI"`) so the UI and CLI accurately report a Flask host while keeping every DTO key intact. Panels whose data sources depend on ASGI middleware or `asyncio` tasks must remain present in `/sharpit/api/panels` with their BootUI contract structure and degrade gracefully on Flask as documented in F0b.

**Vote:** GO — provide `platform` and `web_application_type` on `AppIntrospector` (defaulting to `"fastapi"` and `"ASGI"`), and document every Flask panel and action disposition in F0b.

### Skeptic

The highest operational risk in hosting the full console on WSGI is SSE stream exhaustion of synchronous worker threads. In BootUI (`BootUiChangeStream.java` and `LogTailSseSession.java`) and on FastAPI (`src/sharpit/fastapi/sse.py:20-76`), an open SSE stream holds an async registration or coroutine while `MAX_STREAMS = 20` (`src/sharpit/engine/capture/streams.py:23`) caps memory. On WSGI, each active response iterator occupies one OS thread for up to `stream_max_seconds` (default `3.0` s in `src/sharpit/settings.py:104`). A developer running `gunicorn --reload` (which defaults to 1 synchronous worker thread) or `flask run --without-threads` who opens the UI with two SSE streams (`/activity/stream` and `/log-tail/stream`) could stall concurrent REST calls during the 3-second stream window, and a leaked stream on client disconnect would permanently leak a `StreamSlots` slot and a `_Ticker` subscriber (`src/sharpit/engine/capture/streams.py:55-68`). Using a private `asyncio` event loop per active WSGI stream call on the serving worker thread avoids spawning background threads, caps stream duration at `stream_max_seconds`, bounds WSGI stream slots against the worker thread count, and cleans up via the WSGI `close()` protocol.

**Vote:** GO WITH CONDITIONS — cap WSGI stream slots against detected worker threads (`WSGI_DEFAULT_MAX_STREAMS = 4`, or `max(1, min(4, W - 1))` when thread count `W` is known), run the async event source on a per-request private event loop on the WSGI worker thread without spawning threads, and guarantee idempotent slot and subscriber cleanup in `ConsoleStream.close()`.

### Verdict: GO WITH CONDITIONS

1. **Zero ASGI `scope` leaks in `engine/`:** Replace `scope` dict reads in `overview.py`, `probe.py`, `tools.py`, and `mcp.py` with typed fields on `ConsoleCall` and `HostProbe`.
2. **Duplicate-header parity across ASGI and WSGI:** Reject both multi-tuple duplicate occurrences and comma-joined occurrences in `Host`, `Origin`, and `Sec-Fetch-Site` before running `evaluate_guard`.
3. **Host threadpool isolation on FastAPI:** Run in-memory console reads directly on the ASGI event loop thread (0 threads spawned, 0 host AnyIO threadpool slots taken) and offload disk-reading/blocking handlers (`off_loop=True`) to a per-context daemon executor.
4. **Bounded WSGI streaming with deterministic cleanup:** Drive `EventSource` on WSGI via a private per-stream `asyncio` loop on the serving worker thread, cap WSGI stream slots against worker thread capacity, and release slots and `_Ticker` subscribers inside an idempotent `close()` hook called on both normal completion and `GeneratorExit` / WSGI `close()`.
5. **Flask reload-only auto-activation:** Auto-enable on Flask only when a reload or debug reloader signal (`flask run --reload`, `flask run --debug`, `gunicorn --reload`, `WERKZEUG_RUN_MAIN=true`) is present; bare `flask run` stays inactive (`404`).

## 2. Worst-Case Trace (`/sharpit:scenario`)

Trace of a real Flask host failure modes if the console were mounted without the F0 contract safeguards:

1. **Comma-joined `Host` header bypass on WSGI (`src/sharpit/engine/guard.py:218-226`, `src/sharpit/fastapi/adapter.py:103,149`):**
   Today `has_duplicate_security_headers(raw_headers)` in `src/sharpit/engine/guard.py:218-226` counts how many tuples in `raw_headers` share the name `b"host"`, `b"origin"`, or `b"sec-fetch-site"`, and `extract_headers` in `src/sharpit/engine/headers.py:7-16` keeps the first tuple for each lowercase name. Under PEP 3333 WSGI, the HTTP server folds two incoming `Host: localhost:5000` and `Host: evil.example` headers into a single `environ["HTTP_HOST"] = "localhost:5000, evil.example"`. `has_duplicate_security_headers` sees only one `b"host"` tuple and passes; if any downstream consumer splits on the first comma while another takes the last, host validation splits from dispatch.
2. **WSGI worker starvation and leaked `_Ticker` subscribers on SSE disconnect (`src/sharpit/engine/capture/streams.py:55-97`, `src/sharpit/fastapi/sse.py:30-75`):**
   When a browser connects to `GET /sharpit/api/exceptions/stream`, `ChangeStream.subscribe()` (`src/sharpit/engine/capture/streams.py:194-203`) calls `_Ticker.wait(after)` (`streams.py:78-97`), which captures `asyncio.get_running_loop()` in `_Waiter` (`streams.py:50`) and registers it in `self._subs` (`streams.py:85`). On WSGI there is no running event loop on the worker thread (`RuntimeError: no running event loop`). If a naive WSGI adapter spun up a background thread with a loop and the WSGI client disconnected mid-stream without triggering `GeneratorExit` cleanup on that loop, `self._subs.discard(waiter)` (`streams.py:96`) and `slots.release()` (`src/sharpit/fastapi/sse.py:42`) would never run, leaking one of `StreamSlots` (`streams.py:28-45`) per disconnect until every subsequent stream returns `503` (`sse.py:26-29`) and `_Ticker._signal()` (`streams.py:57-68`) wakes dead loops on every exception or SQL event.
3. **WSGI `FlaskClient` false single-thread detection (`werkzeug/test.py` vs `gunicorn`):**
   Werkzeug's test `EnvironBuilder` sets `environ["wsgi.multithread"] = False` even though in-process test calls do not contend for a single socket worker, whereas `gunicorn --reload` with default sync workers also sets `wsgi.multithread = False` with 1 worker process. Relying on `wsgi.multithread` alone would either break all Flask SSE contract tests under `app.test_client()` or allow 20 concurrent streams (`MAX_STREAMS = 20`, `streams.py:23`) to lock all threads of a `--threads 4` WSGI server.
4. **ASGI `scope` crashes in engine tools on Flask (`src/sharpit/engine/collectors/overview.py:21-23`, `src/sharpit/engine/tools.py:409`, `src/sharpit/engine/mcp.py:391`):**
   `GET /sharpit/api/overview`, `POST /sharpit/api/mcp` (`tools/call` for `get_overview` or `trigger_pentest_scan`), and `POST /sharpit/api/cli/tools/get_overview` pass `scope` into `overview_dto(ctx, scope)` (`overview.py:19`) and `pentesting._scan(ctx, scope)` (`src/sharpit/engine/tools04/pentesting.py:32`). On Flask, if `HostProbe` is absent and `POST /sharpit/api/pentesting/scan` or `POST /sharpit/api/http-probe` is invoked, `run_probe` (`src/sharpit/engine/probe.py:224-301`) attempts `await app(scope, receive, send)` on a WSGI Flask app object (`TypeError: 'Flask' object is not awaitable` or wrong signature), leaving the single-flight lock or probe caller with an unhandled exception instead of a clean contract response.

- `tests/flask/test_signals.py::test_flask_activation_matrix_for_flask_run_debug_reload_and_gunicorn_reload` — asserts `flask run` stays inactive (`404`), while `flask run --debug`, `flask run --reload`, `WERKZEUG_RUN_MAIN=true`, and `gunicorn --reload` auto-enable the console.
