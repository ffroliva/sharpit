# A11 CORS Preflight Checks Implementation Plan

> Run `/sharpit:status --feature a11-cors-preflight-checks` for the next unchecked step. Complete one task at a time and run `/sharpit:check` before each commit.

**Goal:** Replace the "pending" CORS entry of the pentesting scan with BootUI v2.5.0's CORS findings, evaluated on the OPTIONS and GET evidence that the scan already retains.

**Architecture:** The pentesting engine package gains a pure header-bounding function (BootUI's `boundedHeaders`), Java-compatible text helpers, per-header-name completeness on `SyntheticResponse`, a small assessment module for "required header" gaps, and one module for the CORS rules and the PT-A05-069 diagnostic. The report builder calls them. The FastAPI probe only groups raw headers and calls the bounding function. No request, route, tool or action is added: the scan keeps sending exactly one GET and one OPTIONS (fixed synthetic origin and request method, fixed path), and the existing gated scan action is the only way to reach the checks. The scan result passes through the context masker before it is cached.

**Predict verdict:** Go with conditions (confidence 7/10). The conditions are folded into the tasks below.

## Design decisions

BootUI is ported exactly unless Python or the safety model forces a difference; each forced difference is a deviation row below.

| Decision | Rationale | Consequence |
|---|---|---|
| OPTIONS incompleteness is a failed request or truncated headers; a truncated OPTIONS body is not incomplete evidence. | BootUI raises PT-A05-069, marks the scan partial and makes A02 indeterminate only on `failed()` or `headersTruncated()` (`PentestingChecks.java` 214 to 221, `PentestingScanner.java` 255 to 259, `PentestingCheckRegistry.java` 415 to 423); no CORS rule reads the OPTIONS body. | A10's behaviour changes: an OPTIONS body over the limit no longer raises PT-A05-069 or `PARTIAL`; the body-limit limitation line stays. No A10 test pins the old behaviour; the new test does. |
| `SyntheticResponse` keeps `headers_truncated` and gains `incomplete_header_names` and `header_inventory_incomplete`. The two derived fields are set in `__post_init__` through `object.__setattr__` (the dataclass is frozen). A bare `headers_truncated=True` with no names and no inventory flag means the inventory is incomplete; names or an incomplete inventory make `headers_truncated` true. | BootUI's legacy constructor sets the inventory flag from the truncated flag (`PentestingLocalHttpResponse.java` line 38) and derives the truncated flag from names and inventory (line 51). Treating the bare flag as "complete" would let a rule read an unknown header as absent. | `headers_complete(*names)` is false for any listed incomplete name, and for every name when the inventory is incomplete. A10 constructors stay valid. Both derivation directions are tested. |
| BootUI's `boundedHeaders` is ported as a pure engine function, `bound_headers`, split into `bound_headers` (outer loop over names) and a private `_bound_entry_values` (loop over one name's values) sharing a small budget record. Each function has McCabe complexity 9 or lower. | `_retain` is at McCabe 10 (`ruff --select C901` at max 9 flags it) and BootUI's method has an outer loop, an inner loop and seven branches, so one function would be over the ratchet. | `_retain` and its counters leave the probe. The blank-name test uses the Java `isBlank` helper. |
| Header text is compared with Java semantics: `java_trim` strips only characters up to U+0020 and `java_is_blank` is true only for Java whitespace (U+0009 to U+000D, U+001C to U+001F, U+0020). | Java `String.trim()` keeps U+00A0 and U+0085 and strips U+0001; Python `str.strip()` does the opposite on all three. Headers are decoded as Latin-1, so a host sending `*` followed by U+00A0 is a finding in sharpit and silent in BootUI if `str.strip()` is used. `isBlank` is not "every character up to U+0020" either (U+0001 is not Java whitespace). | Every `trim`, `isBlank` and `split(",")` token trim in the ported rules and in A10's TRACE check uses the helpers. |
| A rule that requires a header name is withheld, with BootUI's gap strings, when that name is incomplete; it is never downgraded to a weaker finding. | BootUI's `headers()` returns early on a missing required name (`PentestingChecks.java` 566, 606, 647, 1395, 2842 to 2852). `PentestingAssessment.java` 53 to 71: `headers()` records `<M> required response headers were incomplete.` and `<M> required response headers were unavailable.` (two gaps), a failed response records `<M> probe was unavailable.` first, and `retainedHeaders()` (PT-A05-073) records only the first of the two header strings. | A table test covers each rule, each required name and the exact gap strings. |
| PT-A05-069 follows BootUI's two evidence forms and its gaps (`OPTIONS probe was unavailable.`, `OPTIONS response headers were incomplete.`). | `PentestingChecks.java` 188 to 229. The probe keeps only fixed incomplete reasons (`pentesting_probe.py` 151, 153, 166), so BootUI's text with that reason as the error carries no host text. | A failed request says `Request failed before CORS preflight headers could be inspected: <reason>`; truncated headers say `Response headers exceeded bounded retention limits`. | A fixed limitation names PT-A05-073 as indeterminate when either of its halves is withheld. | BootUI's 069 list omits PT-A05-073 although its preflight half skips silently on a failed preflight. | Fail closed at no parity cost; the 069 finding text stays BootUI's. |
| CORS evidence is BootUI's text, including the untrimmed origin echoed by -008 and -023 and the host's spelling of a sensitive token echoed by -073, sanitised as BootUI's `evidence()` does (each CR, LF and TAB run to one space, Java trim, 240 characters with `...`). Only the fragments echoed from the host (an origin, a header token) pass through the context masker, one by one, before the 240-character cut. Fixed BootUI text is never masked. When `Masker.mask_text` returns `None` (`METADATA_ONLY`), the fragment becomes the fixed placeholder `[masked]`. | `PentestingChecks.java` 578 to 583, 621 to 625, 2903 to 2910; `PentestingCheckSupport.java` 51 to 63. ## Global Constraints

- Reads have no side effects; no GET route or read MCP/CLI tool opens a socket, writes a file, changes a logger level, or changes `os.environ`.
- Actions follow BootUI: the scan keeps its enablement, guard, enabled-panel, non-read-only and single-flight gates; A11 adds no action.
- Secrets are masked before output; response bodies and exception text are not returned. CORS evidence is BootUI's text with host-echoed fragments masked before the 240-character cut; fixed text is never masked.
- Python `>=3.12`; runtime dependencies exactly `starlette` and `packaging`; `engine/` imports no `fastapi` or `starlette`, and the FastAPI adapter imports the shared probe constants and the bounding function from the engine, never the reverse.
- Every ported test cites its BootUI source with `# ported: <Class>.<method>`.
- No module under `src/` exceeds 1000 lines; ratchets only go down (`checks.py` is 524 lines; the CORS rules go in their own module). Every function added or touched is at McCabe 9 or lower, except functions already pinned in `tests/complexity_baseline.json`, whose counts do not rise; `_retain` leaves the probe.
- A failure, timeout, truncation or unobserved header is indeterminate, never a clean result.
- Evidence describes a synthetic preflight against the in-process ASGI app; it never claims browser or deployed-edge behaviour.
- Every `test:` commit carries wrong-value stubs in `src` (returning the wrong state, never raising) so that each red is an assertion; a stub is replaced in the `feat:` commit that follows. A test that asserts absence also asserts a positive control in the same test (the sibling input that fires), so a stub that returns no findings fails it.
- A test that is green before its lane's code exists is a characterization test: it is listed with the mutant that makes it fail, run as a regression guard and left out of the `red_check.py` node ids.

## Risk register

| Severity | Risk | Mitigation |
|---|---|---|
| Critical | A host-controlled value reaches the report unmasked | BootUI's evidence echoes only whitespace around `*` or the probe origin and fixed sensitive names; host-echoed fragments pass through the masker (required, keyword-only) with a fixed placeholder under `METADATA_ONLY`; real-`Masker` tests in `MASKED`, `METADATA_ONLY` and `FULL`, a planted-secret test on every output surface, and a secret-bearing non-matching origin with a positive control. |
| Critical | A CORS check reads as clean when the preflight failed or a header was not retained | PT-A05-069 with a fixed reason, per-name completeness, the required-name table test, a bare truncated flag meaning an incomplete inventory, scan `PARTIAL`, A02 coverage `INDETERMINATE`. |
| Critical | A rule downgrades to a weaker finding when a name it depends on is incomplete (credentials reads as absent) | The rule is withheld with a gap; the table test asserts no finding for each rule and name, with the complete sibling as control. |
| High | Per-name completeness changes A10's behaviour | `headers_truncated` stays and is derived from names and inventory; the A10 probe and report tests stay green. The intended changes (OPTIONS body, A02 status, A10 OPTIONS input, TRACE joined values) are stated and tested. |
| High | Constants drift between the probe and the rules | One `PROBE_ORIGIN` and one `PROBE_REQUEST_METHOD` in the engine, imported by the probe; a test pins the request. |
| High | Comparison semantics drift from BootUI (case, trailing slash, `True` versus `true`, trimmed versus untrimmed, Unicode whitespace) | Exact comparisons ported with BootUI's cases, the asymmetry tests and the Java helper tests. |
| High | Standing limitations pushed out of the 20-entry cap by new gaps | Gaps are deduplicated and built in a helper; a worst-case test with the gaps asserted present. |
| Medium | Report wording overstates CORS verification | Keep BootUI's "actual resource sharing was not tested" wording and add the A02 limitation; a text test pins both. |
| Medium | A02 `INFO` status is new to a sharpit consumer | The status is BootUI's contract value; check the UI sources and the CLI and MCP summaries for a closed status set before Task 4 is committed. |
