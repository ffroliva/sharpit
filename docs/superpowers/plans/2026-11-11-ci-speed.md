# CI Speed Implementation Plan

> For agentic workers: run `/sharpit:status --feature ci-speed` for the next unchecked step. One task at a time;
> `/sharpit:check` before every commit. Every pytest run passes `-n` (default `-n auto`; state a lower value and why).
> Long commands (full suite, `ab`, `uv sync`) run in the background; read the log when notified.

**Goal:** CI feedback faster on every PR, with every gate still running: the four owner-approved changes of
`docs/superpowers/specs/2026-11-11-ci-speed.md`, then the CI wall measured before and after.

**Architecture:** (1) the conftest's SQLAlchemy-mark check moves from `pytest_pycollect_makemodule` into a `Module`
subclass's `collect()`; (2) `sharpit/__init__.py` resolves its public names through PEP 562 `__getattr__`, and the
FastAPI introspector looks FastAPI up at first use; (3) the 3.13 leg becomes the coverage run; (4) the Windows
masking-gates job runs as six parts through a second `tests/_shard.py` partition. T1 and T2 are independent of T3
and T4. Expected wall after all four: ~5:30-6:00 (spec §6), not 3:00.

**Predict verdict:** (2) GO 8/10 (spec §4.2, mitigations below). (1), (3), (4): owner-approved CI/test-harness
changes with no product surface; no separate predict.

## Global Constraints

- Reads have no side effects; actions follow BootUI (AGENTS.md): untouched by this plan, and nothing here may change
  it.
- Runtime deps exactly `starlette` and `packaging`; `fastapi` optional, imported only inside `try/except ImportError`
  or in `sharpit/fastapi/`.
- `engine/` never imports `fastapi`, `starlette` or `sharpit.fastapi` (architecture rules 1-2, enforced by
  `tests/engine/test_import_boundary.py`).
- A budget is never raised to pass; a budget test is never marked slow or deselected (rule 5).
- Ratchets only go down (rule 6). A speed change never skips, deselects out of the gate, `xfail`s or marks slow,
  loosens an assertion, raises a timeout, or edits the pytest-speed baseline or exceptions.
- A crash is not a red; one condition per assert; `red_check.py` before every `test:` commit.
- Commits: conventional prefix, explicit `git add` paths, no AI attribution. Never push or merge `main`.

## Risk register

| Severity | Risk | Mitigation |
|---|---|---|
| High | (3) overhead budgets no longer enforced on 3.13 (the tracer skips them) | Recorded in the spec §4.3 and the PR body for the owner; still enforced on 3.12, 3.14, Windows 3.14 |
| High | (1) the mark check stops biting | T1 adds an end-to-end planted violation first, green on the base, red with the check deleted |
| Medium | (2) an import-time side effect moves from `import sharpit` to first access | T2 step 1 greps the closure and pins the result; a module with one stays eager |
| Medium | (2) pyright strict loses `install`'s type | `TYPE_CHECKING` re-exports; `uv run pyright` in the gate |
| Medium | (4) +5 Windows jobs add ~400-500 runner-s of setup and queueing | T5 measures queue latency before and after |
| Medium | (3) the tracer makes the 3.13 leg the slowest Linux shard | 5 shards instead of 4; ceiling pinned; T5 reads the real durations |
| Low | (4) round-robin parts unbalanced | largest test ~3.5 s vs ~289 s parts; T5 reads per-part JUnit |
