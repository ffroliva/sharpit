# CI Speed Implementation Plan

> For agentic workers: run `/sharpit:status --feature ci-speed` for the next unchecked step. One task at a time;
> `/sharpit:check` before every commit. Every pytest run passes `-n` (default `-n auto`; state a lower value and why).
> Long commands (full suite, `ab`, `uv sync`) run in the background; read the log when notified. Nested pytest runs in
> new tests clear `SHARPIT_SHARD` from their environment.

**Goal:** faster CI on every PR with every gate still running: the nine owner-approved changes of
`docs/superpowers/specs/2026-11-11-ci-speed.md`, then both walls measured before and after.

**Architecture:** T1 moves the conftest's SQLAlchemy-mark check into a `Module.collect()`; T2 makes `import sharpit`
and the introspector's FastAPI lookups lazy; T3 makes the 3.13 leg the coverage run (budgets kept on 3.13); T4/T7 run
the masking gates as file rows on both OSes; T6 moves the combine into the `sonar` job and caches the scanner; T8 adds
PR concurrency, merges tiny jobs and orders the critical path first; T9 measures, then fixes, the Windows-only ~1.3 s
per test; T5 measures it all on CI. T1, T2 and T9 are independent of the CI-layout tasks (T3, T4, T6, T7, T8). Expected
after all nine: required wall ~4:00-4:30, last-job ~4:10-4:40 (spec §7), not 3:00.

**Predict verdict:** T2 GO 8/10 (spec §4.2). The others are owner-approved CI/test-harness changes with no product
surface. Council (Claude 4 personas, agy): APPROVE WITH CHANGES, folded in (spec §9).

## Global Constraints

- Reads have no side effects; actions follow BootUI: untouched, and nothing here may change it.
- Runtime deps exactly `starlette` and `packaging`; `fastapi` optional, imported only inside `try/except ImportError`
  or in `sharpit/fastapi/`.
- `engine/` never imports `fastapi`, `starlette` or `sharpit.fastapi` (rules 1-2, `tests/engine/test_import_boundary.py`).
- A budget is never raised to pass; a budget test is never marked slow or deselected (rule 5).
- Ratchets only go down (rule 6). A speed change never skips, deselects out of the gate, `xfail`s or marks slow,
  loosens an assertion, raises a timeout, or edits the pytest-speed baseline or exceptions.
- A crash is not a red; one condition per assert; `red_check.py` before every `test:` commit.
- Commits: conventional prefix, explicit `git add` paths, no AI attribution. Never push or merge `main`.

## Risk register

| Severity | Risk | Mitigation |
|---|---|---|
| High | T4/T7 partition leaking into nested runs | file rows in the matrix, no env var (council H1) |
| High | T1 mark check stops biting | end-to-end planted violation first, red with the check deleted |
| High | T3 budgets lost on 3.13 | 5/5 runs `timing_files()` without coverage (council H2), pinned |
| High | T6 quality gate or ratchet bypassed | both stay in the required `sonar` job; layout test pins order |
| Medium | T2 import-time side effect moves | T2 step 1 checks and pins; such a module stays eager |
| Medium | T2 pyright accepts any `sharpit.<name>` | `__getattr__` under `if not TYPE_CHECKING`; pyright probe test |
| Medium | T8 cancelling hides a result | only superseded `pull_request` runs; `main` never cancelled |
| Medium | T9 cause in the runner image | stop rule: report with the measurement, no fix claimed |
| Low | T4/T7 +4 jobs of setup | ~+70 runner-s, measured in T5 |
