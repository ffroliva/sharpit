## 2. What must not change (all nine)

- No test skipped, deselected out of the gate, `xfail`ed or marked slow; no assertion loosened or data shrunk; no
  timeout raised; no edit to `tests/test_durations.json`, `tests/pytest_speed_exceptions.json` or a ratchet baseline
  (`tests/complexity_baseline.json`, `sonar-baseline.txt`).
- Every gate still runs on every PR, under the same required check names. Aggregators stay `always()`, require success,
  and keep the docs-only `exit 0` before any result check.
- Coverage and Sonar inputs unchanged: same suite, Python 3.13, `--extra test`, `COVERAGE_CORE=sysmon`, combined the
  same way; `sonar-project.properties` unchanged (`sonar.qualitygate.wait=true`). There is no `fail_under` in
  `pyproject.toml`: the coverage threshold is the Sonar quality gate's, enforced by the `sonar` check.
- The Sonar quality gate and the ratchet (`scripts/ci/sonar_ratchet.py`, `sonar-baseline.txt`) are enforced before merge
  by the required `sonar` check.
- The masking gates run the same tests with the same assertions on Linux and Windows; on each OS every gate file runs
  in exactly one job.
- Overhead budgets stay enforced on every leg that enforces them today, 3.13 included (§4.3), and are never marked slow.

## 3. Verification rule (all nine)

Each change gets a red test that pins the cost as a count (parses, imported modules, CI layout lines, jobs), never wall
time, watched red for the assertion that names the defect (a crash is not a red). Nested pytest runs in new tests clear
`SHARPIT_SHARD` from their environment (as `tests/test_ci_layout.py:259` does). Then a paired A/B where it applies
(`uv run python -m scripts.pytest_speed ab --config pytest-speed.toml --base-dir <base> --change-dir . --rounds 4 --out ab -- <files> -n auto`)
and both walls before/after from the jobs API (`scripts/ci/ci_walls.py`, three runs each side; plan T5).

## 4. The changes

### 4.1 (1) Collection hook: check only the modules pytest collects

**Cause (measured).** `tests/conftest.py::pytest_pycollect_makemodule` reads and `ast.parse`s every module pytest
builds a `Module` node for: every sibling file in each directory on the way to the target (`Dir.collect`), even for a
single node id. Report: 114 modules for one node id, 0.55 s per nested `python -m pytest`, about 67 s of the 674 s local
cost of `test_gates_bite.py` (~122 nested runs). Local: parsing all 370 test modules costs 0.78 s.

**Design.** `pytest_pycollect_makemodule` returns `_SqlaCheckedModule.from_parent(parent, path=module_path)` (pytest
9.2's default is `Module.from_parent(parent, path=module_path)`, `_pytest/python.py:235`). Its `collect()` runs the
same check with the same `pytest.fail(f"{path.name} {NEEDS_SQLALCHEMY_MISSING.format(...)}", pytrace=False)`, then
`return super().collect()`: before import, only for collected modules.

**Must not change.** The error text; failing before import; `sqlalchemy_imports_without_marker` and its unit test;
`tests/fixtures/apps/unbounded_read/conftest.py`'s re-exports.

**Risks.** The error is reported on the module's node instead of the directory's (same text, exit code 2; pinned).
No end-to-end test of the hook exists today, only the function's unit test: a planted violation is added first. The
hook is `firstresult`; no other plugin in the repo implements it. `pytest_ignore_collect` in the same conftest parses
every `.py` when SQLAlchemy is absent (no-sqlalchemy job only): same cause class, follow-up.

**Verification.** Red `test_a_single_node_id_run_parses_only_its_own_module` (pytester, repo conftest via
`-p conftest`, 30 sibling modules, a counter around `conftest.sqlalchemy_imports_without_marker`; expected red
`30 != 1`). Planted `test_an_unmarked_sqlalchemy_module_still_fails_collection_with_the_same_text` (exit 2 and the exact
line; green on base and after; red with the check deleted). A/B on `test_gates_bite.py`: about −0.55 s per nested run.

**Predicted wall.** Required: ~0 (coverage path not affected). Last-job: Windows gates −74 test-s × 0.22 ≈ −16 s.

### 4.2 (2) Lazy `import sharpit`

**Cause (measured).** `src/sharpit/__init__.py` imports `sharpit.fastapi.adapter`, `sharpit.fastapi.sources` and
`securitylogs` eagerly; every pytest process loads `sharpit.pytest_plugin` (`pytest11`), which imports `sharpit`.

**Spike, correcting the report.** What a nested pytest process imports (`sharpit.pytest_plugin` plus the conftest's
`sharpit.settings`, `engine.sqla`, `capture.transactions`, `sources.sqlite`, `sqltext.identity`): eager 1.00 / 1.08 s,
749 modules; with an empty package standing in for a lazy one, 0.89 / 0.82 s, 631 modules. FastAPI and pydantic are
still imported: `pytest_plugin/__init__.py:34` → `pytest_plugin/apps.py:20` → `fastapi/introspector.py:76`
(`_FASTAPI_APPS, _API_ROUTES, _API_WEBSOCKET_ROUTES = _fastapi_classes()`) and `introspector.py:90`
(`_KNOWN_ROUTES = (*_API_ROUTES, *_API_WEBSOCKET_ROUTES, WebSocketRoute, Route)`, used at :495). `fastapi.applications`
+ `fastapi.routing` cost 0.26-0.30 s standalone. A lazy `__init__` alone saves ~0.2 s per process (not ~1 s); step 2b
(FastAPI lookups at first use) up to ~0.3 s more.

**Design.**
- `__version__ = "0.5.0"` stays a plain string literal (the only version site; read by the Sonar job's "Read project
  version" step and the release workflow's regex, by `sharpit.pytest_plugin` and the adapter). `__all__` unchanged.
- `if not TYPE_CHECKING:` defines module `__getattr__` (one explicit `from ... import ...` per public name, cached in
  `globals()`; unknown names raise `AttributeError(f"module 'sharpit' has no attribute {name!r}")`) and `__dir__`
  (`sorted(set(globals()) | set(__all__))`). Defining them only at runtime keeps pyright reporting
  `from sharpit import typo` as an error (a module `__getattr__` visible to pyright would make every name valid).
- `if TYPE_CHECKING:` imports the four public names with `X as X` re-exports, so pyright strict sees their real types.
- Explicit imports keep `tests/engine/test_import_boundary.py` able to see the edges (no `import_module(str)`).
- Step 2b: `_fastapi_classes()` becomes `functools.cache`d and is called at use sites; `_KNOWN_ROUTES` becomes a cached
  function too (`_known_routes()`), used at :495. FastAPI missing still gives empty tuples.
- New planted import-boundary rule: an `engine/` module may import only `__version__` from `sharpit` (so no engine
  module can trigger the lazy adapter import).
- Changelog: `import sharpit` no longer imports `sharpit.fastapi` (or FastAPI); `sharpit.install` imports it on first
  access.
- No new public name (`SharpitHandle` stays unexported).

**Predict: five personas** (`skills/predict/SKILL.md`, written in turn).
- *Architect* (8/10). No new dependency, `engine/` untouched, the `__init__` → adapter edge exists today and only moves
  into a function; explicit imports keep it visible to the boundary test; the new rule closes the one new hole
  (engine importing a lazy name).
- *Security* (8/10). Guard, activation, masking code unchanged; only import timing moves. Risk: an import-time side
  effect in the adapter's closure would move from `import sharpit` to first access: T2 step 1 checks and pins it; a
  module with one stays eager. No GET/MCP change.
- *Contract parity* (9/10). No endpoint, DTO or error body changes; an `ImportError` inside the lazy import propagates
  unchanged (PEP 562 does not wrap it).
- *Host-app compatibility* (7/10). `import sharpit; sharpit.install(app)`, `from sharpit import install`,
  `from sharpit import *`, `dir()`, `inspect.getmembers`, `importlib.reload` keep working on 3.12-3.14; concurrent
  first access is serialised by the import lock. `hasattr(sharpit, "install")` on a broken install raises instead of
  returning `False`; today the same break fails `import sharpit`. Host apps' own pytest runs get the saving.
- *Devil's Advocate* (6/10). The gain is ~0.2-0.5 s per process, smaller than the report claimed; the plugin needs
  `__version__` from the package, so the package must be cheap anyway. No new exports.

Security and Host-app both name import-time side effects → a pinned step. Mean 7.6, no STOP. **GO, 8/10.**

**Must not change.** `__all__`, `__version__` literal, the `pytest11` entry point, the boundary rules, pyright strict,
FastAPI-less behaviour.

**Verification.** Red `test_import_sharpit_does_not_import_fastapi_or_the_adapter` (fresh subprocess; `fastapi`,
`pydantic`, `sharpit.fastapi` not in `sys.modules`, one assert each). Red (2b)
`test_loading_the_pytest_plugin_does_not_import_fastapi`. Characterisation:
`test_the_public_names_resolve_lazily_and_dir_lists_them`; `test_without_fastapi_a_starlette_install_introspects_as_before`
(FastAPI blocked by a meta-path finder: `install(Starlette())` succeeds and its routes report equals the base's,
pinned as a literal captured on the base); `test_pyright_rejects_an_unknown_sharpit_name` (pyright on a probe file
`from sharpit import typo` reports `reportAttributeAccessIssue`); boundary rule
`test_the_engine_imports_only_the_version_from_the_package` with its planted violation. A/B on `test_gates_bite.py` and
`tests/engine/test_guard.py`.

**Predicted wall.** Required: ~0. Last-job: Windows gates −0.45 s × ~122 nested runs ≈ −55 test-s × 0.22 ≈ −12 s.

### 4.3 (3) Coverage on the 3.13 leg; the four coverage shards go; budgets stay enforced on 3.13

**Cause (measured).** `coverage-shard` (4 shards, 3.13, `--extra test`, sysmon) reruns the suite the 3.13 leg of
`test-shard` (5 shards, same install) already runs. Main runs: 443-447 runner-s (3.13 leg) + 452-469 (coverage shards).
Saving ≈ the 3.13 leg minus one extra shard's setup, about −415 runner-s (report estimate −585).

**Design.** The 3.13 rows leave `test-shard`; `coverage-shard` becomes the 3.13 leg: `include:` rows
`{ os: ubuntu-latest, python: "3.13", shard: 1/5 }` .. `5/5` (the `os` key is in every row so `_legs()` in
`tests/test_ci_layout.py` keys the leg `ubuntu-latest3.13` and platform resolution works), display name
`test shard (ubuntu-latest, 3.13, i/5)`, the coverage run line as today. **Budgets on 3.13:** the `5/5` row adds one
step after the coverage run, without `--cov` and without `COVERAGE_*`:
`uv run pytest -q -n auto $(uv run --no-sync python -c "import sys; sys.path.insert(0, 'tests'); from _shard import timing_files; print(' '.join(sorted(timing_files())))")`
(`SHARPIT_SHARD` unset; 11 files, 39.8 test-s on 3.13 in the PR run), with its own JUnit/overhead/speed uploads. Artifact
names stay `coverage-data-*`, `junit-coverage-shard-*`, `speed-coverage-shard-*` (plus `-budgets` for the new step), so
`coverage` combines unchanged and `scripts/ci/shard_weights.py` (reads only `junit-test-shard-*`) keeps ignoring
tracer-distorted timings. The `test` aggregator's `needs` becomes `[test-shard, coverage-shard, lint, changes]`, and
its run step checks `needs.coverage-shard.result` after the docs-only `exit 0`.

Rejected: a `coverage` flag on the 3.13 rows of `test-shard` (GitHub `needs` takes the whole matrix: `coverage` and
`sonar` would wait for, and fail on, the Windows shards).

**Must not change.** Sonar inputs; required names; `test_the_coverage_shards_use_the_sys_monitoring_tracer`; the intent
of `test_the_required_test_check_still_fails_when_lint_fails` (it asserts the exact string
`"needs: [test-shard, lint, changes]"`: updated deliberately to the new `needs`, still proving a lint failure fails
`test`).

**Risks.** The tracer slows the leg: coverage shards took 104-148 s of pytest for 4 shards; 5 shards ≈ 103 s each, 5/5
+~20 s for the budget step. `ci_walls.py` uses job names; required names unchanged.

**Verification.** Red layout tests: no `test-shard` 3.13 rows; `coverage-shard` = `ubuntu-latest3.13` `1/5`..`5/5`
with `--cov=sharpit`; `test` needs and checks `coverage-shard` after the docs-only exit; the 5/5 budget step runs
`timing_files()` with no `--cov` and no `COVERAGE_` env. (No ceiling test for this leg: it would compute the same
`shard_loads` as the plain legs and prove nothing.) CI: `coverage.xml` line rate equal to the base on the same code;
budgets reported on 3.13 in the overhead artifact.

**Predicted wall.** Required: coverage leg ~118-140 s per shard, end ~25 s earlier than today's coverage shards when
not queued → ~5:35. Last-job: unchanged (~6:40 after T1-T2).

### 4.4 (4) and (7) Masking gates: one job per gate file group, on both OSes

**Owner decision, recorded.** pytest-speed forbids "adds shards ... as the fix". The owner overrides it, 2026-11-11, for
the masking-gates jobs on both OSes: what is left after (1) and (2) is the code under test doing work the test needs
(CPU by design, real git, nested runs); only parallel runners cut its wall. Test-seconds stay the same.

**Cause (measured).** Last-job wall is set by `masking gates (windows-latest)` (pytest 385 s); next is
`masking gates (ubuntu-latest)` (pytest 282 s, end 332 s).

**Design (file rows, no environment variable).** Council finding H1: an env partition (`SHARPIT_GATES_SHARD`) would
leak into the gates' own nested `python -m pytest` runs (`test_gates_bite.py:860/887/943` pass `env={**os.environ}`,
`cwd=ROOT`): every nested run would exit 4 and every named-mutant test go red. So the split is by file, in the matrix:

| Row | Files | Windows test-s → pytest wall | Linux test-s → pytest wall |
|---|---|---|---|
| gates-bite | `tests/masking/test_gates_bite.py` | 745 (≈610 after T1-T2) → ~134 s | 294 (≈255) → ~79 s |
| scales | `tests/masking/test_masking_scales_linearly.py` | 556 → ~122 s | 438 → ~136 s |
| surfaces+lane | `tests/masking/test_statement_surfaces.py tests/scripts/test_lane_gate.py` | 431 → ~95 s | 166 → ~51 s |

`masking-gates` matrix: `include:` six rows `{ os, part, files }`; run line `pytest ${{ matrix.files }} -q -n auto ...`;
name `masking gates (${{ matrix.os }}, ${{ matrix.part }})`; artifact names gain `-${{ matrix.part }}`.
`masking-gates-check` unchanged (needs the whole matrix). `tests/_shard.py` is unchanged (`OWN_JOB` still keeps the four
files out of every shard). A finer split, if ever needed, passes the part as a pytest CLI option, never an env var.

**Ceiling.** A file cannot be split by this design, so the pinned ceiling per OS is the heaviest single gate file:
no row may carry more than it (Windows 745, Linux 438 test-s). Pinned with `GATE_SECONDS` in
`tests/test_ci_layout.py` (the report's numbers). Council M2: this adds 4 jobs (2 → 6), not 10 as a k=6 split would.

**Must not change.** The same four files and assertions on both OSes; each file in exactly one row per OS;
`test_the_heavy_masking_gates_have_one_job_and_no_shard_collects_them` green.

**Risks.** +4 jobs × setup (Windows ~23 s, Linux ~12 s) ≈ +70 runner-s. The Windows gates-bite row (~157 s with setup)
becomes the longest gate job; below T8's ~3:00 window only if T1-T2 land.

**Verification.** Red layout tests: per OS the union of `files` equals `OWN_JOB`, each exactly once; no row over its
OS's ceiling; artifact names unique per row; `parse_artifact` of the new names returns `("masking-gates", ...)`. CI:
every row green; the union of the rows' JUnit node ids equals the 1,568 of a whole run.

**Predicted wall.** Required: ~0 (not required). Last-job: T4 → ~5:35 (now set by `sonar` and the Linux gates at
~5:32); T7 → Linux gates ≤ ~150 s → last-job = required (~5:20 after T6).

### 4.5 (6) Sonar off the critical path, still enforced before merge

**Cause (measured).** The required wall ends with `coverage` (236→247: setup, `uv sync`, download, combine, upload)
then `sonar` (250→359: setup, checkout, download, then the scan step 100 s, then the ratchet). The scan waits for the
SonarCloud quality gate (`sonar.qualitygate.wait=true`), so part of the 100 s is server-side and no cache can cut it;
the split between scanner start-up, analysis and the wait is not checked.

**Design.**
- The `sonar` job `needs: [coverage-shard, changes]` directly and does the combine itself (download `coverage-data-*`,
  `coverage combine`, `coverage xml`) before the scan and the ratchet: one job, no handoff. `coverage` stays a required
  aggregator with its own name (checks `changes`, then the docs-only exit, then `needs.coverage-shard.result`) and
  keeps uploading `coverage-xml` for people; Sonar no longer waits for it.
- Cache the scanner: `actions/cache` (pinned SHA) on `~/.sonar/cache`, key `sonar-${{ runner.os }}-<scan-action version>`;
  measured in T5 against the uncached scan.
- Where the gate lives: the required `sonar` check in `main`'s branch protection, unchanged. The quality gate (scan
  with `sonar.qualitygate.wait=true`) and `scripts/ci/sonar_ratchet.py` (PR: `--pull-request`, push: `--branch`, never
  above `sonar-baseline.txt` on `main`) run in that job, so a PR cannot merge until both pass.
- Rejected: a `workflow_run` workflow. It starts after the whole CI workflow ends (later, not earlier), runs with
  secrets on artifacts and a `sonar-project.properties` from the PR head (a PR could point `sonar.host.url` elsewhere
  and receive the token), and its check is not attached to the PR head without extra commit-status plumbing.

**Must not change.** Scan inputs (`coverage.xml` from the same data, same properties, same action pin); the ratchet;
the fork/dependabot guards on both steps; the required names `coverage` and `sonar`.

**Risks.** A cache restored from a poisoned run: the cache holds only the scanner JRE/plugins, keyed by version, written
by this repo's own runs; zizmor must stay clean. The scan still sits after the coverage leg: the required wall's floor.

**Verification.** Red layout tests: `sonar` needs `coverage-shard` and not `coverage`; `sonar` runs `coverage combine`
before the scan step and the ratchet after it, in one job; the cache step precedes the scan; `coverage` still checks
`coverage-shard` after the docs-only exit. CI: Sonar gate and ratchet green on the same inputs; scan step duration with
a warm cache vs cold.

**Predicted wall.** Required: −(coverage job 11 s + gap 3 s + duplicate setup ~5 s) ≈ −15 s; cache: not checked
(0 to −30 s). → ~5:20. Last-job: same as required once T7 lands.

### 4.6 (8) Queueing: fit the first wave in 20 runners

**Cause (measured).** PR #135 run: 54 jobs, 4,275 runner-s, peak 20 concurrent (the limit). 4,275 / 20 = 214 s is a
packing floor for one run alone; Linux test shards started up to 168 s late and `coverage shard (2/4)` 78 s late. The
fleet often has several PR runs at once (seven in `gh run list` on 2026-11-11), all sharing the 20 runners, and
superseded runs keep running. Tiny jobs: `changes` 6 s, `lint` 23 s, `vitest` 29 s, `sharpit-gate` 16 s, `ui` 11 s,
`wheel` 12 s, `workflow-lint` 11 s, four `lowest` shards 11-14 s; aggregators 2-7 s each. `live` legs: ~770 runner-s,
not required.

**Design.**
- `concurrency: { group: "${{ github.workflow }}-${{ github.event.pull_request.number || github.ref }}", cancel-in-progress: "${{ github.event_name == 'pull_request' }}" }`:
  a new push to a PR cancels its superseded run; pushes to `main` never cancel.
- Merge the tiny non-required jobs: `workflow-lint` and `sharpit-gate` become steps of `lint` (−2 jobs). `ui`, `vitest`
  and `wheel` are required contexts: merging them would rename required checks, an owner settings decision; they stay.
  The four `lowest` shards (11-14 s each, setup-dominated) become `lowest-shard` 1/2..2/2 if their weighted loads stay
  under the Linux ceiling (pinned by the existing ceiling test extended to that job), −2 jobs.
- Order: the job keys in `ci.yml` put the required critical path first (`coverage-shard`, `test-shard`, `lint`) and
  `live` last. GitHub's start order following the file order is **not checked**; T5 measures start latency per job.
  `live` gets no extra `needs` (that would delay the last-job wall).
- After (3), (4), (7) and this: about 50 jobs and ≈ 4,275 − 415 (T3) + 40 (T3 budget step) + 70 (T4/T7 setup)
  − 45 (T1-T2) − 70 (T9) − 60 (merges) ≈ 3,750 runner-s → packing floor ≈ 188 s for one run alone.

**Must not change.** Every job's steps (moved, not removed); required names; `push` to `main` runs to completion.

**Risks.** Cancelling a PR run hides its result: only the superseded run, never `main`. A merged `lint` job grows to
~50 s: still well before the `test` aggregators need it.

**Verification.** Red layout tests: the `concurrency` block with `cancel-in-progress` true only for `pull_request`;
no `workflow-lint`/`sharpit-gate` job, their steps inside `lint`; a pinned job count (`len(JOBS)` and the matrix-expanded
count, lowered never raised); `coverage-shard` and `test-shard` before `live` in file order. CI: queue latency p50/max
per job, before/after.

**Predicted wall.** Required: coverage leg starts at ~12 s → ends ~150 s → `sonar` ~110 s → **~4:20**. Last-job:
≥ required; live and the gate rows pack into ~190-230 s → **~4:20-4:30**.

### 4.7 (9) The Windows-only ~1.3 s per test

**Cause (measured so far; not named yet).** From run `43047297693`'s artifacts: the five files average, per test,
Windows 3.14 vs Linux 3.14: `test_exceptions_api` 1.70 / 0.29 s (34 tests), `test_http_route_templates` 1.42 / 0.12
(13), `test_http_exchanges_api` 1.35 / 0.14 (8), `test_data_api` 1.62 / 0.73 (8), `test_log_tail_api` 0.80 / 0.14
(33). Linux 3.12-3.14 are all fast, so it is not Python 3.14. The fixture timer gives ≈ 0.0-0.1 s of fixture setup per
file, so the cost is in the call or the teardown. Tests in those files that build no app take 0.002 s; app-building tests
have a ~1.1-1.4 s floor. Same signature in 15 files (164 tests, +210 test-s, e.g. `test_fastapi_security_api`,
`test_plugin_baseline`, `test_plugin_xdist`, `test_dismissed_findings_api`), plus `test_safety_matrix` +150 test-s
(+0.12 s × 1,270 tests). Windows leg 1,637 test-s vs Linux 3.14 1,023.

Candidates, unchecked: per-test app build + `TestClient` start/stop on Windows (event loop, portal thread), teardown not
covered by the fixture timer (`no_side_effects` verification walking the tree), Defender scanning files each test writes
(state dir, SQLite), a DNS/socket lookup timing out, a 1 s wait or join.

**Design.** Measurement first (plan T9): split call vs teardown with JUnit `junit_duration_report=call` against the
total; `python -m cProfile` one slow test (`test_custom_404_handler_unwrapped`) with `-p no:xdist` on `windows-latest`
in a temporary diagnostic step on the branch; read the top cumulative entries. Then the fix in the module the profile
names, with a red count test (a call count of the named cost per test: client start-ups, tree walks, waits, lookups),
or, if the cause is the runner (Defender), stop and report it with its measurement.

**Must not change.** The tests and their assertions; `no_side_effects` checks (made cheaper is fine, narrowed is not).

**Risks.** The cause may be in the runner image, not fixable in the repo: the stop rule applies.

**Predicted wall.** Up to −210 test-s (−360 if `test_safety_matrix` shares the cause) on Windows ≈ −15-40 s per Windows
shard. Windows shards (~190-215 s end) are not the required wall's long pole after T8, so: required ~0, last-job ~0
directly; it keeps the Windows `test` legs inside the window and frees ~70+ runner-s.
