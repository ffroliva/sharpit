## 2. What must not change (all four)

- No test skipped, deselected out of the gate, `xfail`ed or marked slow; no assertion loosened or data shrunk; no
  timeout raised; no edit to `tests/test_durations.json`, `tests/pytest_speed_exceptions.json` or any ratchet baseline
  (`tests/complexity_baseline.json`, `sonar-baseline.txt`).
- Every gate still runs on every PR, under the same required check names (`test (<os>, <py>)`, `coverage`, `sonar`,
  `masking-gates-check`, ...). Aggregators stay `always()` and require success.
- The coverage threshold, `coverage.xml` and the Sonar inputs are unchanged: the same suite, the same Python (3.13),
  the same install (`--extra test`), the same `COVERAGE_CORE=sysmon`, combined the same way.
- The masking gates run the same tests with the same assertions on Linux and on Windows; on Windows the union of the
  parts is the whole set, each test exactly once.
- Overhead budget tests keep their budgets and are never marked slow (AGENTS.md architecture rule 5). §4.3 states the
  one place where (3) changes where they are enforced.

## 3. Verification rule (all four)

Each change gets a red test that pins the cost as a count (parses, imported modules, CI layout lines), never wall
time, watched red on the unfixed code for the assertion that names the defect (a crash is not a red). Then a paired
A/B where it applies (`uv run python -m scripts.pytest_speed ab --config pytest-speed.toml --base-dir <base> --change-dir . --rounds 4 --out ab -- <files> -n auto`),
and the CI wall before/after from the jobs API (`scripts/ci/ci_walls.py`, three runs each side, plan T5).

## 4. The four changes

### 4.1 (1) Collection hook: check only the modules pytest collects

**Cause (measured).** `tests/conftest.py::pytest_pycollect_makemodule` reads and `ast.parse`s every module pytest
builds a `Module` node for. pytest builds one for every sibling file in each directory on the way to the target
(`Dir.collect`), even for a single node id; only the matching ones are then collected. Report: 114 modules parsed for
one node id, 0.55 s per nested `python -m pytest`, about 67 s of the 674 s local cost of `test_gates_bite.py`
(~122 nested runs). Local check here: parsing all 370 test modules costs 0.78 s.

**Design.** `pytest_pycollect_makemodule` returns `_SqlaCheckedModule.from_parent(parent, path=module_path)` (pytest
9.2's default is `Module.from_parent(parent, path=module_path)`, `_pytest/python.py:235`). The subclass's `collect()`
runs the same check, with the same `pytest.fail(f"{path.name} {NEEDS_SQLALCHEMY_MISSING.format(...)}", pytrace=False)`
text, then returns `super().collect()`. The check runs before the module is imported (`Module.collect` imports via
`self.obj`), only for modules actually collected.

**Must not change.** The error text; the module still fails before import; `sqlalchemy_imports_without_marker` and
its unit test `tests/fastapi/test_sqla_absent.py::test_collection_hook_requires_marker`; the fixture conftest
`tests/fixtures/apps/unbounded_read/conftest.py` that re-exports the names.

**Risks.**
- The failure is reported on the module's node id instead of during the parent directory's collection. Same text,
  same exit code 2 ("Interrupted: 1 error during collection"); the end-to-end test below pins both.
- No end-to-end test of the hook exists today: only the function's unit test. A planted violation must be added first
  and seen green on the base (characterisation), then red with the check deleted (red-capable), before the refactor.
- `pytest_pycollect_makemodule` is `firstresult`: returning a node makes ours the result. No other plugin in the repo
  implements it (grep: only `tests/conftest.py`).
- `pytest_ignore_collect` in the same conftest also parses every `.py` file, only when SQLAlchemy is absent (the
  no-sqlalchemy job). Same cause class, not in scope; noted for a follow-up.

**Verification.**
- Red: `test_a_single_node_id_run_parses_only_its_own_module`: a pytester run with the repo conftest as a plugin
  (`-p conftest`, `PYTHONPATH=tests`, as `tests/test_ci_layout.py` loads `_shard`), a directory of 30 test modules, a
  counting plugin that wraps `conftest.sqlalchemy_imports_without_marker`, `--collect-only <one module>::test_a`.
  Asserts the count is 1. Expected red: `30 != 1`.
- Planted violation: `test_an_unmarked_sqlalchemy_module_still_fails_collection_with_the_same_text`: same harness, a
  module with `import sqlalchemy` and no mark; asserts exit code 2 and the exact line
  `test_planted.py imports sqlalchemy at module level without pytestmark = pytest.mark.needs_sqlalchemy`. Green on the
  base and after; red when the check is deleted (delete-the-control, recorded in the PR).
- A/B: `tests/masking/test_gates_bite.py` base vs change. Expected about −0.55 s per nested run.

### 4.2 (2) Lazy `import sharpit`

**Cause (measured).** `src/sharpit/__init__.py` imports `sharpit.fastapi.adapter` (the guard, tools, collectors,
settings), `sharpit.fastapi.sources` and `securitylogs` eagerly. Every pytest process loads `sharpit.pytest_plugin`
through the `pytest11` entry point, which imports `sharpit`. Report: `import sharpit` about 1.06 s, 193 modules.

**Spike (this spec), and a correction to the report.** Importing what a nested pytest process imports
(`sharpit.pytest_plugin`, plus the conftest's `sharpit.settings`, `engine.sqla`, `capture.transactions`,
`sources.sqlite`, `sqltext.identity`), four runs: eager 1.00 / 1.08 s and 749 modules; with an empty `sharpit`
package standing in for a lazy one, 0.89 / 0.82 s and 631 modules. **FastAPI and pydantic are still imported** in the
lazy case: `sharpit/pytest_plugin/__init__.py:34` → `pytest_plugin/apps.py:20` →
`sharpit/fastapi/introspector.py:76`, whose module-level `_FASTAPI_APPS, ... = _fastapi_classes()` imports
`fastapi.applications`. Standalone, `fastapi.applications` + `fastapi.routing` (with pydantic) cost 0.26-0.30 s.
So a lazy `__init__` alone saves about 0.2 s per pytest process, not the report's ~1 s; deferring the introspector's
FastAPI lookup to first use is worth up to about 0.3 s more. The design does both, the second as a separate step that
stops if FastAPI still arrives through another path.

**Design.**
- `__init__.py` keeps `__version__ = "0.5.0"` as a plain attribute (the only version site; `sharpit.pytest_plugin` and
  the adapter read it) and the exact current `__all__`. `install`, `attach_sql_sources`, `detach_sql_sources` and
  `record_security_event` resolve in a PEP 562 module `__getattr__`, one explicit `from ... import ...` per name (so
  AST-based tools, including `tests/engine/test_import_boundary.py`, still see the edges; no `import_module(str)`),
  cached into `globals()`. Unknown names raise `AttributeError(f"module 'sharpit' has no attribute {name!r}")`.
- `__dir__` returns `sorted(set(globals()) | set(__all__))`.
- An `if TYPE_CHECKING:` block imports the four names with `as` re-exports, so pyright strict and IDEs see the real
  signatures of `from sharpit import install`.
- Step 2b: `introspector._fastapi_classes()` becomes a `functools.cache`d function called at first use instead of at
  import; the module-level names `_FASTAPI_APPS`, `_API_ROUTES`, `_API_WEBSOCKET_ROUTES` become calls. Behaviour is
  the same: FastAPI missing still gives empty tuples that match no class.
- No new public name. `SharpitHandle` is not exported today and is not added (Devil's Advocate, below).

**Predict: five personas** (`skills/predict/SKILL.md`; written in turn, each from the code read above).

- *Architect* (8/10). No new dependency; `engine/` untouched; the `__init__` → `sharpit.fastapi.adapter` edge exists
  today, it only moves inside a function. Explicit imports keep `test_import_boundary.py` able to see the edge
  (an `import_module` string would hide it: rejected). `install()` cost unchanged; the first `sharpit.install` access
  pays the import once, as `import sharpit` does today. Rule 2 (engine never imports `sharpit.fastapi`) unaffected.
- *Security* (8/10). Activation, guard chain and masking code are unchanged; only the moment their modules are imported
  moves. Risk: an import-time side effect in the adapter's closure (a logger configured, a handler attached, an
  OpenTelemetry hook) would now happen at first access rather than at `import sharpit`. Mitigation: T2 step greps the
  closure for module-level side effects and pins the result; any found keeps that module eager. No GET-route or MCP
  change, so `no_side_effects` coverage is unaffected.
- *Contract parity* (9/10). No endpoint, DTO or error body changes. Error texts raised by `install()` when FastAPI or an
  extra is missing are produced by the same code, so stay verbatim; an `ImportError` raised inside the lazy import
  propagates unchanged (PEP 562 does not wrap it). Pinned by a test that compares the message with and without the
  lazy path.
- *Host-app compatibility* (7/10). `import sharpit; sharpit.install(app)`, `from sharpit import install`,
  `from sharpit import *` (resolves `__all__` through `__getattr__`: same modules as today), `dir(sharpit)`,
  `inspect.getmembers`, `importlib.reload(sharpit)` all keep working on Python 3.12-3.14. Behaviour change:
  `hasattr(sharpit, "install")` with a broken install raises the `ImportError` instead of returning `False`; today the
  same break fails `import sharpit` itself, so this is not a regression. Concurrent first access is serialised by the
  import lock. Host apps' own pytest runs get the saving, since they load the `pytest11` plugin too.
- *Devil's Advocate* (6/10). The saving is smaller than the report claimed (§ spike): ~0.2 s from `__init__`, up to
  ~0.3 s more only with step 2b. The smaller change with the same outcome for CI would be step 2b plus making
  `sharpit.pytest_plugin` avoid `import sharpit`; but the plugin needs `__version__` from the package, so the package
  must be cheap anyway: (2) is the needed change. No new exports (`SharpitHandle`): YAGNI.

Reconcile: Security and Host-app both name import-time side effects; it becomes a T2 step with a pinned check. Mean
7.6, no STOP, Devil's Advocate found no simpler path that the others missed. **Verdict: GO, 8/10**, with the
mitigations: explicit imports, `TYPE_CHECKING` re-exports, side-effect check, error-text test, step 2b gated on the
red test.

**Must not change.** The public surface (`__all__`, `__version__`), the `pytest11` entry point
(`sharpit = "sharpit.pytest_plugin"`), the import-boundary rules, every error message, pyright strict clean.

**Verification.**
- Red: `test_import_sharpit_does_not_import_fastapi_or_the_adapter`: a fresh `python -c "import sharpit, sys; ..."`
  subprocess; asserts `fastapi`, `pydantic`, `sharpit.fastapi` are not in `sys.modules` (one assert each). Expected
  red: `'fastapi' in sys.modules`.
- Red (step 2b): `test_loading_the_pytest_plugin_does_not_import_fastapi`: same, `import sharpit.pytest_plugin`.
  Expected red: `'fastapi' in sys.modules`, from `introspector.py:76`.
- Surface: `test_the_public_names_resolve_lazily_and_dir_lists_them` (`from sharpit import install` is the adapter's
  function, `dir()` contains `__all__`, an unknown name raises `AttributeError` with the standard text).
- A/B: `tests/masking/test_gates_bite.py` and one ordinary file (`tests/engine/test_guard.py`), base vs change.

### 4.3 (3) Coverage on the 3.13 leg; the four coverage shards go

**Cause (measured).** The `coverage-shard` job (4 shards, Python 3.13, `--extra test`, `COVERAGE_CORE=sysmon`) runs
the same suite as the 3.13 leg of `test-shard` (5 shards, Python 3.13, `--extra test`) a second time, with coverage.
Main runs: 443-447 runner-s for the 3.13 leg plus 452-469 runner-s for the coverage shards. The report estimates
−585 runner-s and the queueing wave from about 221 s to about 195 s; from the jobs API the saving is about the 3.13
leg's cost minus one extra shard's setup, about −415 runner-s.

**Design.** The 3.13 rows leave `test-shard`; `coverage-shard` becomes the 3.13 leg: 5 shards (`1/5`..`5/5`), the same
run line as today's coverage shards (`--cov=sharpit --cov-report=`, `COVERAGE_FILE` in `runner.temp`,
`COVERAGE_CORE: sysmon`), display name `test shard (ubuntu-latest, 3.13, i/5)`. Its artifacts keep their
`coverage-data-<index>`, `junit-coverage-shard-<index>` and `speed-coverage-shard-<index>` names, so `coverage`
combines them unchanged (`coverage combine coverage-*.data && coverage xml`) and `scripts/ci/shard_weights.py`, which
reads only `junit-test-shard-*`, keeps ignoring timings distorted by the tracer. The required `test` aggregator adds
`coverage-shard` to its `needs` and requires its success, so `test (ubuntu-latest, 3.13)` still fails when a 3.13
test fails (all four `test` legs require it: stricter, as they already require every shard and lint).

Rejected alternative: keep the 3.13 rows in `test-shard` with a matrix `coverage` flag. GitHub `needs` takes the whole
matrix, so `coverage` and `sonar` would wait for the Windows shards too and fail on a Windows flake; and every coverage
step would need an `if:` on the flag.

**Must not change.** Coverage threshold and Sonar inputs (same Python, install, tracer, test set: `OWN_JOB` files are
excluded from both today); required check names; `test_the_coverage_shards_use_the_sys_monitoring_tracer`.

**Risks.**
- **Overhead budgets stop being enforced on 3.13.** `tests/overhead.py::paired` skips every budget test while a tracer
  runs (line 86); today the plain 3.13 leg enforces them. After (3) they are enforced on 3.12, 3.14 (Linux) and 3.14
  (Windows), not on 3.13. A regression that shows only on 3.13 would pass. This follows from the owner's choice of
  the 3.13 leg; it is recorded here for the owner to see, and no budget is changed or marked.
- The tracer slows the leg. Coverage shards today take 64-195 s; 5 shards instead of 4 spread the same work, so each
  should be about 20 % shorter. Pinned: the leg's predicted loads stay under the Linux ceiling (170 weighted test-s,
  computed from plain-run weights); the CI run in T5 checks the real duration.
- `scripts/ci/ci_walls.py` and `tests/scripts/test_ci_walls.py` use job names; the required set
  (`test (ubuntu-latest, 3.13)`, `coverage`) is unchanged, the display name of the 3.13 shards is kept.

**Verification.** Red tests in `tests/test_ci_layout.py` (exact names in the plan): no `test-shard` row on 3.13; the
`coverage-shard` leg lists `1/5`..`5/5` once each on 3.13 with `--cov=sharpit`; `test` needs and checks
`coverage-shard`; the coverage leg's loads stay under the Linux ceiling. Then the CI run: `coverage.xml` line rate
equal to the base's (same commit's code), Sonar quality gate on the same inputs.

### 4.4 (4) Split the Windows masking-gates job

**Owner decision, recorded.** pytest-speed's never-weaken rule forbids "adds shards ... as the fix". The owner
overrides it for this one job on 2026-11-11: the four files are each the code under test doing work the test needs
(report: CPU by design, real git, nested runs), (1) and (2) remove the removable part, and what remains is wall that
only parallel runners can cut. The test-seconds stay the same; this changes only the critical path.

**Cause (measured).** `masking gates (windows-latest)` is the critical path: 411 s in the PR #135 run (8:24 run in the
report), 1,732 Windows test-s in four files no shard may hold (`tests/_shard.py::OWN_JOB`).

**Design.** `tests/_shard.py` gets a second partition, `SHARPIT_GATES_SHARD=i/k`, using the mechanism the split files
already use: `pytest_ignore_collect` keeps only the `OWN_JOB` files; `pytest_collection_modifyitems` keeps, per file,
the items whose index in nodeid order satisfies `index % k + 1 == i`, and reports the rest through
`pytest_deselected` exactly as the split files do today. Every test lands in exactly one part. Setting both
`SHARPIT_SHARD` and `SHARPIT_GATES_SHARD` is a `pytest.UsageError`. The `masking-gates` matrix becomes
`include:` rows: `ubuntu-latest` whole (no variable, as today), `windows-latest` with `gates: 1/6`..`6/6`. The run line
stays the four file paths. Artifact names gain `-${{ strategy.job-index }}` (`junit-masking-gates-<os>-<index>`,
overhead and speed likewise) so the parts do not collide; `parse_artifact` already returns `("masking-gates", <rest>)`.
`masking-gates-check` is unchanged (it needs the whole matrix).

Sizing: with per-file round-robin each part carries about 1/k of every file. k = 6 gives 289 test-s per part on
today's numbers (1,732 / 6) and about 265 after (1) and (2), under the Windows test-shard ceiling of 305
(`LOAD_CEILING` in `tests/test_ci_layout.py`); k = 5 would give 346 today: over. The measured per-file Windows seconds
go in `tests/test_ci_layout.py` as `GATE_SECONDS` so the pin is computed, not asserted by hand.

**Must not change.** The same four files, tests and assertions on both OSes; the Linux leg runs them whole; no
`OWN_JOB` file is collected by a normal shard (`test_the_heavy_masking_gates_have_one_job_and_no_shard_collects_them`
stays green).

**Risks.**
- Runner cost: five more Windows jobs, each paying Windows setup (Python install, `uv sync`; a Windows test shard takes
  115-215 s for about 295 test-s, so setup is a large share): about +400-500 runner-s, roughly cancelling (3)'s saving
  in the queue. T5 measures queueing before and after.
- Round-robin balances only while no single test dominates a part. The largest single tests are nested runs (~3.5 s)
  against 289 s parts: fine; T5 reads the parts' JUnit to confirm the spread.
- The Linux masking-gates leg (299 s in the PR run) is not split (the owner approved Windows only); after (4) it is on
  the critical path (§6).

**Verification.** Red tests: the partition (`tests/test_shard.py`: every `OWN_JOB` test in exactly one of k parts;
both variables set is a usage error), the layout (`tests/test_ci_layout.py`: the Windows rows list `1/6`..`6/6` once
each, the Linux row has no partition, artifact names carry the job index, the predicted part load is under the
Windows ceiling). Then CI: every part green, the union of the parts' JUnit equals the 1,568 node ids of the whole run.
