## 1. Intent

Two things a team needs before it adopts sharpit, and the panels that make its pitch true.

- **Adoptable:** a team can turn sharpit on in CI without breaking its build (report-only), with a GitHub Action and a
  job summary, with a baseline so old findings do not block new work, and with a project that passes a procurement
  check (README that tells the truth, SECURITY.md, Dependabot).
- **Parity, database and security first:** sharpit claims to be a deterministic reviewer that guard-rails agents. The
  database panels (Wave A) are where that claim is measured (the sharpit-bench benchmark measures the same area), and
  the security panels (Wave B) are what a platform team and a CISO look at. Runtime panels (Wave C) are the stretch.
- **The minimum bar is BootUI's feature set** (owner). 0.4.0 moves parity from 20 of about 53 portable panels to about
  34, and catches up the 20 existing panels with BootUI 2.2.0 (drift, §9).

## 4. Anti-goals (a lane that does any of these is rejected, however green)

- Weakens a safety-model rule (AGENTS.md §Safety model). In particular **a GET that opens a socket, runs SQL, reads a
  file outside the app, calls user code, writes a file or changes logging/os.environ.** Anything that talks to a
  database or a network does it on a POST action, and the GET returns the cached result (the alembic/health pattern).
- Fabricates data. A counter Python cannot measure is `null` with a reason, never an estimate dressed as a measurement.
- Raises a budget or a ratchet (overhead budgets, complexity baseline, sonar baseline, the 1000-line module limit).
- Adds a runtime dependency. Optional libraries are imported only in their named gatekeeper module (§6.3).
- Merges a half-done panel. A panel that misses its definition of done (§6.1) stays on its lane branch, listed in the
  morning report.
- Changes BootUI's keys or error strings for convenience. Deviations are logged in §11 with a reason.

## 5. Adoption

### 5.1 Report-only mode (G1)

`--sharpit-report-only` / ini `sharpit_report_only = true`. Every gate and advisor runs and the report is written
exactly as today, with an honest `status`. What changes:

- No test is failed by a sharpit gate: the gate's finding is recorded, the test outcome stays what pytest decided.
- `session.exitstatus` is never raised by sharpit. pytest's own non-zero codes are untouched.
- The report gets `"mode": "report-only"` (otherwise `"gate"`); JUnit findings are still written.
- The terminal summary ends with `sharpit report-only: N tests would fail, status <status>`.
- Combined with a baseline, report-only still classifies findings (new / existing / fixed).

### 5.2 Baselines (G2)

- `--sharpit-baseline=PATH` / ini `sharpit_baseline` reads a baseline. `--sharpit-write-baseline=PATH` writes one from
  this run's findings and **is the only way a baseline is written** (never implicitly, never by the console).
- File: JSON `{"schema": "sharpit-baseline/1", "createdAt": <epoch ms>, "sharpitVersion": "...", "findings":
  [{"fingerprint": "...", "ruleId": "...", "summary": "..."}]}`, sorted by fingerprint, masked, stable bytes so it diffs
  cleanly in a PR.
- With a baseline: a finding whose fingerprint is listed is `existing` and does not fail; an unlisted finding is `new`
  and gates as today; a listed fingerprint not seen this run is counted `fixed`. A baseline written by a different
  baseline `schema`, or unreadable, makes the run `unknown` with a reason (fails closed; §12.14).
- Report: `baseline: {path, sha256, existing, new, fixed}` and per finding `baselineState`. This is requirement R6 of
  `04-metrics-dashboard.md`; `report.schema.json` grows additively (`sharpit-report/1` stays).
- Count-gate findings and advisor findings both carry fingerprints already (0.3.0 §5.2); the baseline covers both.

### 5.3 GitHub Action and job summary (G3)

- `action.yml` at the repo root (a composite action, so `uses: ffroliva/sharpit@v0.4.0` works). Inputs: `pytest-args`,
  `report-only` (default `true`: a first run must not break a build), `baseline`, `fail-on`, `report-path`. It installs
  `sharpit==<the action's own version>` into the caller's Python (the caller runs `actions/setup-python` first), runs
  pytest with `--sharpit`, and writes the job summary.
- `python -m sharpit.report summary <report.json>` renders Markdown for `$GITHUB_STEP_SUMMARY`: status, mode, totals,
  baseline counts, the top 20 findings (rule, test, summary). Pure function over the JSON, tested with golden reports.
- Pinned SHAs inside the action, as in our own CI. A sample workflow goes in `docs/ci/github-actions.md`.

### 5.4 Procurement hygiene (G4)

README: correct install (`pip install sharpit`, it is on PyPI), lead with the gate and the gflow-cli proof, a
"60 seconds" section. `SECURITY.md` (supported versions, private reporting via GitHub advisories, the network-egress
statement: only the OSV and EPSS clients use the network). `.github/dependabot.yml` for `uv`/pip, GitHub Actions and
the `ui/` npm tree. Fix `skills/README.md` ("no SonarQube project" is stale).

## 6. Panels: the common contract

### 6.1 Definition of done, per panel (file-checkable)

1. Endpoints, DTO keys, nulls, enums and error strings match BootUI 2.2.0, proven by a test that loads the panel's
   golden fixture (captured from tiny-ledger-bootui, sanitised with `scripts/sanitize_golden.py`) and compares the
   **key structure and types** of sharpit's response to it (values differ by nature).
2. Each ported behaviour test cites its source: `# ported: <BootUI class>.<method>`.
3. The safety checks: the `no_side_effects` fixture on every GET; masking of anything secret-shaped (URLs with
   credentials, tokens, headers) before any output; the guard chain and panel access unchanged; the panel appears in
   `PANELS` with BootUI's `actionCapable`, and its `SHARPIT_PANELS_<ID>_ENABLED/_READ_ONLY` switches work.
4. Optional library imported only in its gatekeeper (§6.3), with the import-boundary test and AGENTS.md row changed in
   the same lane. A planted violation proves the rule bites.
5. Hot-path code (SQL/transaction/session listeners, HTTP client hooks, span processors) has an overhead budget test.
6. MCP tool(s) and CLI command(s) where BootUI has them, masked, read-only.
7. The Vue view ported into `ui/src` (BootUI's view is the reference). Lanes do **not** run `npm run build`; the static
   rebuild happens once per wave on the integration branch (§10.4).
8. The four gates green in the lane worktree (`ruff check`, `ruff format --check`, `pyright`, `pytest -n auto`), plus
   `--resolution lowest-direct` and the no-SQLAlchemy job run locally (`docs/development/ci.md`).
9. Live check: the panel answers on tiny-ledger-py when the increment it needs exists, otherwise on
   `examples/fastapi_sqla`, recorded in the lane report with the exact requests.

### 6.2 Panel ids

BootUI ids are kept when the concept is the same (`data`, `transactions`, `database-advisor`, `postgresql`, `mysql`,
`traces`, `security`, `security-logs`, `pentesting`, `architecture`). Where the JVM concept has a Python stand-in, the id
names the Python thing and the DTO keeps BootUI's shape, as alembic did for flyway: `hibernate-statistics` →
`sqlalchemy-statistics`; `spring-security` → `fastapi-security`; the `spring` advisor → `fastapi` advisor.
Coordinator's call (§12).

### 6.3 Gatekeepers (named now so lanes do not collide)

| Library | Gatekeeper | Used by |
|---|---|---|
| SQLAlchemy | `engine/sqla.py` (exists; extended) | Data, Transactions, statistics, advisor, PostgreSQL, MySQL |
| OpenTelemetry SDK | `engine/otel.py` (new) | Traces; Wave C Metrics if OTel metrics |
| `tomllib` (stdlib), `ast` (stdlib) | no gatekeeper needed | Architecture (reads `[tool.importlinter]` contracts if present; stdlib import graph, **no grimp dependency**) |
| `httpx` (Wave C) | `engine/httpclient.py` (new) | REST Client Trace, AI |
| `prometheus_client` (Wave C) | `engine/collectors/metrics/prometheus_source.py` (new) | Metrics |

PostgreSQL and MySQL run their catalog SQL **through the app's own SQLAlchemy engine** (`engine/sqla.py`); no driver is
imported by sharpit.

## 8. Wave B: security (G6)

Every Wave B lane changes something the safety model guards, so each starts with `/sharpit:predict` and its plan goes
through `/sharpit:llm-council --tier high` before code (AGENTS.md).

| Panel | Python source | Calls | Size |
|---|---|---|---|
| `security` (advisor) | FastAPI `Depends` tree (security schemes: `OAuth2*`, `HTTPBearer`, `APIKey*`), `CORSMiddleware`/`TrustedHostMiddleware`/`HTTPSRedirectMiddleware` config, routes without any security dependency | reads app objects only; CORS `*` with credentials is a finding; rule ids and text from BootUI where a FastAPI analogue exists | L |
| `fastapi-security` (BootUI `spring-security`) | the same `Depends` tree as an endpoint → security-requirement map, with BootUI's `/explain` and `/endpoints` routes | **static on GET** (BootUI evaluates matchers on GET; sharpit only reads route objects, which is no side effect) | M |
| `security-logs` | records from loggers named in BootUI's list mapped to Python (`uvicorn.error`, `fastapi`, auth libraries' loggers) via the existing log-tail handler, with BootUI's SSE stream | no new handler; a filter over the log-tail buffer and its stream | M |
| `pentesting` | BootUI's route-based checks run **in-process over ASGI** like http-probe (never a loopback socket), POST only, bounded concurrency, never against routes under the sharpit mount, never a mutating method unless the check is a pure OPTIONS/HEAD | the riskiest lane: predict + council mandatory | L |
| `architecture` | stdlib `ast` import graph of the app package (`engine/importgraph.py`, stdlib only) + import-linter contracts from `pyproject.toml` if present | no new dependency; POST scan reads source files of the app package only | L |
| `fastapi` advisor | Spring advisor rules with a FastAPI analogue + new rules: sync `def` endpoints doing I/O on the threadpool, blocking calls in `async def`, Pydantic v1 leftovers, missing `response_model` on public routes | rule ids `FASTAPI-*`; new rules marked N in the contract | L |

Wave B is larger than first estimated (four L panels). If the night runs short, the order is `fastapi-security`,
`security-logs`, `security`, `fastapi` advisor, `architecture`, `pentesting`; unfinished panels stay parked.

## 12. Coordinator's calls (for the owner to check while reading)

1. Report-only is a separate switch, not a severity value; it keeps the status honest.
2. Baselines are written only by `--sharpit-write-baseline`; a version-mismatched baseline fails closed (`unknown`).
3. The Action defaults to `report-only: true`.
4. Panel ids per §6.2 (`sqlalchemy-statistics`, `fastapi-security`, `fastapi` advisor).
5. No grimp, no new runtime dependency; PostgreSQL/MySQL through the app's engine.
6. Database Advisor: missing evidence is `SKIPPED` with a reason, never `PASSED` (§12.13).
7. Pentesting: in-process, POST-triggered, GET/HEAD/OPTIONS only, bounded; council mandatory (§12.15).
8. tiny-ledger-py answers to its design's open questions: increment 1 is accounts, deposits, withdrawals and balance
   (asset transfers, tax lots and the audit chain later); rate limiting deferred; a `standalone` profile with no auth
   exists for quick runs; Kafka/audit routes answer 501 until increment 5; OTel exports to the reference compose's
   optional collector profile; ports: the Java app 8080, tiny-ledger-py 8081, shared backing services.
9. Golden comparison is structural (keys, types, nulls), not by value.
10. UI static build once per wave on the integration branch, not per lane.
11. **Goldens fallback.** If L0a cannot capture a panel by the time its lane needs it, the lane builds a structural
    fixture from BootUI's DTO record sources, marked `"provisional": true` in the fixture's sidecar, and L0a replaces it
    when the capture lands. A provisional fixture does not block the merge; the morning report lists them. L0a is not a
    single point of failure.
12. **Extra keys are allowed, missing keys are not.** The golden comparison asserts that every BootUI key is present
    with a compatible type and nullability; sharpit may add keys (as 0.2.0 added `tasks`/`taskCount` to threads), each
    logged in §11. This is how `data` adds tables and relationships and `sqlalchemy-statistics` adds N+1 per route.
13. **Advisor status vocabulary stays sharpit's** (`PASSED` / `FAILED` / `SKIPPED` per rule; `PASSED` / `FAILED` /
    `UNKNOWN` per run, 0.3.0 §5.3); `sharpit-report/1` and fingerprints do not change. The BootUI mapping
    (`PASS`→`PASSED`, `VIOLATION`→`FAILED`, `SKIPPED`/`ERROR`→`SKIPPED` with a limitation) is one table in
    `engine/advisors/`, logged in §11. A Database Advisor rule without evidence is `SKIPPED` with the reason, as in
    BootUI; the run is `UNKNOWN` only when no rule could run. (This replaces "UNKNOWN per rule" in §7.)
14. **Baseline compatibility is by baseline schema, not sharpit version.** `sharpit-baseline/1` stays readable by every
    0.x release; only a different `schema` fails closed. A fingerprint-stability test pins the fingerprints of a fixed
    finding set, so any lane that changes a fingerprint fails it (and must bump the baseline schema with a migration).
15. **Pentesting may send GET, HEAD and OPTIONS** (safe methods, as BootUI's "at most one GET and one OPTIONS"), in
    process over ASGI, to the app's own routes only, never under the sharpit mount, never a request body, never an
    unsafe method. The council reviews exactly this.
16. **Wave C has no contract extract yet** (it is still being written); its lanes are "extract, then build" and run
    only if Waves A, B and the drift lanes are merged or parked.
