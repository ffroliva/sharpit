## 4. Anti-goals (a lane that does any of these is rejected, however green)

- Weakens a safety-model rule (AGENTS.md). In particular **a GET or an MCP tool that opens a socket, runs SQL, reads a
  file outside the app, calls user code, configures ORM mappers, writes a file or changes logging/os.environ.** Database
  and network work happens on a POST action; the GET returns the cached result (the alembic/health pattern).
- Fabricates data. A counter Python cannot measure is `null` with a reason.
- Raises a budget or a ratchet (overhead budgets, complexity baseline, sonar baseline, the 1000-line module limit).
- Adds a runtime dependency. Optional libraries are imported only in their gatekeeper (§6.3).
- Merges a panel that misses its definition of done (§6.1). It stays on its lane branch, listed in the morning report.
- Changes BootUI's keys or error strings for convenience. Deviations are logged in §11 with the reason.

## 5. Adoption

### 5.1 Report-only mode (G1)

`--sharpit-report-only` / ini `sharpit_report_only = true`. Every gate and advisor runs and the report is written as
today, with an honest `status`.

- Findings do not fail a test (no `report.outcome = "failed"` from a sharpit gate, no JUnit `<failure>` for them) and
  do not raise `session.exitstatus`.
- **Any unknown reason still exits 1**, exactly as in 0.3.0, unless `--sharpit-allow-unknown` — **including when the
  status is `fail`** (status precedence puts `fail` before `unknown`, so `exit_fails` checks the unknown reasons
  themselves under report-only, not only the status). Report-only relaxes findings, never blindness: a broken
  baseline, a blind capture or a crashed worker still fails the build.
- An advisor rule BootUI reports as `ERROR` (mapped to sharpit's `SKIPPED`, §11) also adds an unknown reason (the run is
  `UNKNOWN`), so report-only cannot hide a rule that could not run.
- G1 and G2 are **one lane** (they change the same gate path).
- A bad `--sharpit-baseline` path or an unreadable baseline is a `pytest.UsageError` at session start.
- The report gets `"mode": "report-only" | "gate"` and lists the unknown reasons that caused exit 1. JUnit: finding
  testcases are written without `<failure>`; the session `sharpit.status` case gets `<failure>` only when unknown
  reasons exist (and names them). Terminal summary ends with `sharpit report-only: N tests would fail, status <status>`.
- `--sharpit-fail-on` still selects which advisor findings count as `fail`; report-only decides only whether a `fail`
  breaks the build.

### 5.2 Baselines (G2)

- `--sharpit-baseline=PATH` / ini `sharpit_baseline` reads one. `--sharpit-write-baseline=PATH` writes one from this
  run and **is the only way a baseline is written**. It **refuses** (`pytest.UsageError` at session end, file not
  written) when the run was partial **or any unknown reason exists** (checked directly, not via `status`, since `fail`
  precedes `unknown`): a baseline is only ever written from a complete, seeing run.
- **Partial-run detection** works under xdist, where the controller never collects (`xdist/dsession.py`): each worker
  records its partial-run facts (`pytest_deselected` count, selection options `-k`/`-m`/node-id args/`--lf`/`--deselect`/
  `--sw`) and ships them in `workeroutput`; the controller adds its own facts (`-x`/`--maxfail` stopping early,
  `session.shouldstop`, `KeyboardInterrupt`, tests collected vs run). Any fact makes the run partial. An xdist test proves it.
- **Where it acts:** a baseline is **not** a dismissal. `gates.evaluate_test` and the advisors' `assess` take a baseline
  mapping `{fingerprint: observed}`; a baselined finding keeps `dismissed: false` (its 0.3.0 meaning) and gets
  `baselineState`; a gate skips failing only when `not dismissed and baselineState == "existing"`. The baseline is
  loaded on every xdist worker. An explicit dismissal still wins.
- **Count regressions stay visible:** `Finding` gains `observed: int | None` (the count for count gates); a fingerprint
  in the baseline whose `observed` this run is higher than the baseline's is `new`, not `existing` (the `max-queries`
  fingerprint is the node id only, `gates.py:45`). A test shows a baselined test going from 12 to 500 queries fails.
- File (stable bytes, diff-friendly): `{"schema": "sharpit-baseline/1", "findings": [{"fingerprint", "ruleId",
  "target", "message", "observed"}]}` (`observed` = the count for count gates, else `null`), sorted by fingerprint, masked. No timestamp or version in the file (they would churn the diff);
  provenance comes from git.
- With a baseline: a listed fingerprint is `existing` (never fails), an unlisted one is `new` (gates as today), a listed
  one not seen this run is `fixed`, **unless the run was partial**: then `fixed` is `null` and `fixedReason` is
  `"partial run"` (`fixedReason` is `null` otherwise).
- **Scope:** count-gate findings and advisor findings that have fingerprints. **Vulnerability findings are excluded in
  0.4.0** (they have no fingerprint, `advisors/registry.py:42`); the report says so.
- Fingerprints are `advisor:rule:sha256(rule, identity or target, test node id)` (`advisors/findings.py:30`), so
  renaming a test makes its findings `new` (documented). A **fingerprint-stability test** runs real gate and advisor
  code twice over the example app with varying runtime values (ids, timings, parameter values) and asserts identical
  fingerprints; a lane that changes a fingerprint fails it and must bump the baseline schema with a migration.
- Compatibility is by baseline `schema`, not sharpit version: `sharpit-baseline/1` stays readable by every 0.x.
- Report (additive inside `sharpit-report/1`; readers of /1 must accept added keys, written in `report.schema.json`):
  `baseline` (`null` when none) = `{path, sha256, existing, new, fixed, fixedReason}`, and per finding `baselineState`
  and `observed` (`null` when none). All keys emitted, nulls included.
- Docs: a baseline file should be owned in CODEOWNERS, or a PR can baseline its own findings.

### 5.3 GitHub Action and job summary (G3)

- `action.yml` at the repo root (composite). Inputs: `pytest-args`, `report-only` (default `true`), `baseline`,
  `fail-on`, `report-path`, `install` (`pip` default, `none` when the project already depends on sharpit, e.g.
  `uv add --dev sharpit` + `uv run pytest`), `runner` (default `python -m pytest`).
- Every input reaches the shell through `env:`, never `${{ }}` inside `run:` (script injection), and every expansion is
  double-quoted; `pytest-args` is split with `shlex` in a Python step, never by the shell. A static test over
  `action.yml` enforces both rules.
- The sharpit version is a literal in `action.yml`, bumped by `/sharpit:release` (a SHA pin cannot derive it).
- `python -m sharpit.report summary <report.json>` renders Markdown for `$GITHUB_STEP_SUMMARY`: status, mode, totals,
  baseline counts, top 20 findings; every value escaped for Markdown. Pure function, golden-tested.
- Verified tonight by static tests over `action.yml` and golden tests of the summary step; one manual run against a
  locally built wheel is recorded in the lane report (not part of the gates: no network in tests). Tagging and
  publishing stay with the owner.

### 5.5 Findings from the sharpit-bench spike (owner, 2026-11-01)

Source: `C:\development\github\sharpit-bench-spike\docs\sharpit-0.4.0-findings.md` (sharpit 0.3.0 from PyPI against
Ryandaydev/odsc-west-2024-1 `ed7f0d7`; evidence under `results/` there). Each finding gets a regression test that
reproduces the spike's case in a fixture app (red on 0.3.0 for the right reason, quoted in the lane report).

- **F3 (high, committed, lane G6): green must be reachable on clean code.** Today `pytest --sharpit` with no
  `--sharpit-app` is `unknown` and exits 1 (`advisor 'rest-api' could not assess: no application`). 0.4.0:
  1. **Autodetect** at `pytest_sessionfinish`: scan `sys.modules` for module globals that are `fastapi.FastAPI` /
     Starlette instances (a read of objects already imported, no import, no call); exactly one → use it and print
     `sharpit: using app <module>:<attr> (pass --sharpit-app to choose)`; several → use none and print the candidates.
  2. **No app found** → the `rest-api` advisor is `SKIPPED` with the reason and a terminal warning naming
     `--sharpit-app module:attr`; it **does not** make the run `unknown`. SQL capture blindness still does (unchanged).
  3. `--sharpit-require-app` / ini `sharpit_require_app = true` restores 0.3.0's fail-closed behaviour for teams that
     want it. Logged in §11 as a change from 0.3.0.
- **F4 (low, committed, lane G6): quiet terminal output by default.** Non-failing advisor notes are not printed;
  the terminal shows gate failures, the status line and one count line (`sharpit: 8 advisor notes in <report path>`).
  `--sharpit-verbose` (or pytest `-v` twice, `-vv`) prints them as today. The JSON/JUnit reports are unchanged.
- **F5 (medium, best effort 1, lane T-n-plus-one-message): an actionable N+1 message.** The finding names the
  lazy-loaded relationship (`Player.performances lazy-loaded 1018 times`) from SQLAlchemy's ORM load events
  (`InstanceEvents.load` / attribute lazy-load hooks through `engine/sqla.py`, attached only while a test session
  runs), shows the masked statement, suggests `selectinload(Player.performances)` (or `joinedload` for many-to-one), and
  gives the **application source location** of the first lazy load (innermost application frame, the 0.2.0 frame
  logic). Message keys are additive; the fingerprint is unchanged (identity stays the statement shape).
- **F6 (low, inside lane T-n-plus-one-message): an overhead budget for query-heavy tests.** A budget test runs a
  fixture of about 35,000 SELECTs with and without `--sharpit` and pins the ratio at the measured value plus the
  usual margin (`docs/development/overhead-budgets.md`); F5's ORM hooks must stay inside it. Spike reference: plain
  23.5 s, queryguard 38.4 s, sharpit 39.3 s.
- **F1 (high, best effort 2, lane T-swallowed-exceptions): swallowed exceptions in application code.** During a test
  session only, `sys.monitoring` (Python ≥ 3.12, always available) `RAISE` + `EXCEPTION_HANDLED` events, restricted to
  application files (the 0.2.0 application-frame rule: not site-packages, not stdlib, not sharpit), record exceptions
  raised and handled in the same test. A handled exception becomes a finding `sharpit.swallowed-exception` when the
  handler (located by the `EXCEPTION_HANDLED` code location, then parsed with stdlib `ast`, cached per code object)
  catches `Exception`, `BaseException` or is bare, **and** its body neither re-raises nor calls a logger/`warnings`.
  It gates like the exceptions gate (fails the test; the marker `sharpit(allow_swallowed=True)` relaxes it; baselines
  and report-only apply). The same AST rule runs as a static check in the `rest-api`/`fastapi` advisor path over route
  handler modules (`FASTAPI-ERR-*`, rule text new, marked N). Overhead budget test for the monitoring hooks; the tool id
  is claimed with `sys.monitoring.use_tool_id` and freed at session end; another tool holding the id → the source
  reports `attached: false` (a limitation, not a crash).
- **F2 (medium, best effort 3, lane T-unbounded-read): unbounded reads on paged endpoints.** During a request to a
  route whose parameters include `skip`, `limit`, `offset`, `page` or `page_size`, a SELECT with no `LIMIT`/`FETCH`
  whose ORM load events materialise more instances than the response's page size by a factor ≥ 2 (default; setting
  `SHARPIT_ACTIVITY_UNBOUNDED_READ_FACTOR`) is a finding `sharpit.unbounded-read` (the spike: 52 `Team` loaded for a
  page of 5). Gate on by default with the marker relax `sharpit(allow_unbounded_read=True)`. The page size is taken
  from the request's bound `limit`/`page_size` argument; with none bound, the rule does not fire (no guessing).

### 6.1 Definition of done, per panel (file-checkable)

1. **Golden parity:** every BootUI 2.2.0 key present with a compatible type and nullability (extra sharpit keys
   allowed and logged in §11), checked against the panel's golden fixture captured from tiny-ledger-bootui. Where an
   honest Python answer is `null` for a key BootUI types as a primitive (e.g. Hibernate counters), the key is listed in
   the panel's `nullable.json` next to its golden, with the reason; the checker reads it, and §11 logs it. Each lane
   report carries a **field map**: every BootUI key → its Python source, or `null` + reason. A
   **provisional** fixture (§12.11) is built by a different worker than the lane, from BootUI's DTO record sources; a
   panel on a provisional fixture merges but is counted **unverified**, not parity, in `PARITY.md`.
2. Each ported behaviour test cites `# ported: <BootUI class>.<method>`.
3. Safety: `no_side_effects` on every GET; panel in `PANELS` with BootUI's `actionCapable` and working
   `SHARPIT_PANELS_<ID>_ENABLED/_READ_ONLY`; the guard chain unchanged; **masking with a test per new secret source**:
   catalog statement text (`pg_stat_statements`, `pg_stat_activity`), span attributes (`db.statement`, HTTP headers),
   middleware configuration (CORS/TrustedHost values), security event data, log records.
4. Gatekeeper only (§6.3); its import-boundary row exists from the foundation commit.
5. Hot-path code (SQL/connection listeners, span processors) has an overhead budget test.
6. **MCP exposes read tools only** (`get_*`); action tools are CLI-only, as in 0.3.0 (`engine/tools.py`).
7. **A Svelte 5 view** in `ui/src` (sharpit's UI is Svelte 5 + TypeScript; BootUI's Vue view is the behavioural
   reference), passing `npm --prefix ui run check` and its vitest tests. Lanes do not run `npm run build`.
8. The four gates green in the lane worktree, plus lowest-direct and the no-SQLAlchemy job (`docs/development/ci.md`).
9. Live check on `examples/fastapi_sqla` (always) and on tiny-ledger-py when the increment exists; requests recorded.
   **PostgreSQL/MySQL panels are tested against a real leased database** (`agentctl lease database`, the reference
   compose's Postgres; a MySQL container for `mysql`), selected by an env var the tests read; a run in which those
   tests only skipped may merge, but counts as **unverified**.
10. Its lane `handoff.md` is current (§10.3).

### 6.4 Database access rules (all database panels)

- POST only, through the **existing `run_db_read`** (`sqla.py:383-424`: `run_sync` for async engines, `internal()`
  correlation so sharpit's own SQL is never captured, timeouts, the executor). Nothing re-implements it.
- `bounded` (`sqla.py:352-380`) and the existing callers (alembic, health) are **unchanged**. `run_db_read` gains two
  keyword-only parameters with today's behaviour as default: separate `wall_timeout` (the `asyncio.timeout`) and
  `statement_timeout`, and `read_only=False`. With `read_only=True` it uses a new sibling of `bounded`,
  `bounded_read_only`, that owns the transaction and runs, in this order, **before any other statement**:
  - PostgreSQL: `SET TRANSACTION READ ONLY` (first statement of the transaction), `SET LOCAL statement_timeout`,
    `SET LOCAL lock_timeout`, then the panel's queries;
  - MySQL/MariaDB: `SET SESSION transaction_read_only = 1` and the timeout variable before the transaction starts,
    both restored in `finally`, the connection invalidated if the restore fails (the pattern `bounded` already uses).
- **AUTOCOMMIT fails closed:** after setup the wrapper checks `conn.in_transaction()` and, on PostgreSQL,
  `current_setting('transaction_read_only') = 'on'` (MySQL: `@@transaction_read_only = 1`); if either fails, no
  catalog SQL runs and the panel returns `unavailableReason`.
- Tests on the leased databases prove that **a write inside the wrapper is rejected** on both dialects, and that an
  AUTOCOMMIT engine yields `unavailableReason`.
- Every optional catalog query (`pg_stat_statements` absent, not preloaded, permission denied) runs **inside
  `begin_nested()`** (always, not as an alternative to a pre-check), so one failing query never aborts the
  transaction; it becomes that section's `unavailableReason`.

  - **re-runs the four gates itself** at the lane's head commit (it does not trust gate logs), and checks that the
    lowest-direct and no-SQLAlchemy logs name that head commit's SHA (those jobs run in a throwaway copy, since
    lowest-direct rewrites `uv.lock`);

    constants, or `uv.lock`/`pyproject.toml` dependency lists;

- **Merging:** the coordinator merges one lane at a time (merges are minutes; lanes are hours); after each merge the
