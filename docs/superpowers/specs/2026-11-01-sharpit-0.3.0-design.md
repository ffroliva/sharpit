## 1. Intent

0.2.0 shows what the app does while a developer uses it. 0.3.0 turns the same capture into **findings a CI job can
gate on**. A `pytest --sharpit` run tags every SQL statement and exception with the test that caused it, writes a
JSON report against a published schema plus JUnit XML, and fails the build when a test runs too many queries, runs an
N+1, logs an exception, or when an advisor finds something. When sharpit could not see enough to judge, the report
says `unknown` rather than passing quietly.

Two uses must work. Owner: both are valid and both are supported.

- **In code** (the dev console, as today): `sharpit.install(app)`, now also tracing raw `sqlite3`.
- **Out of code** (`pytest --sharpit`): no change to the app.

The rule from the MVP stays: when in doubt, do what BootUI does. BootUI has no test-time plugin and no shared report
schema (its CLI writes one typed JSON per panel; `docs/CLI.md` gates on `severityCounts` with `jq`), so most of this
release is sharpit's own design. Each place it departs from BootUI is logged in §14.

## 3. Non-goals (0.3.0)

Owner: baselines, SARIF, the HTML report, database and security advisors, the collector container (deferred, not
dropped), psycopg/asyncpg sources. All of these move to 0.4.0 or later (the rest of #6 is re-filed under 0.4.0). Also
out: timing-based gates, a `sharpit` console script, an MCP tool for the report, running the vulnerabilities advisor
from the plugin (it needs the network), and capturing HTTP exchanges per test.

## 4. Anti-goals

- **A quiet green.** If `--sharpit` was given and sharpit could not see what it needed, the run is `unknown` and the
  build fails unless the user explicitly allows unknown (coordinator's call, §6.6).
- **The plugin acting without being asked.** Installing sharpit changes nothing about a plain `pytest` run. Importing
  the plugin module patches nothing, sets no contextvar, adds no handler and opens no file (B1).
- **A secret in a report.** Reports never contain bound parameter values, whatever `SHARPIT_SQL_TRACE_CAPTURE_PARAMETERS`
  says. SQL is written normalised (literals replaced) and then masked (B4).
- **A flaky gate.** Gates count; they never time. Durations may be reported, never gated (B8).
- **Blaming the wrong test.** Only statements tagged with the running test count against it (B6).
- **A patch that outlives its owner** (B5, A5), or a patch that breaks a host query: every hook catches its own
  errors and the statement runs exactly as it would without sharpit.
- Everything in 0.2.0 §4 still applies: inactive sharpit adds nothing; no GET or MCP tool opens a socket or writes a
  file; every buffer is bounded.

## 5. P1: the finding contract and the advisor registry

### 5.1 The problem today

`RuleResult` holds a rule's status, a violation count and up to 10 sample strings. A violation has no identity of its
own, so it cannot be dismissed, tracked or attributed to a test, and the report has no common shape between
advisors. `dismissals.owning_panel()` hard-wires REST API and vulnerabilities.

### 5.2 `Finding`

New module `engine/advisors/findings.py`:

```python
@dataclass(frozen=True)
class Finding:
    rule_id: str            # e.g. "RAPI-004", "sharpit.n-plus-one"
    advisor: str            # registry id: "rest-api", "test-runtime"
    severity: Severity      # CRITICAL|HIGH|MEDIUM|LOW|INFO (rules.SEVERITIES)
    target: str             # what it is about, stable across runs: "GET /owners/{owner_id}", a normalised SQL, a nodeid
    message: str            # human text, already masked
    test_node_id: str | None = None
    dismissed: bool = False

    @property
    def fingerprint(self) -> str: ...   # "<advisor>:<rule_id>:<16 hex of sha256(rule_id, target, test_node_id or "")>"
```

- **Fingerprint.** The finding's own inputs contain no file paths or timestamps, so it survives reformatting. It
  changes when the target changes (a renamed route or table is a different finding, explicitly). One exception: an
  exception finding's target includes the 0.2.0 exception-group fingerprint (class + first application frame, a port
  of BootUI's `ExceptionStore` key, which includes line numbers), so moving the raising line makes it a new finding,
  as in BootUI. It always matches
  `[A-Za-z0-9._:-]{1,200}`, the dismissal id grammar.
- **DTO** (`to_dto()`, camelCase, every key emitted): `ruleId`, `advisor`, `severity`, `target`, `message`,
  `fingerprint`, `testNodeId`, `dismissed`.

### 5.3 Advisor runs and the three outcomes

```python
@dataclass(frozen=True)
class AdvisorRun:
    advisor: str
    status: Literal["PASSED", "FAILED", "UNKNOWN"]
    findings: tuple[Finding, ...]
    evidence: dict[str, Any]      # the existing AdvisorEvidenceDto shape (usable, coverageComplete, limitations)
    reason: str | None            # why UNKNOWN; None otherwise
```

The status is derived, never set by hand (`AdvisorRun.of(...)`), from BootUI's evidence semantics
(`RestApiScanner.evidence()`, `SPECIFICATION.md` "confirmed empty scope ... counts as assessed"):

1. any non-dismissed finding at or above the gate severity → `FAILED`;
2. otherwise, `coverageComplete` false, or `usable` false **with** limitations, or the scan status is `PARTIAL` or
   `ERROR` → `UNKNOWN`, with `reason` = the first limitation, else `"assessment evidence is incomplete"`;
3. otherwise → `PASSED`. A confirmed-empty scope (BootUI's `usable:false, coverageComplete:true`, no limitations, for
   example an app with no routes) is `PASSED`.

`PASSED` therefore means "looked at everything it needed and found nothing". "Found nothing but could not look
everywhere" is `UNKNOWN`. Rule statuses keep BootUI's vocabulary inside panel DTOs; a `SKIPPED` rule affects the run
only through `coverageComplete`, never directly. This is the rule that applies to every advisor from now on.

### 5.4 The registry

New module `engine/advisors/registry.py`. An advisor registers once, at import of its own module:

```python
@dataclass(frozen=True)
class AdvisorSpec:
    id: str                          # "rest-api"
    panel: str                       # the panel whose gate covers dismissing its findings
    owns: Callable[[str], bool]      # rule id or fingerprint -> belongs to this advisor
    offline: bool                    # True: may run in a test session (no socket)
```

- `dismissals.owning_panel(id)` asks the registry instead of hard-wiring. The behaviour for today's ids is unchanged
  (golden and existing tests pin it).
- Registered in 0.3.0: `rest-api` (offline, runnable by the plugin), `vulnerabilities` (not offline, registered for
  dismissal ownership only), `test-runtime` (the plugin's own count rules, §6.4; dismissable by fingerprint only
  through the state file, there is no panel UI for it in 0.3.0).
- Import boundary: `registry.py` imports no collector. Collectors import the registry (rule 3 still holds: no
  collector imports another).

### 5.5 REST API on the contract (P4)

- `collectors/restapi/rules.evaluate()` returns structured violations, `(target, message)`, instead of bare strings,
  one per occurrence (no sample cap; the 10-sample cap stays in `RuleResult` for the panel). `target` is the route(s)
  the violation names as `"<METHOD> <path>"`, sorted and joined with `" | "` when a rule names several (for example
  `RAPI-MAP-002` duplicate routes), and the handler's `module:qualname` for a rule about a handler with no single
  route. The plan lists the target of every ported rule in a table, and a golden test pins the fingerprints.
- `RestApiService.run() -> AdvisorRun` is the new primary entry point. `report()` and `scan()` render the existing
  `RestApiReport` DTO **from the same run**: `results[].sampleViolations` stay the same strings as today
  (`f"{target}: {message}"` where today's text had that form; the builder keeps today's exact text, and the golden
  fixtures prove it). The panel JSON does not change shape.
- `PARTIAL` maps to `UNKNOWN` when nothing at gate severity was found; `NOT_SCANNED` never reaches a report (the
  plugin always runs a scan).

### 5.6 Per-finding dismissal

BootUI already dismisses single findings: a vulnerability is dismissed by `vulnerabilityId::packageName` in the same
`dismissedRules:` list as rule ids (`DependencyReports.java`, `DismissedRulesStore.java`; sharpit ports it as
`::pypi:`). sharpit generalises that, without a new block:

- A finding fingerprint is stored in the existing `dismissedRules:` list of `<state_dir>/sharpit.yml`, next to rule
  ids and vulnerability keys. `owning_panel()` resolves a fingerprint through the registry by its `<advisor>:` prefix.
- A rule-level dismissal still dismisses every finding of that rule. A fingerprint dismisses one finding.
- API and UI: the existing dismissed-rules endpoints accept a fingerprint (same guard, refused on a read-only panel, not
  an MCP tool). The REST API panel gets a "dismiss this finding" action on a violation row in the details drawer.
  Coordinator's call: kept small; no bulk actions.
- As in BootUI (`features/advisors.md`: commit `boot-ui.yml` to baseline), committing `sharpit.yml` is the way to
  accept findings until the 0.4.0 baseline file exists.
- The pytest plugin reads the list from the same state dir (`SHARPIT_STATE_DIR` or the default) and never writes it.

## 6. P2 + P3: the pytest plugin

### 6.1 Packaging and loading

- Module `src/sharpit/pytest_plugin/` (an adapter, like `sharpit/fastapi/`), registered as
  `[project.entry-points.pytest11] sharpit = "sharpit.pytest_plugin"`. `pytest` is **not** a runtime dependency: the
  module is only imported by pytest itself.
- The engine never imports `sharpit.pytest_plugin` (new import-boundary rule in `test_import_boundary.py` and in
  AGENTS.md, same PR).
- B1: importing the plugin registers options and the marker and does nothing else. A test imports it under the
  `no_side_effects` fixture, and a test runs a plain `pytest` (via `pytester`) and asserts `sqlite3.connect` is the
  stdlib function, no SQLAlchemy listener is attached and no report file exists.

### 6.2 Options

Every option has a CLI form and an ini form. CLI wins over ini. They are pytest options, not `SharpitSettings`: env
`SHARPIT_*` still governs settings shared with the console (masking, state dir, profiles, N+1 threshold, SQL trace
switches). This split is logged in §14.

| CLI | ini | Default | Meaning |
|---|---|---|---|
| `--sharpit` | `sharpit = true` | off | turn the plugin on for this session |
| `--sharpit-report=PATH` | `sharpit_report` | `sharpit-report.json` | JSON report path (controller only) |
| `--sharpit-junit=PATH` | `sharpit_junit` | none | JUnit XML of findings; not written when unset |
| `--sharpit-max-queries=N` | `sharpit_max_queries` | none | default per-test budget for the call phase |
| `--sharpit-fail-on=SEV` | `sharpit_fail_on` | `HIGH` | advisor findings at or above fail the session |
| `--sharpit-allow-unknown` | `sharpit_allow_unknown = true` | off | `unknown` does not fail the build |
| `--sharpit-app=MOD:ATTR` | `sharpit_app` | none | the ASGI app (or a zero-argument factory) the advisors read |
| `--sharpit-no-advisors` | `sharpit_advisors = false` | advisors on | run the count gates only |

Gates that are always on with `--sharpit`: N+1 (threshold = `SHARPIT_ACTIVITY_N_PLUS_ONE_THRESHOLD`, default 5) and
exceptions (any captured exception fails its test). Each can be relaxed per test with the marker (§6.5).
Coordinator's calls: the option names above, `HIGH` as the default severity gate (BootUI's REST rules are mostly
MEDIUM/LOW; gating those by default would make the first run unusable), and both count gates on by default.

### 6.3 Lifecycle and hook order

| Hook | What happens |
|---|---|
| `pytest_addoption` | options and ini keys; nothing else |
| `pytest_configure` | register the `sharpit` marker always (no "unknown marker" warning); return unless `--sharpit` |
| `pytest_load_initial_conftests` (tryfirst, hookwrapper) | when `--sharpit`: the activation check (§6.7), then attach the sqlite3 source and, if SQLAlchemy is already imported, its listeners. Runs **before conftests import app code** (B5, A6). `early_config.known_args_namespace` carries the flag; the ini flag is read with `early_config.getini` |
| `pytest_sessionstart` | retry attaching SQLAlchemy if it was imported by a conftest |
| `pytest_runtest_protocol` (hookwrapper) | set the current-test window `(nodeid)`; reset it after |
| `pytest_runtest_setup` / `_call` / `_teardown` (hookwrappers) | set the phase; set the `TEST` contextvar `(nodeid, phase)` in the test's own thread, reset after; retry the SQLAlchemy attach (cheap) |
| `pytest_runtest_makereport` (hookwrapper) | for the `call` phase, evaluate the test's gates (§6.4); a violation turns a passed report into a failed one with a `sharpit:` long-repr; a test that already failed keeps its own failure and gets the sharpit lines appended |
| `pytest_sessionfinish` | run the offline advisors (§6.6); worker: put the session's facts in `config.workeroutput["sharpit"]`; controller (or a run without xdist): merge, write reports, set `session.exitstatus` |
| `pytest_unconfigure` | detach everything with the identity checks (§8.4), even after a crash in an earlier hook |
| `pytest_terminal_summary` | one block: status, per-gate counts, worst tests, report path |

The builder verifies the exact hook (`pytest_load_initial_conftests` vs `pytest_cmdline_main`) against pytest's
current docs; the requirement is fixed: attach before any conftest module is imported, detach in every exit path.

### 6.4 Attribution, phases and the count gates

**Attribution (B6).** Verified 2026-11-01 (anyio 4.15.1, starlette 1.10.0): a contextvar set in the test thread is
visible inside both `async def` and `def` handlers called through `TestClient`, **including through a long-lived
`with TestClient(app)` opened in an earlier fixture**: each request carries the calling test's current value (probe:
tag set to `test-1` then `test-2` after the portal opened; handlers saw `test-1` then `test-2`). A task started by the
lifespan keeps the value from when the lifespan started (it saw `fixture-setup`), which is exactly the stale-tag case
below. No context-propagation shim is needed; a test pins this behaviour so an anyio change shows up. So:

- `engine/capture/correlation.py` gains `TEST: ContextVar[tuple[str, str] | None]` (nodeid, phase), next to `REQUEST`.
- The plugin also keeps a process-global "current test window" (the nodeid between `runtest_protocol` start and end).
- A statement **counts against a test** only when its `TEST` tag equals the current window's nodeid. Anything else
  goes to the **unattributed** bucket, which is reported, never gated: a statement with no tag (a thread that dropped
  the context, aiosqlite's worker thread), or a stale tag (a worker started by a lifespan in an earlier test, like
  gflow's `FlowWorker`, still carrying that test's id).
- Statements marked `INTERNAL` (sharpit's own work) are ignored.

**Phases (B7).** Every fact carries its phase. The gates apply to the `call` phase only. Setup and teardown counts are
reported per test.

**Filtered statements (B7).** A sharpit-only rule (BootUI records PRAGMA, schema and DDL statements; JDBC
commit/rollback never reach it as SQL text), applied **only in the test-session sink**: the console's SQL Trace stays
unfiltered, as in BootUI. Built in, not configurable in 0.3.0 (coordinator's call), and listed by name in the
report's `filtered.rules`:

- `PRAGMA ...`;
- reads of `sqlite_master` / `sqlite_schema` / `sqlite_temp_master`;
- reads and writes of `alembic_version`;
- transaction control: `BEGIN`, `COMMIT`, `ROLLBACK`, `SAVEPOINT`, `RELEASE`.

Filtered statements are counted (`filtered.count` per test and in total) but never gated.

**Gates per test, call phase only:**

| Rule id (`test-runtime` advisor) | Fails when | Severity |
|---|---|---|
| `sharpit.max-queries` | queries > the budget (marker, else `--sharpit-max-queries`; no budget → not evaluated) | HIGH |
| `sharpit.n-plus-one` | one `SELECT` group runs ≥ threshold times (threshold minimum 2, as BootUI) | HIGH |
| `sharpit.exception` | more than `max_exceptions` (default 0, §6.5) swallowed exceptions | HIGH |

A query is one `execute`, one `executemany` (a batch, as BootUI records a JDBC batch once) or one `executescript`.

N+1 grouping uses the 0.2.0 activity key (`Normalized.fingerprint`: literals folded, `IN` lists collapsed, case
ignored), not BootUI's literal-keeping key; logged in §14. The finding's `target` is `Normalized.sql` and its
fingerprint input is `Normalized.fingerprint`, so the finding's identity is the grouping key.

A gate violation becomes a `Finding` and fails that test. Targets: `max-queries` = the nodeid; `n-plus-one` = the
normalised SQL; `exception` = the nodeid plus the exception-group fingerprint, so two different exceptions in one test
are two findings. `test_node_id` is always set. A dismissed fingerprint does not fail the test.

**Exceptions source: what "swallowed" means.** The gate is about exceptions the app handled or logged but did not raise
to its caller, the silent errors a passing test hides. Sources, for the session, with `--sharpit`:

- the 0.2.0 exception capture's `logging` path (records with `exc_info` at ERROR or above, from any logger);
- when the app under test runs `sharpit.install` with capture active by its own activation rules, its middleware and
  wrapped-handler paths.

They are de-duplicated by exception object identity within a test. An exception that **escaped the ASGI app** (sharpit's
middleware saw it propagate out, so TestClient re-raises it into the test, where `pytest.raises` or a failure deals
with it) is excluded, along with every logged copy of the same object. Without the middleware sharpit cannot see an
escape, so a logged-then-re-raised exception counts; documented, and the marker's `max_exceptions` covers a deliberate
case. Messages are masked.

### 6.5 The marker (P3)

```python
@pytest.mark.sharpit(max_queries=5)                       # owner
@pytest.mark.sharpit(allow_n_plus_one=True, max_exceptions=1)
```

Only these three keyword arguments exist (`max_queries: int`, `allow_n_plus_one: bool`, `max_exceptions: int`,
default 0). Anything else is a `pytest.UsageError` at collection. The closest marker wins (function over class over
module). Without `--sharpit` the marker does nothing. Coordinator's call: the two extra arguments, so a test that
exercises an error path can say so instead of being dismissed.

### 6.6 Outcome of the session

The report's `status`:

1. `fail`: any test failed a sharpit gate, or any advisor run is `FAILED`;
2. `unknown`: otherwise, any of:
   - no SQL source attached at session end;
   - **no statement attributed to any test** in the whole run (sources attached but blind, or everything landed in
     `unattributed`): reason `"no SQL statement was attributed to a test"`;
   - **an untraced driver is in use**: at session end `sys.modules` holds a DB-API driver sharpit does not trace in
     0.3.0 (`asyncpg`, `psycopg`, `psycopg2`, `pymysql`, `MySQLdb`, `oracledb`, `pyodbc`) and SQLAlchemy is not
     imported (with SQLAlchemy imported, its source covers them; listed as a limitation only). The driver appears in
     `sources[]` with `attached: false`;
   - an advisor run is `UNKNOWN` (for example `rest-api` with no app: reason
     `"no application: pass --sharpit-app or call sharpit.install in the tests"`);
   - a worker's facts are missing at merge (a crashed xdist worker);
3. `pass`: otherwise.

The terminal summary warns when unattributed statements outnumber attributed ones, without changing the status.

Exit status: `fail` sets `session.exitstatus = 1` if pytest would have returned 0. `unknown` does the same unless
`--sharpit-allow-unknown` (coordinator's call, from the brainstorm: "`--sharpit` given but capture could not attach →
unknown, build FAILS by default; a setting allows it"). pytest's own non-zero codes are never lowered.

**Which app the advisors read.** `--sharpit-app` if given (imported in `pytest_sessionfinish`, after the tests, so it
is never imported before the sqlite3 patch). Otherwise every app passed to `sharpit.install` during the session, **active
or not**, in install order: `install()` records each app in a process-level weak registry
(`sharpit.fastapi.installed_apps()`) before its activation decision, because reading routes is a side-effect-free read.
`--sharpit` never changes what `install()` decides; capture through the app's own middleware happens only when the
app's own activation enables it (the safety model is unchanged). Otherwise `rest-api` is `UNKNOWN`. `--sharpit-no-advisors` skips advisors entirely; the report then
lists them under `advisors` with status `UNKNOWN` and reason `"advisors disabled"` but they do not make the session
`unknown` (the user asked for count gates only). Coordinator's call.

### 6.7 Activation for the test session (B3)

The plugin never calls `activation.decide()` with a dev-server signal. With `--sharpit` it computes the active
profiles from the same `profile_vars` and settings:

- a profile in `SHARPIT_DISABLED_PROFILES` is active (e.g. `APP_ENV=production`) → `pytest.UsageError`
  `"sharpit: --sharpit refused because active profile '<p>' is in SHARPIT_DISABLED_PROFILES"`, unless
  `SHARPIT_ENABLED=ON`, which proceeds with the same warning text as `decide()`;
- `SHARPIT_ENABLED=OFF` together with `--sharpit` → `pytest.UsageError` (two explicit instructions disagree; fail
  closed). Coordinator's call;
- an invalid `SHARPIT_ENABLED` value → `pytest.UsageError` with `decide()`'s reason text (fail closed). Other settings
  warnings (an invalid `SHARPIT_*` value falling back to its fail-safe) do not stop the run; they go to the report's
  `warnings` list and the terminal summary;
- otherwise the session is captured. The plugin opens no HTTP surface, mounts nothing and starts no thread.

### 6.8 xdist

- Each worker attaches and detaches in its own process (B5) and evaluates its own tests' gates.
- In `pytest_sessionfinish` a worker serialises its facts (§7 per-test entries, unattributed and filtered counters,
  source status, advisor runs) as JSON into `config.workeroutput["sharpit"]`.
- The controller collects them in `pytest_testnodedown(node, error)`. A node that ends with an error or without the
  key is recorded in `workers[]` with `"status": "missing"`, which makes the run `unknown`.
- The controller runs no capture of its own and writes the reports.
- **Where advisors run.** With `--sharpit-app`, once, on the controller (or the single process without xdist).
  Without it, each worker runs them over the apps installed in that worker and ships the runs in `workeroutput`.
- The merge is a concatenation (test ids are unique per run), plus sums for the counters. Advisor runs of one advisor
  from several workers merge as: findings de-duplicated by fingerprint; status `FAILED` if any is, else `PASSED` if any
  worker assessed fully, else `UNKNOWN`.

```json
    {"ruleId": "sharpit.n-plus-one", "advisor": "test-runtime", "severity": "HIGH",
     "target": "SELECT ... FROM pets WHERE owner_id = ?", "message": "10 executions of one SELECT in the call phase",
     "fingerprint": "test-runtime:sharpit.n-plus-one:3f9a...", "testNodeId": "tests/test_owners.py::test_list",
     "dismissed": false}
  ]
}
```

- `severityCounts` uses BootUI's form and `SeverityOrder.DEFAULT` (`CRITICAL, HIGH, MEDIUM, LOW, INFO`, zeros
  included), counted after dismissal, one per finding. That equals BootUI's per-rule sum of `violationCount` because
  `evaluate()` emits every occurrence (§5.5). A BootUI-style `jq` gate works on it unchanged. (Vulnerabilities, with
  BootUI's `UNKNOWN`/`NONE` severities, are not run by the plugin.)
- `warnings`: settings warnings and source limitations (for example `"connections opened before capture started are
  not traced"`), each masked; always present, possibly empty. It sits between `statusReasons` and `gates`.
- `findings` is the one flat list (the name #18 settles on, §14). Per-test entries reference findings by fingerprint.
- Per-test SQL: only normalised, masked SQL, and only in `nPlusOne` and `topStatements` (at most 10 per test and 20
  unattributed). Never parameters (B4). `tests[]` is complete (every test that ran), not capped.
- Versioning: `schema` is `sharpit-report/<major>`. Adding a key is a minor change within `/1` (consumers must ignore
  unknown keys; the schema says `additionalProperties: true` at the top level and on objects meant to grow). Removing
  or renaming a key, or changing a meaning, is `/2`.

### 7.2 JUnit XML

Only with `--sharpit-junit`. One `<testsuite name="sharpit">`, one `<testcase>` per finding
(`classname` = advisor, `name` = fingerprint) with a `<failure type="<ruleId>" message="...">` when the finding is not
dismissed, plus one `<testcase name="sharpit.status">` that fails when the run is `fail`, or `unknown` without
`--sharpit-allow-unknown`. It never repeats the user's own tests (pytest's `--junitxml` already covers them, and gate
failures already show there because the test itself failed). Coordinator's call.

### 7.3 Writers and masking

One function renders the JSON, and the JUnit writer reads that same dict. Every string that comes from the app (SQL,
messages, targets, exception text) has already gone through the masker when the fact was recorded. The secret corpus
test (`tests/test_masking_corpus.py`) gains the report writers: it plants every corpus secret as a bound parameter, as
an SQL literal, in an exception message and in a route path, runs a `pytester` session with `--sharpit` and both
reports on, and asserts no secret appears in either file.

## 8. P5: the sqlite3 source and the shared SQL source interface

### 8.1 One recorder, one source per driver

New package `engine/sources/`:

- `engine/sources/dispatch.py`: the routing and emitting code that is in `sqla.py` today (`_statement_targets`
  minus the engine lookup, `_record`, the one-warning-per-process failure path), plus the **session sink** used by the
  plugin. A source calls one function:

  ```python
  def emit(event: SqlEvent) -> None: ...   # never raises

  @dataclass(frozen=True, slots=True)
  class SqlEvent:
      source: str                 # "sqlalchemy" | "sqlite3"
      sql: str                    # placeholder SQL, never expanded
      parameters: object          # passed to the recorder for masking; the session sink drops it
      executemany: bool
      batch_size: int | None
      started_ns: int
      duration_ns: int
      rowcount: int
      error: BaseException | None
      connection_id: str | None
      engine: object | None       # SQLAlchemy only, for the "held by" routing rule
  ```

  `emit` sends the event to (a) the console contexts by today's rules (in a request: that request's context; outside:
  the contexts holding the engine, else the only context) and (b) the test-session sink when the plugin set one.
  `INTERNAL` is checked once, in `emit`.
- `engine/sqla.py` keeps its listeners and registry and calls `emit`. Its tests and the overhead budget keep passing
  unchanged.
- `engine/sources/sqlite.py`: the only module that imports `sqlite3` (a new gatekeeper row in AGENTS.md rule 4).

### 8.2 Mechanism (council, unanimous)

While attached, `sqlite3.connect` is replaced by a function that calls the original with
`factory=TracedConnection` (or, if the caller passed its own `factory` that subclasses `sqlite3.Connection`, a cached
`type("Traced"+name, (TracedMixin, factory), {})`; a factory that is not a `Connection` subclass is passed through
untraced and counted in the source's `limitations`).

- `TracedConnection` overrides `execute`, `executemany`, `executescript` and `cursor()`; `cursor()` returns a
  `TracedCursor` overriding the same three. `Connection.execute` does not call a Python `cursor()` override, so both
  levels are needed.
- Each override times the call with `perf_counter_ns`, calls the original, and emits an `SqlEvent` with the SQL as
  given, the parameters, `executemany`, the row count (`cursor.rowcount`) and the error. An error is emitted and then
  re-raised unchanged.
- `executescript` emits one event and counts as one query, like a JDBC batch in BootUI (`SqlTracingProxies`
  records a batch once, classified by its first statement). Its category is `category_of(script)`, which reads the
  first statement; no new category value is added (BootUI's set is SELECT, INSERT, UPDATE, DELETE, DDL, OTHER).
  `batchSize` stays 0 for a script: sharpit does not split SQL.
- `executemany` emits one event with `executemany=True` and `batch_size = len(parameters)`, as the SQLAlchemy source
  does.
- **Never** `set_trace_callback`: no timing, rowcount or error, and its SQL has the bound values expanded, which the
  masker cannot see (A4).
- The tracing runs in the caller's thread; nothing touches a connection from another thread (A7).
- Connection id: `hex(id(conn))`.

### 8.3 Patch point

Patch `sqlite3.connect` only, never `sqlite3.dbapi2.connect`. Verified 2026-11-01: SQLAlchemy 2.1.6 opens SQLite
through `sqlite3.dbapi2.connect`, so SQLAlchemy-on-SQLite stays on the SQLAlchemy source and is never counted twice.
A test pins it: a SQLAlchemy SQLite engine with both sources attached records each statement exactly once, with
`source == "sqlalchemy"`. If a future SQLAlchemy goes through `sqlite3.connect`, that test fails and the fix is a
contextvar set around SQLAlchemy's connect (the sqlite3 source then skips), not a silent double count.

### 8.4 Attach and detach

- `attach()` is idempotent: a second call while attached does nothing (A5).
- `detach()` restores the original only when `sqlite3.connect` is still sharpit's function; otherwise it logs one
  warning and leaves the other library's patch in place.
- Connections opened before `attach()`, and a `from sqlite3 import connect` bound before it, are not traced. This is a
  documented limit. The SQL Trace panel and the report's `sources[].limitations` say
  `"connections opened before capture started are not traced"` (A6).

### 8.5 Who attaches

| Trigger | When | Decision |
|---|---|---|
| `sharpit.install(app)` | on the active branch only, when `SHARPIT_SQL_TRACE_ENABLED` and `SHARPIT_SQL_TRACE_SQLITE3_ENABLED` (new, default true) | `activation.decide()` (A2) |
| `sharpit.attach_sql_sources()` | new public function, for a dev wrapper that must patch before importing the app | the same settings and `activation.decide()`; returns the `ActivationStatus`; capture never switches sharpit on by itself |
| `pytest --sharpit` | `pytest_load_initial_conftests` | §6.7 |

`attach_sql_sources()` and a later `install()` share one attachment (the second is a no-op). Detach happens when the
last context that needs it is removed (the `sqla.remove` pattern) or in `pytest_unconfigure`.

### 8.6 What the console shows

The SQL Trace panel's `dataSources` lists `sqlite3` next to the SQLAlchemy engines when the source is attached, and the
rows carry no new keys (BootUI's `SqlTraceReport` shape is kept). Statements from outside the app's package (for
example gflow's `browser_cookie3` reading the browser's cookie database) are still recorded with their call site, so
the developer can see where they came from (A3). Rows are never recorded, only SQL and masked parameters, and
parameters are off by default.
