# sharpit 0.2.0 — design (runtime diagnostics, database panels, first advisor)

Status: rev 3 (review findings merged, §19; agy council reviews folded in rev 3), draft for the owner · 2026-10-31 · owner: Flavio Oliva · coordinator: Claude.
Builds on the MVP design (`2026-10-30-sharpit-mvp-design.md`, called "MVP spec" below). Everything the MVP spec says
still holds unless this document changes it; its deviation log (§14) and coordinator's calls (§15) carry over.

## 1. Intent

0.1.0 shows what the app *is* (config, routes, providers, loggers, packages). 0.2.0 shows what the app *does* while you
use it: the requests it served, the SQL it ran, the errors it raised, its log, its threads and tasks, its database pools
and migrations, its health, and a first advisor that reviews the REST layer. Scope is exactly the twelve "Build next"
rows of the 2026-10-31 feature-gap survey.

The rule from the MVP stays: **when in doubt, do what BootUI does** (github.com/jdubois/boot-ui, read-only at
`C:\development\github\boot-ui`). Sources of truth, in order: this spec, the MVP spec, the BootUI DTO records and
controllers cited per feature, BootUI's unit tests. Every JSON key below is a BootUI record component unless the
deviation log (§17) says otherwise. Unlogged deviations are bugs.

Path abbreviations as in the survey: `DTO/` = `bootui-core/src/main/java/io/github/jdubois/bootui/core/dto/`,
`ENG/` = `bootui-engine/src/main/java/io/github/jdubois/bootui/engine/`, `AC/` =
`bootui-spring-autoconfigure/src/main/java/io/github/jdubois/bootui/autoconfigure/`, `views/X.vue` =
`bootui-ui/src/main/frontend/src/views/X.vue`.

## 4. Anti-goals (on top of MVP spec §4)

- **Inactive sharpit adds nothing to the host app.** No middleware, no logging handler, no SQLAlchemy listener, no
  wrapped exception handler, no contextvar set. Only the MVP's 404 mount. A test proves it (§14.2).
- A captured value leaves the process without passing through the masker: URL paths, query strings, headers, SQL
  text and bind values (including SQLAlchemy error text), log messages, exception messages, health details, probe
  response headers and bodies.
- A buffer that can grow without a cap. Every buffer below has a fixed, configurable maximum.
- A GET or an MCP tool that opens a socket, connects to the database, runs a user callback or writes a file. Reading
  the database's migration version and running health checks are explicit POSTs.
- The HTTP probe opening a socket, reaching another host, or reaching sharpit's own mount.
- A capture hook that can break a host request. Every hook catches its own errors, logs one warning per hook and
  carries on; a bug in sharpit costs a missing row, never a 500.
- Capture slowing the host noticeably: the per-request overhead budget is ≤ 0.2 ms median with every panel on,
  measured by a test against a bare route (§14.1).

## 5. Constraints (unchanged from the MVP, restated because every feature touches them)

- Runtime dependencies stay exactly `starlette` and `packaging`. `tests/test_packaging.py` keeps enforcing it.
- SQLAlchemy is optional. sharpit never imports it at module load and never imports it at all if the host has not
  (§6.2). Alembic is **not imported at all** (§7.6). httpx is not used (§7.11).
- MCP stays read-only and never executes code. Actions that change state (clear a buffer, pause capture, dismiss a
  rule, change an exception status, run a scan, run a probe, run health checks, read the migration version from the
  database) are guard-protected POSTs (or DELETE), refused on read-only panels, and are not MCP tools.
- The guard chain (MVP spec §7.5) covers every new route, SSE streams included. No new route is outside the API path.
- Python ≥ 3.12, pyright strict on `src/sharpit`, the engine imports neither fastapi nor starlette. Free-threaded
  builds (3.13t/3.14t) are not supported in 0.2.0: when `sys._is_gil_enabled()` is false, Threads shows names only
  with a reason.
- SQLAlchemy-backed panels need SQLAlchemy ≥ 2.0 (the `engine_connect` signature and the pool attributes of §7.7);
  an older version gives `available: false` with the reason.
- `install()` creates no threads and no timers (safe under `gunicorn --preload` and fork). Timers live on the running
  loop and are created lazily.

`engine/capture/*` and `engine/probe.py` speak plain ASGI dicts and stdlib types, so they stay framework-neutral. A
future Django/Flask adapter would supply its own middleware feeding the same buffers.

### 6.1 Wiring at install, only when active

`install()` keeps its order: settings → activation → (inactive: 404 mount, return). On the **active** branch only, and
only for panels whose `SHARPIT_PANELS_<ID>_ENABLED` is true, it then:

| Step | What | Needed by | When disabled |
|---|---|---|---|
| 1 | `app.add_middleware(CaptureMiddleware, ctx=ctx)`: outermost user middleware, inside Starlette's `ServerErrorMiddleware` | F1, F2, F4, request ids for F3 | skipped when `http-exchanges`, `exceptions`, `sql-trace` and `activity` are all disabled |
| 2 | wrap each entry of `app.exception_handlers` whose key is a class that is not an `HTTPException` subclass or `RequestValidationError`; of the int keys only `500` is wrapped (other ints are status-code handlers, i.e. control flow). Handlers registered **after** `install()` are wrapped too (see below) | F2 | skipped when `exceptions` is disabled |
| 3 | add `SharpitLogHandler` to every existing logger with `propagate=False` and at least one handler (uvicorn's `uvicorn`, `uvicorn.access`); the **root** logger gets it at the end of lifespan startup, when the non-propagating loggers are also scanned again (see below) | F5, F2 (`exc_info` records) | skipped when `log-tail` and `exceptions` are disabled |
| 4a | attach the `engine_connect` discovery listener if SQLAlchemy is already imported (§6.2) | F6, F7, F8 (engine registry) | skipped when `alembic`, `database-connection-pools` and `health` are disabled |
| 4b | attach the statement listeners (`before/after_cursor_execute`, `handle_error`) | F3 (F4 reads F3) | skipped when `sql-trace` is disabled |

A wrapped exception handler keeps the original's kind: an `async def` wrapper only when
`is_async_callable(original)` is true, else a plain `def` wrapper (Starlette picks how to call it from that). Tested
with a sync handler, an async handler, a `functools.partial` and a custom 404 handler (left unwrapped).

**Handlers registered after `install()`.** Starlette copies `app.exception_handlers` into its `ExceptionMiddleware`
when it builds the middleware stack on the first ASGI call (the lifespan scope), so wrapping later is impossible and
an `@app.exception_handler(...)` placed after `install()` would never be seen. Step 2 therefore replaces
`app.exception_handlers` with a `dict` subclass whose `__setitem__` wraps qualifying handlers (Starlette's
`add_exception_handler`, which FastAPI's decorator calls, assigns through it). `uninstall_capture()` and lifespan
shutdown put back a plain `dict` holding the originals. Tested with a handler registered after `install()`.

**Middleware order.** `add_middleware` inserts at index 0, so `CaptureMiddleware` is the outermost user middleware
only when `install()` runs after the host's own `add_middleware` / `@app.middleware` calls. Requests a later-added
middleware answers itself (a CORS preflight, an auth 401, a rate-limit 429) never reach it. sharpit does not reorder
the host's middleware: at lifespan startup (or the first request) it checks `app.user_middleware[0]` and, when it is
not `CaptureMiddleware`, logs one warning naming the outer middleware and saying to call `sharpit.install(app)` last.
The README says the same.

The MVP's lifespan wrapper (already active-only) gains duties. On startup, after the host's own startup has run: retry
steps 4a/4b if SQLAlchemy was not imported at install, attach the root log handler (attaching it at the end of
startup leaves `logging.basicConfig()` / `dictConfig()` called by the app during startup working), and scan the
non-propagating loggers of step 3 again, attaching where the handler is missing (`uvicorn.run(app)` called from the
app's own module runs uvicorn's `dictConfig` after `install()`, which drops handlers from the `uvicorn` loggers).
Every logger sharpit attached to is recorded, so shutdown removes exactly those. If the app runs
without lifespan, the first host request seen by `CaptureMiddleware` does the same. When Log Tail is read and the
handler is no longer on root (the app called `dictConfig` or `basicConfig(force=True)` later), the panel reports
`available: false` with that reason. On shutdown it removes the log handler and the SQLAlchemy listeners.
`SharpitHandle.uninstall_capture()` does the same for tests and for apps run without lifespan. (uvicorn sends
`lifespan.shutdown` only after open responses have drained, so lifespan does not close SSE streams; their short
lifetime does, §10.)

**Root handler and the console.** With a handler on root, `Logger.callHandlers` no longer falls back to
`logging.lastResort`, so an unconfigured app would stop printing its warnings. `SharpitLogHandler.emit` therefore
forwards a record to `logging.lastResort` when no other handler in the record's logger hierarchy would have handled
it and `record.levelno >= logging.lastResort.level`. Two tests: an unconfigured app still prints a warning to stderr
while sharpit is active, and `basicConfig()` called during startup still configures root.

**Starlette build order.** `add_middleware` only works before the middleware stack is built (Starlette raises
`RuntimeError` once the app has started). `install()` is documented to run before the app serves; if `add_middleware`
raises, sharpit logs one warning ("request capture unavailable: install() ran after the app started"), the panels that
need it report `available: false` with that reason, and everything else works. A test pins this against the minimum
supported Starlette. A second `install()` call returns the existing handle (MVP behaviour), so the middleware is never
added twice.

**Pure ASGI, never `BaseHTTPMiddleware`.** `BaseHTTPMiddleware` runs the endpoint in another task (contextvars set
downstream are invisible upstream) and buffers streaming bodies. `CaptureMiddleware` wraps `receive`/`send` only.

**Self-exclusion.** Requests whose route path is under `settings.path` are passed through untouched (the route path
is computed by the same helper `SharpitMount` uses, so `--root-path` and Starlette's `root_path` semantics agree;
tested with `--root-path /api`):
no request id, no exchange row, no activity tick. They are counted in `hiddenSelf` (BootUI `exclude-self`). SQL run by
sharpit itself (health checks, migration version read) runs with the internal marker of §9 and is not traced.

### 6.2 SQLAlchemy without importing SQLAlchemy

`engine/sqla.py` reads `sys.modules.get("sqlalchemy")`. If it is absent, every SQLAlchemy-backed panel reports
`available: false`, reason `"SQLAlchemy is not imported by this application"`, and nothing is attached. Importing it
ourselves would cost the install budget (MVP spec §4: ≤ 50 ms) and load a library the app may not use.

When present (and ≥ 2.0, §5), sharpit registers **class-level** listeners on `sqlalchemy.engine.Engine`:
`engine_connect` (engine discovery, step 4a) and `before_cursor_execute`, `after_cursor_execute`, `handle_error` (F3,
step 4b). Class-level listeners cover every engine, including engines created later in a factory or lifespan, and
`AsyncEngine` (its `sync_engine` is an `Engine`). Attach points, first one wins: `install()`, lifespan startup, first
host request seen by `CaptureMiddleware`. Detach with `sqlalchemy.event.remove` on shutdown.

**Several apps in one process.** The listeners are process-wide but the data is not. Each installed context has an
id, and `RequestInfo` (§9) carries the id of the context whose middleware created it. A statement inside a request
is recorded only by that context. A statement outside any request is recorded by the contexts whose engine registry
holds its engine, or by the only active context when there is one. App A's console never shows SQL that ran inside
app B's requests.

**Engine registry** (F6, F7, F8): a `WeakSet` fed by (a) `install(app, engines=[...])` (Engine or AsyncEngine; new
kwarg, no env var) and (b) the `engine_connect` listener, which sees an engine the first time it hands out a
connection. sharpit never scans `gc` and never creates an engine. An engine that has never connected and was not
passed in is invisible; the empty state says so and shows the `engines=[...]` snippet.

Engine display name: `<dialect>+<driver>://<host>[:<port>]/<database>`, built from the URL **without** userinfo and
**without** the query string, then passed through the masker. Two engines with the same name get `#2`, `#3` (the beans
rule).

**Async engines.** The registry holds the sync `Engine` (for an `AsyncEngine`, its `sync_engine`). sharpit's own
reads (health §7.8, Alembic §7.6) check `engine.dialect.is_async`: when true they run on the event loop through
`sqlalchemy.ext.asyncio.AsyncEngine(engine)` (imported only because SQLAlchemy is already in `sys.modules`) under
`asyncio.timeout`; otherwise in a worker thread through `asyncio.to_thread`, which copies the `INTERNAL` contextvar
(`loop.run_in_executor` does not). Running a sync engine call on an async driver would raise `MissingGreenlet` and
report a healthy database as DOWN.

## 7. Features

Every report below emits every key, `null` when unknown (MVP rule). Epoch milliseconds unless a BootUI `Instant` is
named. Paging uses the MVP `PagedList` semantics (`q`, `offset`, `limit`, clamp to 1..1000). The UI does not render
parity-only fields that are always null or false (thread priority and lock fields, Hikari-only pool settings, Flyway
`installedBy`/`checksum`, `sessionId`) nor permanently disabled actions (Flyway migrate/clean). Captured strings are
rendered as text: no `{@html}` on any captured value (SQL highlighting, probe bodies, log colouring included); a lint
or grep test enforces it.

### 7.1 HTTP Exchanges (F1)

- **Purpose.** The last N requests the app served: when, what, how it ended, how long it took.
- **Python source.** `CaptureMiddleware` on the host app (§6.1).
- **Capture.** On `http` scopes only (WebSocket and lifespan pass through). Start time from `time.perf_counter_ns()`
  at entry; status from `http.response.start`; size = sum of `http.response.body` chunk lengths. The row is finalised
  in a `finally` around `await app(...)`, never by waiting for a final chunk (a mid-stream disconnect,
  `http.response.pathsend` and trailers send none): end = the final chunk if seen, else the app's return; status = the
  status actually sent when `http.response.start` went out (an exception after that keeps the sent status and sets
  the row's error flag); 500 only when no start was sent and an `Exception` escaped (re-raised; Starlette's
  `ServerErrorMiddleware` sends the 500 after us); 499 (nginx's "client closed request", logged in §17) only when no
  start was sent and an `http.disconnect` was received or the task was cancelled. Only `Exception` is caught:
  `CancelledError` re-raises and is never recorded in F2.
- **Buffer.** `collections.deque(maxlen=SHARPIT_HTTP_EXCHANGES_MAX_EXCHANGES)` (default 200, BootUI default); a
  `threading.Lock` around append/snapshot. Caps: path 2 048 characters, query 2 048 characters, 50 headers per side,
  1 024 characters per header value (longer values are cut with `…`), so a row has a byte bound.
- **Masking.** Path: each segment the secret-value detector flags (`is_secret_value`: reset tokens, JWTs, API keys)
  is replaced with `******` at capture time; the masked path is the one stored everywhere a request path appears (F1,
  F2 `requestPath`, F4, and through `mask_text` the uvicorn access-log lines of F5). Query string: each `name=value`
  pair is masked by name (`is_sensitive_key`) and by value (`is_secret_value`), then re-encoded; `uri` = masked path +
  masked query. Headers: always masked by name
  (`authorization`, `proxy-authorization`, `cookie`, `set-cookie`, `x-api-key` plus `is_sensitive_key`), and by value.
  `HttpHeaderDto.masked` is true when any value was replaced. `METADATA_ONLY` → `query` null, header values `[]`.
- **JSON.** `GET {api}/http-exchanges?q&method&statusClass&offset&limit` → `HttpExchangesReport {total, recorded,
  hiddenSelf, exchanges: HttpExchangeDto[], page, unavailableReason}`. `HttpExchangeDto {id, timestamp, method, path,
  query, uri, status, statusFamily, durationMs, responseSizeBytes, remoteAddress, principal, sessionId, traceId,
  requestHeaders, responseHeaders}`, `HttpHeaderDto {name, values, masked}`. `id` = the request id (§9);
  `timestamp` = ISO-8601 UTC string, as Spring Boot's Jackson writes `Instant` (BootUI sets no
  `WRITE_DATES_AS_TIMESTAMPS` override and `HttpExchanges.vue` parses it with `new Date`; frozen); `statusFamily`
  `"1xx"`…`"5xx"`; `principal` = `scope["user"].display_name` when Starlette's `AuthenticationMiddleware` set an
  authenticated user, else null (the panel help says so: apps using `Depends(get_current_user)` show none);
  `sessionId` null (Starlette sessions are signed cookies, no id); `traceId` = the trace id of an incoming W3C
  `traceparent` header **only when** it parses as `00-<32 hex>-<16 hex>-<2 hex>` with a non-zero trace id, else the
  request id; `remoteAddress` = `scope["client"][0]`, or null when `scope["client"]` is `None`. Newest first. `q`
  matches masked path, masked query, `uri` and `traceId`, as BootUI's `HttpExchangesService.matchesQuery` (method has
  its own filter).
- **Endpoints.** GET only. BootUI has no clear action for this panel; neither does sharpit (`actionCapable` false).
- **UI.** Table: time, method, path, status (coloured by family), duration, size. Filters for method and status class,
  free-text `q`, server paging. Row → side sheet with masked headers and a "Open in Activity" link (F4) and a "Replay
  in Probe" link (F12, pre-fills method and path, never headers). Live refresh through the activity tick stream (F4).
  Empty states: no requests yet ("Call your app, then come back"); capture unavailable (reason from the report).
- **MCP.** `get_http_exchanges` (BootUI name and schema from `bootui-tools.json`).
- **Out of scope.** Request/response bodies, WebSocket frames, exchanges of other workers.

### 7.2 Exceptions (F2)

- **Purpose.** Every distinct error the app raised, grouped with a count, so a developer sees "this broke 14 times"
  instead of 14 log entries.
- **Python sources** (all three can see the same exception object; it is recorded once, see dedup):
  1. `CaptureMiddleware`: an exception that escapes the app (an unhandled 500).
  2. Wrapped `app.exception_handlers` (§6.1 step 2): exceptions the app handles itself with a custom handler. The
     wrapper records, then calls the original handler unchanged. `HTTPException` and `RequestValidationError`
     handlers are not wrapped: they are control flow, already visible in F1.
  3. `SharpitLogHandler`: any record with `exc_info` (`logger.exception(...)`, background tasks, uvicorn's
     "Exception in ASGI application").
- **Dedup.** The first source to see an exception sets `exc.__sharpit_seen__ = <occurrence key>`, where the key is
  the current request id (or a fresh token outside a request). A later source skips the exception only when the
  stored key equals its own current key, so a module-level exception instance raised again in a later request is
  counted again. Instances that refuse attributes fall back to a bounded set of `(id(exc), request id)` pairs (64
  entries), evicted at request end.
- **Grouping** (port of `ExceptionStore`). Frames are ordered innermost first (the reverse of
  `traceback.extract_tb`), as BootUI does. Fingerprint = exception class qualified name + the first application frame
  in that order (`module:function:line`), falling back to the innermost frame; BootUI uses the class plus the top 5
  frames (logged in §17). Application frame = file not under any `site-packages`, `dist-packages` or the stdlib
  directory (the rule beans uses). An `ExceptionGroup` with one member is unwrapped; with several, the first leaf is
  fingerprinted and the others are listed as causes (still ≤ 5). Group `id` = first 16 hex of SHA-256 of the
  fingerprint. Statuses `OPEN`, `ACKNOWLEDGED`, `RESOLVED`; a new occurrence of a `RESOLVED` group reopens it and bumps
  `regressionCount`. Causes: `__cause__`, then `__context__` unless `__suppress_context__`, up to 5 deep, cycle-safe.
- **Re-entrancy.** A thread-local re-entrancy guard is checked **before** any store lock is taken, and DTOs are built
  outside the lock, so a GC finalizer that logs with `exc_info` while the lock is held cannot deadlock.
- **Buffer.** `SHARPIT_EXCEPTIONS_MAX_GROUPS` (100), `_MAX_OCCURRENCES_PER_GROUP` (25), `_MAX_STACK_FRAMES` (50), all
  BootUI defaults; the group with the oldest `lastSeen` is evicted first. Messages are cut at 2 000 characters.
- **Masking.** `Masker.mask_text()` (new, §11) on every message, cause message and logged message. Frames carry file,
  function and line only; **never locals**.
- **JSON.** `GET {api}/exceptions` → `ExceptionsReport {available, unavailableReason, maxGroups, totalExceptions,
  groups: ExceptionGroupDto[]}`. `ExceptionGroupDto {id, exceptionClassName, message, count, firstSeen, lastSeen,
  location, applicationException, lastThread, lastRequestMethod, lastRequestPath, lastHandler, lastSource, lastTraceId,
  status, regressionCount, errorContract}`. `exceptionClassName` = `module.QualName` (`builtins.` dropped);
  `lastHandler` = route endpoint `module:qualname` from `scope["endpoint"]` when available; `lastSource` one of
  `"request"`, `"handler"`, `"log"`; `errorContract` null (no error-contract catalogue in 0.2.0).
  `GET {api}/exceptions/{id}` → `ExceptionDetailDto {group, frames, causes, occurrences}` with
  `ExceptionFrameDto {declaringClass, methodName, fileName, lineNumber, applicationFrame}` (`declaringClass` = module),
  `ExceptionCauseDto {exceptionClassName, message, frames, commonFrames}`, `ExceptionOccurrenceDto {timestamp, thread,
  requestMethod, requestPath, handler, source, traceId}`. Unknown id → 404 `{"error":"Unknown exception group '<id>'"}`.
- **Actions** (panel action-capable, BootUI): `DELETE {api}/exceptions` → 204 (clear);
  `POST {api}/exceptions/{id}/status` body `{"status":"ACKNOWLEDGED"}` → updated group; invalid status → 400 with
  BootUI's text `"Invalid status 'X'; expected one of OPEN, ACKNOWLEDGED, RESOLVED"`. The body is optional in BootUI:
  an empty body gets the same 400 (not a 413 or a JSON-parse error).
- **Stream.** `GET {api}/exceptions/stream` (SSE, coalesced `update` ticks, §10).
- **UI.** Grouped list sorted by `lastSeen`: class, message, count, status chip, application/framework badge.
  Detail: frames with application frames highlighted, causes, last 25 occurrences linking to the request profile.
  Status buttons and Clear are disabled with `readOnlyReason` on a read-only panel. Empty state: "No exceptions
  captured. That is good news."
- **MCP.** `get_exceptions`, `get_exception_detail` (BootUI names and schemas). `clear_exceptions` exists upstream as
  an action tool; sharpit exposes it on `POST {api}/cli/tools/clear_exceptions` only, like `vulnerabilities_scan`.
- **Out of scope.** `sys.excepthook` / `threading.excepthook` (would change process-wide hooks), error-contract links,
  exceptions in WebSocket handlers.

### 7.3 SQL Trace (F3)

- **Purpose.** The recent SQL the app ran, with timings, slow and failed statements, and the statements that repeat.
- **Python source.** SQLAlchemy class-level listeners (§6.2, step 4b). `before_cursor_execute` stores the start time
  on `context._sharpit_t0` (falls back to `conn.info`, read back with `pop` so it never leaks into the next statement); `after_cursor_execute` and
  `handle_error` record. `executemany` → `batchSize` = number of parameter sets.
- **Recorded per statement.** SQL text (cut at `SHARPIT_SQL_TRACE_MAX_SQL_LENGTH`, 2 000), `statementType` and
  `category` as BootUI keeps them apart: `statementType` = `PREPARED` when parameters are bound, else `STATEMENT`;
  `category` = a verbatim port of `SqlTracingProxies.categoryOf` (`SELECT|WITH|SHOW|VALUES|TABLE` → `SELECT`,
  `UPDATE|MERGE|UPSERT` → `UPDATE`, `CREATE|ALTER|DROP|TRUNCATE|COMMENT|RENAME|GRANT|REVOKE` → `DDL`, and so on),
  duration, success, error message, `cursor.rowcount` when ≥ 0, connection id (`id(dbapi_connection)` as hex),
  thread name, slow flag (≥ `SLOW_QUERY_THRESHOLD_MILLIS`, 100; 0 disables), request id, call site.
- **Call site** (`SHARPIT_SQL_TRACE_CAPTURE_CALL_SITE`, default on, BootUI): the first application frame
  (§7.2 rule) from `sys._getframe()` walking at most 64 frames, as `module:function:line`. For `AsyncSession` the
  listener runs inside a greenlet spawned by SQLAlchemy whose frames hold only SQLAlchemy code; when the walk ends
  without an application frame and `greenlet.getcurrent().parent` exists (greenlet read from `sys.modules`), the walk
  continues from `parent.gr_frame` within the same 64-frame budget. An `aiosqlite` test asserts the call site is the
  app's function and that the request id crossed into the greenlet. No values, so not privacy-gated.
- **Bind values** (`SHARPIT_SQL_TRACE_CAPTURE_PARAMETERS`, default **off**, BootUI): when on, at most 5 parameter
  sets × 5 values, each value cut at `MAX_PARAMETER_LENGTH` (200). Dict parameters are masked by key **and** value;
  positional parameters have no name, so only the secret-value detector applies (documented on the panel).
  `METADATA_ONLY` suppresses parameters even when on.
- **Masking.** When parameter capture is off (the default) or exposure is `METADATA_ONLY`, the stored SQL text is the
  normalised form (literals → `?`, the normaliser below, which also handles `$$...$$` and `E'...'`), so inline
  literals such as `VALUES ('bob', 'hunter2')` never reach the buffer. When parameter capture is on, the raw text goes
  through `Masker.mask_text()` (catches `password = 'x'` literals and URL credentials). Error messages go through
  `mask_text`, which also drops SQLAlchemy's `[parameters: ...]` block unless parameter capture is on (§11): an
  `IntegrityError` text otherwise carries the bind values verbatim.
- **Buffer.** Ring buffer `SHARPIT_SQL_TRACE_MAX_ENTRIES` (200, BootUI). Aggregates for `topStatements` are a
  bounded dict keyed on the normalised statement (port of `SqlStatementNormalizer`: literals → `?`, `IN (?, ?, ?)` →
  `IN (?)`, whitespace folded), capped at 500 keys with least-recently-seen eviction. `stats.evicted` counts ring
  evictions. Sync endpoints run statements on several threads at once, so ring, aggregates and stats share one
  `threading.Lock` (as §7.1); the report is built from a snapshot taken under it.
- **Recording switch.** `SHARPIT_SQL_TRACE_RECORDING` (true) is the initial state; pause/resume at runtime does not
  remove the listeners (BootUI), it makes them return immediately. `SHARPIT_SQL_TRACE_ENABLED=false` attaches nothing.
- **JSON.** `GET {api}/sql-trace` → `SqlTraceReport {available, unavailableReason, capturing, captureParameters,
  bufferSize, totalCaptured, slowQueryThresholdMillis, dataSources, stats, entries, topStatements, warnings}` with
  `SqlTraceEntryDto`, `SqlTraceGroupDto {sql, category, executions, totalDurationMillis, maxDurationMillis,
  potentialNPlusOne, callSites}` and `SqlTraceStatsDto` exactly as BootUI. `dataSources` = engine display names.
  `potentialNPlusOne` = a `SELECT`-category group with ≥ `N_PLUS_ONE_THRESHOLD` (5) executions in the buffer.
  `GET {api}/sql-trace/insights`: deferred (§3), route answers 404 until built; the sharpit SQL Trace view has no
  rankings tab and never calls it (BootUI's `SqlTrace.vue` does, so the view is not a literal port).
- **Actions** (action-capable): `POST {api}/sql-trace/clear` → report; `POST {api}/sql-trace/recording` body
  `{"enabled": bool}` → report.
- **Stream.** `GET {api}/sql-trace/stream` (ticks).
- **UI.** Two tabs: Recent (time, type, duration bar, rows, call site, slow/failed badges, request link) and Top
  statements (normalised SQL, executions, total/max time, N+1 badge, call sites). Pause/Resume and Clear disabled on
  read-only. Empty states: SQLAlchemy not imported (with the reason); imported but no engine has run SQL yet;
  recording paused.
- **MCP.** `get_sql_traces` (BootUI name and schema). Clear, pause and resume are not MCP tools; like BootUI's action
  tools they are on the CLI endpoint only: `clear_sql_traces`, `pause_sql_trace_recording`,
  `resume_sql_trace_recording` (§13.3).
- **Out of scope.** Django/psycopg-direct tracing, EXPLAIN, transactions panel, `/insights` route rankings.

### 7.4 Live Activity, request profile, N+1 (F4)

- **Purpose.** One time-ordered feed of requests, SQL and exceptions, and a per-request view that answers "what did
  this request do?".
- **Source.** No new capture: a merge of F1, F2 and F3 at read time, correlated by request id (§9). No own buffer;
  the response is capped at `SHARPIT_ACTIVITY_MAX_ENTRIES` (200, BootUI). Activity only shows a source whose own panel
  is enabled: with `sql-trace` disabled there are no SQL rows and the profile's `sql`/`sqlGroups` are `[]`; with
  `exceptions` disabled no EXCEPTION rows; with `http-exchanges` disabled the REQUEST rows and the profile's `request`
  carry no headers (`requestHeaders`/`responseHeaders` `[]`). `sources` lists the active ones. Enabling `activity`
  alone never attaches the SQL statement listeners (§6.1 step 4b). Safety matrix row: disabled source panel × every
  activity route and `get_live_activity`.
- **JSON.** `GET {api}/activity?type&severity&since&limit&q` → `LiveActivityReport {available, entries, typeCounts,
  kpis, sources, warnings, pageInfo, persistenceOption}` with `pageInfo` and `persistenceOption` null (no persistence).
  `ActivityEntryDto` as BootUI; `type` ∈ `REQUEST`, `SQL`, `EXCEPTION` (BootUI spellings; sharpit has no other
  sources yet); `correlationId` = request id; `parentId` = the request's id on SQL and EXCEPTION rows;
  `sqlNPlusOneSuspected` on REQUEST rows; `profileable` true on REQUEST rows; `securedPrincipal` = F1 `principal`.
  Severities as BootUI's `LiveActivityAssembler`: `ERROR` for 5xx, failed SQL and exceptions, `WARN` for 4xx, `SLOW`
  for slow requests and slow SQL, else `OK` (the only four values `LiveActivity.vue` filters on). A missing `limit`,
  `limit=0` or a missing `since` means "server cap" (`SHARPIT_ACTIVITY_MAX_ENTRIES`), as BootUI. BootUI's `until`,
  `cursor` and `pageSize` belong to persistence and are not accepted (§17).
  `ActivityKpiDto`: `requestsPerMinute`, `errorRatePercent`, `p50LatencyMs`, `p95LatencyMs`, `slowestEndpoint`,
  `slowestEndpointMs`, `activeExceptionCount` (OPEN groups), `sqlPerMinute`, `slowestQueryMs`, `healthStatus` (last
  cached F8 status or null) are computed over the buffers; `heapUsedBytes`, `heapMaxBytes`, `cacheHitRatioPercent`,
  `restCallErrorRatePercent`, `restCallP95LatencyMs` are null and `scheduledTaskFailureCount` is 0 (no such source).
- **Request profile.** `GET {api}/activity/request/{id}` → `RequestProfileDto {available, unavailableReason,
  request, sql, sqlGroups, sqlCorrelationApproximate, exceptions, security, trace, timing, notes}`: `request` = the F1
  row, `sql` = that request's statements, `sqlGroups` = per-request normalised groups with `potentialNPlusOne` at
  ≥ `SHARPIT_ACTIVITY_N_PLUS_ONE_THRESHOLD` (5), `exceptions` = `RequestProfileExceptionDto` rows, `security` `[]`,
  `trace` null, `timing` = `{totalMs, sqlMs, sqlCount, sqlPercent}`. `sqlCorrelationApproximate` is true when any
  statement ran after the response finished (FastAPI `BackgroundTasks`), with a note saying so. A request already
  evicted from F1 → `available: false`, reason `"Request is no longer in the buffer"`.
- **N+1 rule.** Same normalised `SELECT` executed ≥ threshold times under one request id. Flags the REQUEST row and the
  group; the profile lists the group's call sites.
- **Stream.** `GET {api}/activity/stream`: one coalesced `update` tick when any of F1-F3 changes.
- **UI.** Feed with type and severity filters and a KPI strip; REQUEST rows open a profile drawer: timing bar (SQL vs
  rest), statements grouped with the N+1 group on top, exceptions. Slow requests (≥
  `SHARPIT_ACTIVITY_REQUEST_SLOW_THRESHOLD_MS`, 1 000) are marked. Empty state when no request has been captured;
  SQL rows simply absent without SQLAlchemy (the `sources` list says which sources are on).
- **MCP.** `get_live_activity` (BootUI name and `LIMIT` schema from `bootui-tools.json`): the same report as
  `GET {api}/activity`, read-only, with the same per-source panel gating.
- **Out of scope.** pyinstrument profiler, persistence (`use-existing-datasource`), service map, log rows in the feed.

### 7.5 Log Tail (F5)

- **Purpose.** The recent log lines and a live tail, without leaving the browser.
- **Source.** `SharpitLogHandler(logging.Handler)` attached per §6.1 step 3. Its level is `NOTSET`: it sees what the
  app's logger levels already let through and changes no level. It ignores records from the `sharpit` logger
  hierarchy and is re-entrancy guarded; `handleError` is a no-op, so a bad record never prints a traceback from
  sharpit. structlog and loguru reach it only if they forward to stdlib logging (documented).
- **Line.** `LogLineDto {timestamp, level, logger, message, thread}` (BootUI). `message` = `record.getMessage()`
  (formatting errors fall back to `str(record.msg)`), cut at 4 000 characters, through `Masker.mask_text()`.
  Tracebacks are not appended; they go to F2. When SQL parameter capture is off, records from the
  `sqlalchemy.engine` loggers that carry bind values (`echo=True` parameter lines) are dropped.
- **No feedback loop.** sharpit's stream callbacks catch their own errors (§10), so nothing they do produces a log
  record (for example asyncio's "Exception in callback") that the handler would capture and signal again.
- **Buffer.** `SHARPIT_LOG_TAIL_MAX_LINES` (500, BootUI's fixed cap) **and** `SHARPIT_LOG_TAIL_MAX_BYTES` (default
  1 MiB; BootUI's default is 0 = unbounded, which breaks the bounded-memory rule; §17). Oldest evicted first. Each line
  carries a monotonically increasing sequence number for SSE resume.
- **JSON / endpoints.** `GET {api}/log-tail/recent` → `LogLineDto[]` (oldest first, BootUI). `GET
  {api}/log-tail/stream` → SSE: replays the buffer (or only lines after `Last-Event-ID` or `?after=<id>`), then live
  lines; event name `log`, `id` = `<bootNonce>-<seq>` where `bootNonce` is random per process start, data = the JSON
  line. An id whose nonce does not match the current process (after a `--reload` restart, or another worker) replays
  the whole buffer instead of waiting for the sequence to catch up.
- **Stream limits:** 20 concurrent streams (BootUI's number; the 21st gets 503 `{"error":"Too many concurrent sharpit
  streams"}`, sharpit's own response: BootUI completes the emitter with an error instead, §17), per-client queue
  1 000 lines; a client that falls behind is disconnected. See §10 for stream lifetime.
- **Pause and resume.** The view keeps the last event id and reconnects with `?after=<lastId>` on a manual resume,
  and drops lines whose id it already has, so the buffer is not appended twice (BootUI's `LogTail.vue` does append it
  twice).
- **UI.** Monospace tail with level colours, level filter, logger filter, text search over the buffer, pause/follow,
  "copy visible". Not action-capable (BootUI view-only). Empty state: "No log lines yet" with a hint that only records
  that reach the root logger (or uvicorn's loggers) are shown.
- **MCP.** `get_log_tail` (BootUI name and schema).
- **Out of scope.** Reading log files, changing handlers or formats, multi-worker merge.

### 7.6 Migrations: Alembic, read-only (F6)

- **Purpose.** Which migration the database is on and which are pending, without running anything.
- **Decision: no Alembic import, no `env.py`.** `env.py` is arbitrary code and loading revision modules executes them
  (and writes `__pycache__`). sharpit reads the files the way the MVP's getenv scan does:
  1. The ini file: `install(app, alembic_config="...")` or `SHARPIT_ALEMBIC_CONFIG` (default `alembic.ini` in the
     working directory). Parsed with `configparser`; `script_location` and `version_locations` resolved with
     `%(here)s`. A `package:dir` script location is resolved **only** through modules already in `sys.modules` (the
     parent's `__path__`); `importlib.util.find_spec` is not used because it imports parent packages. A package that
     is not imported yet is reported as "unresolved" with a reason. Every ini error message passes through
     `mask_text` before it reaches `unavailableReason` (a `configparser` error can quote `sqlalchemy.url`). Projects
     made with `alembic init -t pyproject` keep `script_location` in `pyproject.toml [tool.alembic]`; that is read
     with `tomllib` when no ini is found.
  2. Each `versions/*.py` file parsed with `ast` (files over 1 MB skipped): module-level `revision`, `down_revision`
     (str, tuple or None), `branch_labels`, `depends_on`, from `Assign` **or** `AnnAssign` nodes (the default
     template since Alembic 1.12 writes `revision: str = "abc"`), values via `ast.literal_eval`, and the docstring's
     first line as description (through `mask_text`). A fixture in the modern template is tested. The graph gives
     heads, branch points and order.
  3. The database side: `SELECT version_num FROM <version_table>` per registered engine (§6.2). This connects, so it
     runs **only** on `POST {api}/alembic/refresh`. The result is cached with its time. An engine without the table is
     reported as "not managed by Alembic". `version_table` and `version_table_schema` from the ini must match
     `[A-Za-z_][A-Za-z0-9_]{0,62}` (else the database read is refused with a reason) and are quoted with the
     dialect's `identifier_preparer`. The read follows §6.2 "Async engines", in its own worker thread for sync
     engines, with both a connect timeout and a statement timeout of `SHARPIT_ALEMBIC_TIMEOUT`; single-flight is held
     until the read actually returns.
- **JSON** (modelled on `FlywayReport`; new keys logged in §17). `GET {api}/alembic/migrations` →
  `{alembicPresent, configPath, total, heads, databases: AlembicDatabaseDto[]}`.
  `AlembicDatabaseDto` = BootUI `FlywayDatabaseDto` keys `{name, currentVersion, applied, pending, total, migrations,
  migrateEnabled, migrateDisabledReason, cleanEnabled, cleanDisabledReason}` + `checkedAt`. `migrateEnabled` and
  `cleanEnabled` are always false, reason `"sharpit never runs migrations"`. `currentVersion` = the database's heads
  joined with `,`, null before the first refresh. Migration rows keep `FlywayMigrationDto` keys: `type` `"PYTHON"`,
  `version` = revision id, `description`, `script` (path relative to the ini), `state` in BootUI's display-name
  casing: `"Success"` (applied), `"Pending"`, `"Unknown"` (database not read yet) or `"Missing"` (in the database,
  not in the files), `installedBy`, `installedOn`, `installedRank`, `executionTime`, `checksum` all null (Alembic does
  not record them). Oldest first, as Flyway's `info().all()`.
  With no database read yet, `databases` holds one entry named `"(not read yet)"` so the file-side history still shows.
- **Endpoints.** GET above; `POST {api}/alembic/refresh` (action-capable, single-flight, 5 s connect and statement
  timeout via `SHARPIT_ALEMBIC_TIMEOUT`).
- **UI.** Per database: current version, applied/pending counts, a linear history (branches shown as a short tree),
  pending rows highlighted, "Read database version" button (disabled on read-only, with reason). Empty states: no
  `alembic.ini` found (shows the setting); found but no engine registered (shows the `engines=` snippet); never read.
- **MCP.** `get_alembic_migrations` (schema NONE): file-side history plus the cached database read; never connects.
  BootUI's `get_flyway_migrations` is not reused because the shape differs.
- **Out of scope.** `upgrade`, `downgrade`, `stamp`, multiple ini files, Django migrations, autogenerate diffs.

### 7.7 Database connection pools (F7)

- **Purpose.** Is the pool exhausted? How many connections are checked out right now?
- **Source.** For each registered engine, `engine.pool` (for `AsyncEngine`, `engine.sync_engine.pool`). `QueuePool`
  and `AsyncAdaptedQueuePool`: `size()`, `checkedin()`, `checkedout()`, `overflow()`, `_max_overflow`, `_timeout`,
  `_recycle`, `_pre_ping`. These read counters only; nothing borrows a connection. `NullPool`, `StaticPool`,
  `SingletonThreadPool`: `available: false`, reason `"<PoolClass> keeps no pool statistics"`.
- **JSON.** `GET {api}/database-connection-pools/pools` → `HikariPoolsReport {hikariPresent, total, pools}` (keys kept;
  `hikariPresent` = SQLAlchemy imported). `HikariPoolDto`: `beanName` = `poolName` = engine display name (unique,
  §6.2; BootUI's snapshot lookup and `DatabaseConnectionPools.vue` key on `poolName`, so two `QueuePool`s must not
  share it), `jdbcUrl` = the engine display name (no userinfo, **no query string**: drivers put secrets there, e.g.
  `odbc_connect=...;PWD=...`), `username` = URL user name through the masker, `driverClassName` =
  `dialect+driver (<PoolClass>)`,
  `minimumIdle` null, `maximumPoolSize` = size + max_overflow (null when overflow is unlimited), `connectionTimeoutMs`
  = pool timeout, `idleTimeoutMs` null, `maxLifetimeMs` = `pool_recycle` (null when -1), `validationTimeoutMs` null,
  `keepaliveTimeMs` null, `readOnly` false, `autoCommit` = engine isolation level is `AUTOCOMMIT`, `available`,
  `unavailableReason`, `snapshot`. `HikariPoolSnapshotDto {timestamp, active = checkedout, idle = checkedin, total =
  checkedin + checkedout, pending = null}` (SQLAlchemy exposes no waiter count; §17).
  `GET {api}/database-connection-pools/pools/{name}/snapshot` → snapshot; unknown name → 404.
- **Buffer.** None; the UI keeps the last 60 polled snapshots per pool in memory for a sparkline.
- **UI.** One card per pool: active/idle/max gauge, overflow in use, settings; polls the snapshot every 2 s while
  visible. Not action-capable (BootUI view-only). Empty states as §6.2.
- **MCP.** `get_database_connection_pools` (BootUI name and schema).
- **Out of scope.** psycopg_pool, asyncpg pools, Django connections.

### 7.8 Health (F8)

- **Purpose.** Is the app and what it depends on up? Unavailable is kept apart from unhealthy (BootUI).
- **Sources.** (a) one `db` component with a child per registered engine; (b) user checks passed as
  `install(app, health_checks={"name": callable})`. A callable takes no arguments and returns `True`/`False`, a
  status string, or a dict (`{"status": "UP", ...details}`); raising means `DOWN` with the masked exception class and
  message. Sync or async is decided by the **result**, not the function kind: the callable is called in a worker
  thread, and a result that is awaitable is awaited on the loop under the same timeout (this covers objects with an
  async `__call__` and sync wrappers that return a coroutine).
- **When checks run.** **Only on `POST {api}/health/check`** (action-capable, single-flight). Each check has a
  deadline of `SHARPIT_HEALTH_TIMEOUT` (default 5 s). Python cannot stop a thread, so the deadline is a wait limit,
  not a cancellation: a timed-out check is reported `DOWN` with `"timed out after 5s; still running"`, and the
  single-flight stays held until every worker thread has actually returned (a new POST meanwhile gets the contract's
  409). Sync work runs on sharpit's own small executor (2 threads, created lazily on the first check), never on
  anyio's default limiter that the host's `def` endpoints share. Engine checks use the dialect's own ping
  (`connection.dialect.do_ping(dbapi_connection)`, the mechanism behind `pool_pre_ping`, which also works on Oracle)
  on a pooled connection with the internal marker (§9), following §6.2 "Async engines"; they are not traced. GET
  returns the last results with `details.checkedAt`; before the first run every component is `UNKNOWN`. Reason: a GET
  must not open a socket or run user code (MVP rule); BootUI's health GET runs Spring's indicators, which is the
  deviation logged in §17.
- **Opening the panel runs the checks.** When the Health panel is writable, the UI sends `POST {api}/health/check`
  once when the panel opens and on each auto-refresh tick, so the developer does not face a page of `UNKNOWN`. This is
  still a guarded POST from the UI and runs user callables: it is not a GET, and a read-only panel only shows the
  cache. MCP `get_health` never runs checks; when nothing has run yet the root carries `guidanceReason` `"Never
  checked; open the Health panel"`.
- **JSON.** `HealthNodeDto` exactly as contract §7. Root `name` `"application"`; status aggregation as Spring's
  default order (`DOWN` > `OUT_OF_SERVICE` > `UP` > `UNKNOWN`). Engine `details`: `{"database": "<dialect>",
  "validationQuery": "dialect ping", "checkedAt": ms}`; errors in `details.error`. Details are masked recursively:
  keys through `is_sensitive_key`, every string value through `mask_text` (so a DSN inside a driver's error message
  is caught), nested dicts and lists walked, any other value becomes `mask_text(repr(v))` cut at 1 000 characters.
  No engines and no checks → `{status: "DISABLED", available: false,
  unavailableReason, setup: [steps with the `engines=` and `health_checks=` snippets]}`. Only engine checks →
  `guidanceReason` and `setup` nudging the user to add checks (BootUI).
- **UI.** Tree with status chips; "Run checks" button (disabled on read-only); last run time. Empty state shows the setup
  steps.
- **MCP.** `get_health` (BootUI name and schema): the cached tree, never runs checks.
- **Out of scope.** Liveness/readiness groups, an HTTP health endpoint for orchestrators, cache/broker pings.

### 7.9 Threads and asyncio tasks (F9)

- **Purpose.** "What is this process doing right now?" For a FastAPI developer the real question is often "which
  coroutine is stuck", so tasks matter as much as threads.
- **Source.** `threading.enumerate()` + `sys._current_frames()` (stack per thread, at most
  `SHARPIT_THREADS_MAX_STACK_FRAMES`, 64). `asyncio.all_tasks(loop)` on the app's loop, whose reference is captured
  at lifespan startup or the first request (`asyncio.get_running_loop()`, never `get_event_loop()`). When the reader
  is not on that loop (an MCP call from a worker thread), the task list is collected on the loop through
  `run_coroutine_threadsafe`; with no known loop, `tasks` is `[]` with a warning. Task stacks are **not** taken from
  `Task.get_stack()`, which returns a single frame for a suspended coroutine: sharpit walks `coro.cr_await` (and
  `gi_yieldfrom`, `ag_await`) down the await chain, collecting each frame, innermost first, capped at the frame limit;
  on Python 3.14+ it uses `asyncio.capture_call_graph(task)`. A test has a task stuck in a nested
  `await asyncio.sleep`. Also read: `get_name()`, `getattr(task.get_coro(), "__qualname__", None)` (an eager task's coroutine can be
  None), the state (`CANCELLED` when `cancelled()`, checked first since `done()` is also true then, else `DONE` or
  `PENDING`), and the task's
  §9 `REQUEST` value via `task.get_context()`. Only the current worker process and its loop are visible.
- **States.** Python has no thread state. sharpit infers it from the stack: `WAITING` when the innermost
  `threading`, `queue`, `selectors` or `concurrent.futures` frame is a known blocking wait (`threading.Condition.wait`,
  `threading.Event.wait`, `queue.Queue.get`, `selectors.*.select`, `concurrent.futures` worker idle), else `RUNNABLE`.
  C-level waits with no Python frame of their own (`time.sleep`, `socket.recv`) read as `RUNNABLE`; the panel help
  says so. The inference list is a module constant with tests.
- **JSON.** `GET {api}/threads?q&state&offset&limit` → `ThreadDumpReport` keys as BootUI; `state` is an exact match on
  the inferred state (BootUI `ThreadDumpController`, used by the state-count chips). `id` = `thread.ident`, `priority`
  0, `virtual` false, `cpuTimeMillis`/`userTimeMillis` null, `blockedCount`/`waitedCount` 0, `inNative` false,
  `suspended` false, `deadlocked` false, lock fields null, `stackTrace` = `"module.function (file:line)"` strings,
  innermost first. `peakThreads`, `startedThreadCount` = current count (no history), `virtualThreadsSupported` false,
  `cpuTimeSupported` false, `deadlockDetected` false. **Added keys** (§17): `tasks: AsyncTaskDto[]` and `taskCount`,
  with `AsyncTaskDto {name, coroutine, state ("PENDING"|"DONE"|"CANCELLED"), stackTrace, request}`, where `request`
  = `{method, path, ageMs}` (masked path) for a task running inside a captured request, else null; capped at 500 tasks; sharpit's
  own SSE tasks are excluded. No locals, no argument values, ever.
- **Endpoints.** GET only. BootUI's `POST /threads/download` (thread dump file) is dropped; the panel is not
  action-capable (§17).
- **UI.** Two tabs, Threads and Tasks: state counts, filter, expandable stacks with application frames highlighted,
  "copy as text". Refresh button (a GET).
- **MCP.** `get_threads` (BootUI name and schema, `state` included; the added `tasks` key included, capped by
  `limit`).
- **Out of scope.** Event-loop lag measurement, `faulthandler` dumps, other worker processes.

### 7.10 REST API advisor (F10)

- **Purpose.** A zero-config review of the app's HTTP API design, ranked by severity, with no network and no requests
  sent.
- **Source.** The route tree the mappings collector already walks (`APIRoute`: methods, path, endpoint, `status_code`,
  `response_model`, `responses`, body field, query params) plus `app.exception_handlers`. sharpit does **not** call
  `app.openapi()`: it builds and caches a schema on the app object and can raise on broken models.
- **Scan.** `POST {api}/rest-api/scan` (single-flight, operation `rest-api-scan`); GET returns the last report or a
  `NOT_SCANNED` report. Pure introspection, but explicit like every BootUI advisor.
- **Rules ported** (ids and names from `docs/REST-API-CHECKS.md`, adapted wording, severities as BootUI):
  `RAPI-MAP-001` (one route answering GET and a mutating method), `MAP-002` (duplicate method + path: Starlette serves
  the first, the second is dead), `MAP-003` (mutation-like function name on GET), `MAP-005` (trailing/doubled
  slashes), `MAP-007` (request body on GET/HEAD/DELETE), `MAP-010` (catch-all `{x:path}` route), `MAP-011` (deeply
  nested path), `NAME-001` (verbs in paths), `NAME-002` (singular collection names), `NAME-003` (lowercase

### 7.11 HTTP Probe (F12)

- **Purpose.** Send one request to your own app from the console and see the status, headers, timing and body.
- **Decision: hand-rolled in-process ASGI call, no httpx.** httpx is not a runtime dependency, and a hand-rolled call
  (about 60 lines) cannot open a socket by construction. `engine/probe.py` builds an `http` scope, feeds one
  `http.request` message with the body, collects `http.response.start`/`body` messages, and awaits the **host app
  object** (so the request goes through the host's middleware, like a real call).
- **Scope.** `client` = the **caller's** `client` from the current sharpit request (the probe never gains loopback
  trust its caller did not already have; a remote token holder stays remote to the host app), `server` = the current
  request's server, `root_path` = the **host-level** root path (the incoming `root_path` minus sharpit's own mount
  prefix, computed with the §6.1 route-path helper), `scheme` `http`, `http_version` `"1.1"`, `state` = a shallow
  copy of the incoming scope's `state` (lifespan state, so `request.state.db` works), `path` decoded, `raw_path`
  kept, the part after `?` in `query_string`, `asgi` `{"version": "3.0", "spec_version": "2.4"}`. Headers: the
  user's headers after validation, plus `host` = the current sharpit request's `Host` value (so
  `TrustedHostMiddleware` and `url_for` work; tested), plus `x-sharpit-probe: 1` so the probe is visible in F1.
  A real request that carries `x-sharpit-probe` has it removed by `CaptureMiddleware`, so only the probe shows as
  one. The scope is tagged `scope["extensions"]["sharpit.probe"] = True`.
- **Never reaches sharpit.** The sharpit guard refuses every request whose scope carries the `sharpit.probe` tag with
  403, before any other rule. This holds whatever path rewriting, `root_path`, percent-encoding (`%2F`, `%73harpit`)
  or doubled slashes do to the path. As an early 400 for usability, a path whose decoded and normalised form is under
  `settings.path` is refused with `{"error":"HTTP Probe cannot target sharpit itself"}`. Tests: a `--root-path /app`
  case, a `%2F` case and a `//sharpit` case all end in 400 or 403, never 200.
- **Receive.** The first `receive()` returns the `http.request` with the body; a second one waits on an event that is
  set when the probe finishes or times out, then returns `http.disconnect` (an immediate disconnect would cancel a
  `StreamingResponse` on older Starlette).
- **Validation** (BootUI `HttpProbeLimits`, messages verbatim with `HTTP Probe`): method ≤ 32 bytes and one of
  `GET HEAD POST PUT PATCH DELETE OPTIONS`; path ≤ 2 048 bytes, must start with `/`, no scheme or host, no `..`
  segments; body ≤ 64 KiB; ≤ 50 headers, name ≤ 256 B, value ≤ 8 KiB, total ≤ 32 KiB; header names must be RFC 7230
  tokens (lowercased) and values must not contain `\r`, `\n` or `\0` (400 in BootUI's wording); BootUI's
  `RESTRICTED_HEADERS` (`host, connection, content-length, expect, upgrade, transfer-encoding, proxy-connection,
  keep-alive, te`) stripped. The request body for the endpoint itself is capped by the MVP's per-endpoint 413 rule.
- **Concurrency.** At most 4 probes run at once; a 5th gets the contract's 409. A probe that times out keeps its slot
  until the host app task has actually ended (it is cancelled; a sync endpoint's worker thread cannot be stopped, so
  the slot is held until that thread returns).
- **Response.** `HttpProbeResponse {status, statusText, headers, body, durationMs, error, truncated}`. Body read up to
  1 MiB (BootUI), then the app task is cancelled and `truncated` is true; decoded as UTF-8 with replacement, binary
  bodies shown as `"<N bytes, content-type>"`. Total timeout 10 s (BootUI) → `error: "HTTP Probe timed out after 10s"`.
  An exception from the app → `status` 500, `error` = masked class and message (also captured by F2). `headers` is a
  map, as BootUI's `Map<String,String>`, holding only BootUI's allow-list (`HttpProbeService.filterHeaders`):
  `content-type`, `content-length` and `location`, lower-cased, repeated values joined with `", "`. Every other
  response header (`Set-Cookie` included) is dropped. `location` passes through `mask_text` (a redirect can carry a
  token in its query) and is cut at 8 KiB. **The text body passes through `mask_text`** (every captured value is masked, §4): it replaces only the
  value side of sensitive `"key": "value"` pairs and flagged tokens, so a JSON body stays valid JSON. `FULL` exposure
  returns it unchanged (MVP warning). Tested with a JSON body and a text body that carry a password and a token.
- **Endpoints.** `POST {api}/http-probe` (action-capable; refused on read-only; 409 when 4 probes are running).
- **UI.** Method selector, path input with route suggestions from `mappings`, headers editor, body editor, response
  view with status, timing, headers and a pretty-printed body. Request history kept in `sessionStorage` (paths and
  methods only, never headers).
- **MCP.** None (BootUI has none; sending requests is an action).
- **Out of scope.** Streaming responses beyond the cap, WebSocket probes, probing other hosts, auth helpers.

## 8. Shared advisor plumbing (F11)

What every advisor (REST API now, vulnerabilities retrofitted, the "Later" advisors next) shares:

- **Rule model.** `RuleDefinition {id, name, category, severity, description, recommendation, learnMoreUrl}`;
  severities `CRITICAL, HIGH, MEDIUM, LOW, INFO` in that order; `RuleResult` adds `status` (`PASSED`, `FAILED`,
  `SKIPPED`), `violationCount`, `sampleViolations` (first 10), `dismissed`.
- **Report helpers.** One function builds `severityCounts` (every severity, zero included), `violationsFound`,
  `evidence` (`AdvisorEvidenceDto`, limitations sanitised: control characters → space, ≤ 240 chars, ≤ 20 items, as the
  BootUI record does) and `violationDetails`.
- **Dismissals, generalised.** `DismissalStore` moves to `engine/advisors/dismissals.py`; the file format and atomic
  write are unchanged. The rule id check becomes `[A-Za-z0-9._:-]{1,200}` (covers `RAPI-MAP-001` and the vulnerability
  ids `<vulnId>::pypi:<name>`), still refusing quotes, spaces, newlines and slashes before the file is touched. The
  existing `{api}/dismissed-rules` routes serve every advisor. Today they check only the **global** read-only flag
  (`_GLOBAL_WRITE_SUBJECTS` in `guard.py`); 0.2.0 adds the owning panel's gate: the route works out the panel from the
  rule id (`RAPI-` → `rest-api`, `::pypi:` → `vulnerabilities`) and applies that panel's enabled and read-only checks
  (contract 403). An id that matches no registered rule gets a 400. Safety matrix row: per-panel read-only ×
  dismiss/restore. Applying dismissals sets
  `dismissed` and recomputes `violationsFound`, `severityCounts` and `scan.violationsFound` from active rules only
  (BootUI). Dismissing never rescans.
- **Violation retention.** Each completed scan gets an opaque `scanId` (`secrets.token_hex(8)`) and keeps every
  violation string up to `SHARPIT_ADVISORS_MAX_RETAINED_VIOLATIONS` (BootUI default 10 000) per advisor; only the
  latest scan is kept. `GET {api}/<advisor>/rules/{ruleId}/violations?scanId&offset&limit` → `AdvisorRuleViolationsDto
  {scanId, ruleId, violationCount, retainedCount, truncated, violations, page}`; `limit` default 100, max
  `min(1000, max-results)`. Errors are BootUI's `AdvisorViolationException` texts and codes (400 for blank or bad
  input, 404 `"Advisor rule has no findings in the current scan."`, a stale `scanId` as BootUI). Never scans.
- **Single-flight.** The MVP's `SingleFlight` with one operation name per advisor; a busy scan → the contract's 409.
- **Score.** BootUI computes the score in the browser (`scannerScore.js`: 100 minus CRITICAL 25, HIGH 10, MEDIUM 3,
  LOW 1, INFO 0 per active finding, floored at 0; eligibility rules from `advisorAssessment`). sharpit ports that file
  to `ui/src/lib/score.ts` with its cases as vitest tests, and shows it on REST API and Vulnerabilities. No `score`
  key in JSON (§16 row 14).
- **UI.** One `AdvisorPanel.svelte` used by REST API and, after a refactor that keeps its tests green,
  Vulnerabilities: score ring, severity counts, rule list, sample violations, paged "View violations", dismiss/restore,
  "Show dismissed" toggle, scan button with busy/failed states.

## 9. Request correlation (contextvars)

- `engine/capture/correlation.py` holds `REQUEST: ContextVar[RequestInfo | None]` with `RequestInfo {id, context_id,
  method, path (masked), endpoint, started_ns, finished_ns}` (`context_id` = the installed sharpit context, §6.2), and
  `INTERNAL: ContextVar[bool]`.
- `CaptureMiddleware` sets `REQUEST` at entry with a fresh id (`secrets.token_hex(8)`) and resets it with the token
  in `finally`. It fills `endpoint` from `scope["endpoint"]` after the app returns (Starlette sets it during routing).
- Reached: async endpoints and dependencies (same task); sync `def` endpoints and dependencies (Starlette runs them in
  the thread pool through anyio, which copies the context; **tested, not assumed**, against the minimum and the latest
  Starlette); `BackgroundTasks` (they run inside the request's context after the response; their SQL carries the id and
  is marked approximate, §7.4); tasks created with `asyncio.create_task` inside the request (they copy the context).
- Not reached: work handed to threads the app starts itself, process pools, other workers. Those rows have no request
  id and appear in the feed without a parent.
- `INTERNAL` is set by sharpit around its own database work (health, Alembic refresh); the SQL listener skips such
  statements.
- No id is set for sharpit's own paths, and none at all when sharpit is inactive (no middleware).

## 10. Live streams (SSE)

- One small helper, `engine/capture/streams.py`: `ChangeStream` (coalesced `update` ticks, at most 4 per second) for
  activity, exceptions and SQL trace; `LineStream` for log tail. Producers call `signal()` from any thread.
- **Bounded hand-off.** Each subscriber has a "dirty" flag. `signal()` only sets it, and schedules one callback with
  `call_soon_threadsafe` on the clean → dirty transition, so at most one callback per subscriber is ever pending in
  the loop's ready queue, and an N+1 route with 100 statements costs at most one wake-up per subscriber. The callback
  is a sharpit function that drains into the bounded subscriber queue and catches its own errors: `QueueFull` marks
  the subscriber for disconnect (a client that falls behind is dropped, §7.5) and logs nothing. A `RuntimeError` from
  `call_soon_threadsafe` on a closed loop (a subscriber whose loop ended) drops that subscriber in the producer. The
  ≤ 4/s tick timer is a `call_later` on the loop, no thread. A test with a subscriber that never reads asserts the
  log buffer's line count stays flat.
- Routes live under their panel's API prefix (`{api}/activity/stream` ...), so the guard and the panel-enabled gate
  apply. They are GETs and read-only panels still stream. SSE handlers unsubscribe and decrement the global stream
  counter in `finally` (a client disconnect arrives as `CancelledError`), so dropped tabs never leave a permanent 503.
- **Lifetime.** Each stream ends after `SHARPIT_STREAM_MAX_SECONDS` (default 3 s) with a `retry: 1000` hint; the
  browser's `EventSource` reconnects, and log tail resumes from `Last-Event-ID`. A non-200 answer (the 503 at the
  stream cap, a 403 after a session expiry) leaves `EventSource` `CLOSED` with no browser retry, so the UI helper
  then opens a new `EventSource` itself after a backoff (1 s doubling to 30 s) and shows the error meanwhile. Reason: uvicorn sends
  `lifespan.shutdown` only after open responses have drained, so lifespan cannot close streams, and an endless stream
  would hold `--reload` hostage; a short lifetime bounds that wait to about 3 s. The short lifetime also ends streams
  to dead clients, so no heartbeat is needed. A test against a real `uvicorn.Server` with an open stream asserts
  shutdown finishes within the lifetime + 1 s.
- **Rotation in the UI.** The shared SSE helper treats a server close as a planned rotation: it reconnects at once,
  keeps showing "connected" while `readyState` is `CONNECTING`, and reloads the panel after reopening so a tick in the
  gap is not lost. BootUI's helper shows "reconnecting"/"Disconnected" on every close; that would flicker every 3 s.
- **Only the visible panel streams.** Browsers allow 6 HTTP/1.1 connections per origin and sharpit shares the app's
  origin, so the UI opens a stream only for the panel on screen and closes it on `visibilitychange` to hidden.
- Total concurrent streams across all panels: 20 (BootUI's log-tail limit, applied globally).
- `EventSource` cannot send an `Authorization` header: remote users authenticate through the session cookie
  (`POST {api}/auth/session`), whose path already covers the API. Loopback users need nothing (MVP guard). A
  generated token is per process, so with `--workers N` remote users need a configured `SHARPIT_AUTHENTICATION_TOKEN` (documented;
  one startup warning when the process can tell it is one of several workers).
- Capture is per process. With several workers, each request, stream and POST reaches one worker's buffers; the
  docs say so.
- Responses carry the API cache headers plus `X-Accel-Buffering: no`.

## 11. Masking additions

- `Masker.mask_text(text)` (new): applies the URL-userinfo rule, then masks the value side of `key=value`, `key: value`
  and `"key": "value"` pairs whose key is sensitive, then any whitespace-delimited token the secret-value detector
  flags (surrounding quotes and punctuation are stripped before the test and kept around the placeholder, so JSON
  stays valid). Unless SQL parameter capture is on and exposure is not `METADATA_ONLY`, it also drops SQLAlchemy's
  `[parameters: ...]` block (the `StatementError` format) and replaces it with `[parameters: ******]`.
  `METADATA_ONLY` → `null`; `FULL` → unchanged (with the MVP warning). sharpit's own token is always masked.
  Its test corpus extends `tests/test_masking_corpus.py` and is asserted across F1-F5, F8, F12 outputs, API, MCP and
  CLI.
- `Masker.mask_path(path)` (new): replaces each path segment that `is_secret_value` flags with `******` (§7.1).
- `Masker.mask_header(name, values)` for F1 (F12 returns only allow-listed headers, §7.11).
- Masking runs at capture time (so the buffers never hold raw secrets), except SQL bind values, which are masked when
  captured as well. A change of exposure at runtime is not possible (settings are frozen), so nothing needs re-masking.

  still parses; a `package:dir` whose package `__init__` raises and is not yet imported reports "unresolved" and is
  not imported); `alembic` is not imported; a hostile `version_table` is refused.
- **Probe**: a socket-blocking fixture proves no socket opens; the self-target refusal and the guard's probe-tag 403
  (`--root-path`, `%2F`, `//` cases); the caller's `client` is copied; `Host` reaches `TrustedHostMiddleware`;
  lifespan `state` is visible; truncation and timeout with a streaming endpoint; the 5th concurrent probe gets 409;
  the probe row appears in F1.
- **Async engines**: health and Alembic reads succeed on an `aiosqlite` engine; a timed-out sync health check keeps
  the single-flight held until its thread returns.
- **Overhead**: per-request overhead with all panels on, measured as the minimum of 5 batches of 2 000 requests to a
  bare route, against the same app with capture off; it must stay under both a relative bound and 0.2 ms absolute
  (§4). A second budget: ≤ 50 µs median per statement on a 100-query route (masking, normaliser, frame walk).

### 14.2 Safety and side effects

- **Inactive adds nothing**: after an inactive `install()`, `app.user_middleware` is unchanged, no handler on root or
  any logger, `sqlalchemy.event.contains(Engine, ...)` false for every event, `app.exception_handlers` identical
  objects, the request contextvar never set. Same for an active install with every capture panel disabled.
- **Shutdown cleans up**: after lifespan shutdown, handlers and listeners are gone; streams end within their
  lifetime (tested against a real `uvicorn.Server`, §10).
- **Console unchanged**: an unconfigured app still prints its warnings to stderr while sharpit is active (§6.1).
- **Several apps**: two apps in one process each see only the SQL of their own requests (§6.2).
- **No side effects on GET** (the MVP `no_side_effects` fixture extended): every new GET and every new MCP tool runs with
  sockets blocked, no database connection checkout (a pool listener spy), no file write, no user health callable
  invoked, no logger level change.
- **Read-only**: every new POST/DELETE is refused under global and per-panel read-only with the contract 403.
- **Masking corpus**: secrets in a URL path segment, a query string, an `Authorization` header, a log message, an
  exception message, an SQL literal (incl. positional `VALUES`, `$$...$$`, `E'...'`), a bind value (when capture is
  on), an `IntegrityError` message with `[parameters: ...]`, an `echo=True` parameter log line, a health detail (nested
  dict, and a driver error carrying a DSN), an Alembic ini error, a probe `Set-Cookie` (dropped), a probe `Location` with a token and a probe JSON and text body
  are masked in API, MCP and CLI outputs, and in the raw buffers.
- **Bounded memory**: each buffer filled past its cap stays at its cap (lines, bytes, groups, occurrences, keys).
- **Hook failure**: a capture hook forced to raise leaves the host response unchanged and logs one warning.
- Safety matrix: every new route × every guard row (source, Host, cross-site, token, panel disabled, read-only), plus
  the probe-tag row, dismissals × per-panel read-only, and disabled source panel × activity routes and
  `get_live_activity`.

### 14.3 UI

- **vitest**: one unit file per new view helper (`score.ts` with `scannerScore.js` cases, SSE reconnect logic, status
  family colours, stack-frame highlighting) and component tests for each new panel's empty, loading, error and
  read-only states.
- **Playwright** against the dogfood sample app (§15), with the production build under sharpit's CSP: each new panel
  loads; HTTP Exchanges shows a request made by the test; an exception route appears in Exceptions and opens its
  detail; SQL Trace shows the N+1 route flagged; Live Activity opens a request profile with the N+1 group; Log Tail
  receives a live line within 2 s; Alembic shows one pending revision after "Read database version"; Health runs
  checks; Threads shows the event-loop task tab; REST API scan shows findings, dismiss and restore change the score;
  HTTP Probe returns 200 for `/owners` and refuses `/sharpit/api/panels`. axe checks on every new panel, light and dark.
- A grep test fails the build on `{@html` in any view that renders captured values (§7).
- The built bundle is committed to `src/sharpit/ui/static/` and the CI drift job stays green.
