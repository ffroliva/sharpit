# G1G2 red audit (2026-11-02)

Eleven G1G2 tests were merged into release/0.4.0 with a ruling, because the lane gate saw no valid red for them: at
their red commits they failed with `TypeError`/`AttributeError` from crash stubs, or passed
(`.superpowers/sdd/0.4.0/logs/G1G2-crash-reds.txt` in the integration worktree). Nobody had seen them catch the defect
they name.

**Method.** On the current code (branch `fix/0.4.0-g1g2-red-audit`, from release/0.4.0 at `34f1689`), for each test:
apply the smallest wrong-value mutation of the production code it guards (never a raise or an import break), run the
single test (`pytest -q -p no:cacheprovider -p no:randomly`), require an `AssertionError` raised in the test file,
revert with `git checkout -- <file>`, and confirm the test passes again. Every revert run passed. Where a faithful
mutation left the test green, a new test was added (nothing weakened) and run against the same mutation.

## Review round: the exclusions repeated in `compare()`

vulnerability exclusion and that both functions fold the advisor name with `.lower()`. Each of these mutations was run
against the whole suite except `tests/scripts` (`pytest -n auto`, 4079 tests). **No test caught any of them.** The only
failures were the two overhead-budget tests, which also fail on the unmutated tree on this busy machine:

## Verdict

What was proven: 10 of the 11 tests fail, with an `AssertionError` raised in their own file, under a wrong-value
mutation of the behaviour they name. The eleventh (`test_vulnerability_findings_excluded_from_baseline`) failed only
when both of its exclusions were removed. Two new tests now cover one half each (`3e57653`).

What was not proven: that the code next to these tests is guarded. The same exclusions in `compare()`, and the case
folding in both functions, survived every test in the suite until `4d99d5b`. The audit found no production defect, but
"the merged behaviour is guarded" holds only for the mutations listed here. The merge-with-ruling was not safe in
process: the gate's refusal was right, and only a mutation run shows whether a test works.
`scripts/dev/red_check.py` runs the gate's red classification on the worker's side, before each `test:` commit.
