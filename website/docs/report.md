# Test report

When running `pytest --sharpit`, sharpit writes a consolidated machine-readable JSON report and optional JUnit XML.
The JSON report follows the published schema `sharpit-report/1`.

The formal JSON Schema definition is available in the repository at
[`docs/reference/report.schema.json`](https://github.com/ffroliva/sharpit/blob/main/docs/reference/report.schema.json).

## The `sharpit-report/1` schema

The report emits all contract keys (including nulls) in `camelCase`, with epoch millisecond timestamps and no outer envelope.

### Schema fields

- `schema`: Schema identifier string, e.g. `"sharpit-report/1"`.
- `tool`: Object with tool metadata (`name` and `version`).
- `generatedAt`: Generation timestamp in epoch milliseconds.
- `status`: Overall session outcome: `"pass"`, `"fail"`, or `"unknown"`.
- `statusReasons`: Array of human-readable strings explaining why the session failed or was unknown.
- `warnings`: Array of masked warning messages (such as settings fallbacks or source limitations).
- `gates`: The configured thresholds for count gates and advisor severity.
- `sources`: List of capture sources (`sqlalchemy`, `sqlite3`, `exceptions`) with attachment status and limitations.
- `workers`: Worker status list for parallel execution (e.g. `gw0`, `gw1`).
- `severityCounts`: Finding counts grouped by severity in standard order (`CRITICAL`, `HIGH`, `MEDIUM`, `LOW`, `INFO`).
- `totals`: Aggregated counts of tests, queries, filtered queries, unattributed queries, unattributed share percentage, and exceptions.
- `tests`: Array of per-test records detailing nodeId, worker, attempt, outcome, query counts across `setup`, `call`, and `teardown` phases, detected N+1 queries, and finding fingerprints.
- `unattributed`: Summary of queries not linked to a specific test and their top normalized SQL statements.
- `filtered`: Count of queries filtered from gating and the active filter rules.
- `advisors`: Results from offline advisor scans per application snapshot.
- `findings`: Flat list of all findings generated by count gates and advisors.

## Schema versioning

The `schema` string is versioned as `sharpit-report/<major>`.

- **Minor changes within `/1`**: Adding new fields or keys is backwards-compatible. Consumers must ignore unknown properties (`additionalProperties: true`).
- **Breaking changes (`/2`)**: Renaming or removing existing keys, or changing their types and semantic meanings, will bump the major version to `sharpit-report/2`.

## BootUI-style CI gating with `jq`

The `severityCounts` list mirrors BootUI's order (`CRITICAL`, `HIGH`, `MEDIUM`, `LOW`, `INFO`), with all severities present.
Counts reflect non-dismissed findings.

You can gate CI pipelines using `jq` directly against `severityCounts`. For example, to fail if any `CRITICAL` or `HIGH` findings exist:

```bash
jq -e '([.severityCounts[] | select(.severity == "CRITICAL" or .severity == "HIGH") | .count] | add) == 0' sharpit-report.json
```

Or to verify that the overall report status passed:

```bash
jq -e '.status == "pass"' sharpit-report.json
```

## JUnit XML report

Specify `--sharpit-junit=PATH` to generate a standard JUnit XML file representing findings.

- Contains a single `<testsuite name="sharpit">`.
- Each finding in the report appears as a `<testcase>` with a `severity` property (`classname` is the advisor, `name` is the finding fingerprint). Only non-dismissed findings at or above `--sharpit-fail-on` carry a `<failure type="<ruleId>" message="...">`; dismissed and lower-severity findings are passing cases.
- A `<testcase name="sharpit.status">` records overall session state, failing if the run status is `fail` or `unknown` (without `--sharpit-allow-unknown`).
- The JUnit file contains findings only and does not duplicate the application tests (standard pytest `--junitxml` covers individual test results).
